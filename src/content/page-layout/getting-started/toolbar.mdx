## Buttons

```js
button.addEventListener('click', () => editor.commands.insertPageBreak())

function render() {
  button.disabled = !editor.can().insertPageBreak()
  boldButton.classList.toggle('is-active', editor.isActive('bold'))
}

editor.on('transaction', render)
```

- **A Command acts on the whole Node at the cursor**, also where a page boundary runs through it.
  `addRowAfter` adds the row below the cursor's row to the table on every page it is drawn on.
- **`editor.can()` asks the same document**, so a button is disabled exactly where the Command
  would do nothing. See [How Commands behave](/page-layout/reference/commands#how-commands-behave).
- **The Commands of the pages**, such as `insertPageBreak()`, `insertColumnBreak()`,
  `insertSectionBreak()`, `undo()` and `redo()`, answer `editor.can()` the same way. See
  [Breaks](/page-layout/features/breaks) and [Sections](/page-layout/features/sections).
- **In React**, `useEditorState` re-renders on the same event.

## Keeping the focus in the editor

A button that takes the focus loses the cursor a Command placed. When the editor is focused again,
the browser hands back the selection from before the Command: after `insertPageBreak()`, the cursor
jumps from the new page back to the foot of the page above.

Prevent the default of `mousedown` on the toolbar's buttons. The `click` still arrives:

```js
toolbar.addEventListener('mousedown', (event) => {
  if (event.target.closest('button')) {
    event.preventDefault()
  }
})
```

## Where the cursor is

```js
const engine = editor.storage.pageLayout.engine

engine.getActivePageIndex() // the page the cursor is on, counting from 0, or the one whose header or footer is open
engine.getPageCount()
engine.getActiveSectionIndex() // its section, or the one whose header or footer is open
engine.getFurnitureTarget() // the header or footer being edited, or null
engine.getTableContext() // the table and row at the cursor, or null
```

- **Read a status bar in `onChange`.** The pages are laid out again after a change, so a page
  number read during the `transaction` event may still be the one before it. The `onChange` option
  of `createPageLayoutEditor` is called once they are drawn.
- **Read again after a change.** Every number these return is true of the layout it was read from.
  Do not keep it.

```js
const editor = createPageLayoutEditor({
  element,
  content,
  extensions: [StarterKit, PageLayout.configure({ setup: pageSetup('A4') })],
  onChange: (editor) => {
    const engine = editor.storage.pageLayout.engine
    status.textContent = `Page ${engine.getActivePageIndex() + 1} of ${engine.getPageCount()}`
  },
})
```

## In a header or footer

- **The toolbar acts there.** A table, a list, a mark or a footnote goes into the header, and
  `editor.can()` and `editor.isActive()` answer for the cursor in it.
- **A button that only belongs in the text** can hide itself while `getFurnitureTarget()` is not
  `null`.
- **A button to leave the header** runs `editor.commands.closeFurniture()`. See
  [Getting in and out](/page-layout/features/header-and-footer#getting-in-and-out).

## A command the pages could not carry

A command that builds its change from what is drawn on one page, rather than from the document, can
write something the editor cannot carry back. The `onCommandOnPages` option of `PageLayout` is told
when that happens, with the command's name, which is how such a command is found. See
[Options](/page-layout/reference/options#the-document).
