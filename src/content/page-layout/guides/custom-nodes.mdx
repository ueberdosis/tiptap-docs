## Quick start

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('callout', {
  splitDepth: 'intoText',
})
```

- **Before the editor.** Call it at module level, before you create the editor. Several fields
  are read while the editor builds its schemas. A rule registered later reaches everything that
  is asked per Node, and nothing that was decided about the schema.
- **Merged field by field.** The later call wins per field, so you can change one thing about a
  type the engine already knows without restating the rest.
- **One registry per page.** Two editors on one page share the rules.

```js
// Your lists may break inside an item, not only between items.
defineNodeLayout('listItem', { splitDepth: 'intoText' })
```

A field whose type is `NodeLayoutRule` takes a value or a function of the Node. Use a value when
the answer belongs to the type, and a function when it depends on an attribute an author set:

```js
defineNodeLayout('card', {
  keepTogether: (node) => node.attrs.keepWhole !== false,
})
```

## The default

A type with no rule is moved whole: if it does not fit in the space left on the page, all of it
goes to the next one.

- **Children** run one below the next.
- **Nothing is repeated** on a continuation.
- **It never forces a page to end.**

For most Nodes that is right. It stops being right in three cases:

- **The Node can be taller than a page**, so moving it on does not help.
- **The Node has parts that should not be separated**, such as a card whose image lands on page
  two while its heading stays on page one.
- **The Node's children sit beside each other** rather than one below the next. Then a cut
  through it is not a position, and the engine has to be told. See
  [Children side by side](/page-layout/guides/custom-nodes#children-side-by-side).

## Layout rule fields

`defineNodeLayout(typeName, layout)` takes a `NodeLayout`. Every field is optional. `Rule<T>`
below is `NodeLayoutRule<T>`: `T`, or a function of the Node returning `T`.

| Field                 | Type                                                        | Default          | Description                                                                                                                                                              |
| --------------------- | ----------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `splitDepth`          | `Rule<SplitDepth>`                                          | `'none'`         | How deep a page may cut. See [How deep a page may cut](/page-layout/guides/custom-nodes#how-deep-a-page-may-cut)                                                         |
| `keepTogether`        | `Rule<boolean>`                                             | `false`          | Move the Node whole wherever that is possible. See [Keeping a Node whole](/page-layout/guides/custom-nodes#keeping-a-node-whole)                                         |
| `keepWithNext`        | `Rule<boolean>`                                             | `false`          | Stay on the page of the next block's first line. See [Keeping a block with the next](/page-layout/guides/custom-nodes#keeping-a-block-with-the-next)                     |
| `parallelChildren`    | `Rule<boolean>`                                             | `false`          | The children sit side by side. See [Children side by side](/page-layout/guides/custom-nodes#children-side-by-side)                                                       |
| `parallelCutRank`     | `Rule<ParallelCutRank>`                                     | `'equal'`        | What a cut through side-by-side children is worth                                                                                                                        |
| `parallelCutNode`     | `boolean`                                                   | `false`          | A type a side-by-side cut reopens. Read while the schemas are built                                                                                                      |
| `parallelChildKeys`   | `Rule<(string \| number \| null)[]>`                        | —                | Stable identities of the children, where generated children shift their indexes                                                                                          |
| `viewContent`         | `string`                                                    | The schema's own | The content expression a divided Node takes while a cut is open. Read while the schemas are built                                                                        |
| `childSpans`          | `Rule<NodeChildSpan[]>`                                     | `[]`             | Content that extends down through later children. See [Content that spans several children](/page-layout/guides/custom-nodes#content-that-spans-several-children)        |
| `repeatedLead`        | `Rule<number>`                                              | `0`              | Leading children every continuation repeats. See [Repeating something on every continuation](/page-layout/guides/custom-nodes#repeating-something-on-every-continuation) |
| `breakMarker`         | `Rule<boolean>`                                             | `false`          | A block that adds no height to the page it starts. See [Breaks of your own](/page-layout/guides/custom-nodes#breaks-of-your-own)                                         |
| `startsPage`          | `Rule<boolean>`                                             | `false`          | The page ends in front of the block                                                                                                                                      |
| `forcedCut`           | `Rule<'page' \| 'region' \| null>`                          | `null`           | What an inline marker ends where it sits                                                                                                                                 |
| `chapterLevel`        | `Rule<number \| null>`                                      | `null`           | The level at which the Node begins a chapter. See [Chapters](/page-layout/guides/custom-nodes#chapters)                                                                  |
| `remeasuresDocument`  | `Rule<boolean>`                                             | `false`          | A change to the block remeasures every block. See [Blocks that restyle the others](/page-layout/guides/custom-nodes#blocks-that-restyle-the-others)                      |
| `isWellFormed`        | `Rule<boolean>`                                             | `true`           | Whether the Node is consistent. See [Nodes that must stay consistent](/page-layout/guides/custom-nodes#nodes-that-must-stay-consistent)                                  |
| `completeEdit`        | `(edit: NodeEdit) => Transaction \| null`                   | —                | What an edit from the pages meant for the whole Node                                                                                                                     |
| `sourcePlugins`       | `() => Plugin[]`                                            | —                | Plugins that run on the document. See [A plugin that keeps the Node consistent](/page-layout/guides/custom-nodes#a-plugin-that-keeps-the-node-consistent)                |
| `viewCommands`        | `string[]`                                                  | —                | Commands of the Extension that run on the pages. See [Commands of your own Extension](/page-layout/guides/custom-nodes#commands-of-your-own-extension)                   |
| `sourceCommands`      | `string[]`                                                  | —                | Commands that run on the document even where a view list names them                                                                                                      |
| `labelAttribute`      | `string`                                                    | —                | The attribute a Decoration writes a label into. See [Labels drawn by a Decoration](/page-layout/guides/custom-nodes#labels-drawn-by-a-decoration)                        |
| `pageText`            | `(node, page: PageContext) => string \| null`               | —                | A value per page, in a header or footer. See [Values per page](/page-layout/guides/custom-nodes#values-per-page)                                                         |
| `ignoredMutation`     | `(mutation: ViewMutationRecord) => boolean`                 | —                | DOM changes of yours that every NodeView of the type lets pass. Read while the schemas are built                                                                         |
| `optionOverrides`     | `Record<string, unknown>`                                   | —                | Options set on the type's Extension in both schemas                                                                                                                      |
| `viewOptionOverrides` | `Record<string, unknown>`                                   | —                | Options set on the type's Extension in the editor that holds the pages only                                                                                              |
| `viewOptionDefaults`  | `Record<string, (editor: () => Editor \| null) => unknown>` | —                | Options filled in on that Extension where the integration left them `null`                                                                                               |
| `viewAttributes`      | `Record<string, unknown>`                                   | —                | Defaults for generated attributes, in the schema of the pages only                                                                                                       |
| `fragmentAdapter`     | `NodeFragmentAdapter`                                       | —                | Builds and rejoins fragments that need generated children at a page cut                                                                                                  |

- **Read while the schemas are built.** `parallelCutNode`, `viewContent`, `ignoredMutation`,
  `viewCommands`, `sourceCommands` and the option fields take a value, not a function of the
  Node. There is no Node to ask yet.
- **Without `isWellFormed`**, a Node counts as consistent, and an edit from the pages is never
  refused for leaving it inconsistent.

## How deep a page may cut

| `splitDepth`        | Description                                                   |
| ------------------- | ------------------------------------------------------------- |
| `'none'`            | Never cut. The Node moves to the next page whole. The default |
| `'betweenChildren'` | Cut between two children, never inside one. What a list does  |
| `'intoText'`        | Cut between two lines of text. What a paragraph does          |

A Node taller than a page is cut anyway, whatever this says. It fits on no page, so the engine
goes one level deeper for that Node rather than letting it hang off the sheet.

## Keeping a Node whole

```js
defineNodeLayout('card', {
  splitDepth: 'betweenChildren',
  keepTogether: true,
})
```

- **Whether to cut at all.** `splitDepth` says how deep a cut may go. `keepTogether` says whether
  to make one at all.
- **Cut only at the top.** With it set, the Node is cut only when it is already at the top of an
  empty page. Everywhere else it moves on whole.
- **A preference, not a prohibition**, like _Keep lines together_ in Word. A card of forty rows
  with `keepTogether` on does not vanish and does not overflow. It breaks as it otherwise would,
  which for the card above is between its children.

## Keeping a block with the next

```js
defineNodeLayout('figureCaption', { keepWithNext: true })
```

The block stays on the page of the first line of the block after it. When the two do not fit
together in what is left of the page, the page ends above it. Word calls it _Keep with next_, and
it keeps a heading from standing alone at the foot of a page.

- **A run of such blocks** moves as one.
- **A next block that may not be cut** counts whole.
- **A preference as well.** The block stays where it is when it is already at the top of a page,
  and when the run and the next line would not fit on a page of their own either.
- **Before a break.** It also stays in front of a page break or a section that starts a page.
- **Top level only.** The rule applies to the blocks at the top level of the document.

### Per block, from a style

What a layout rule says about a type, `blockBreaksOf` says about one block, for a page setting
kept somewhere else, such as a paragraph style or an attribute of your own:

```js
PageLayout.configure({
  blockBreaksOf: (block, doc) => (block.attrs.keepWithNext ? { keepWithNext: true } : null),
})
```

| Field             | Type      | Description                                                      |
| ----------------- | --------- | ---------------------------------------------------------------- |
| `keepWithNext`    | `boolean` | As above                                                         |
| `keepTogether`    | `boolean` | As `keepTogether` in a layout rule: Word's _Keep lines together_ |
| `pageBreakBefore` | `boolean` | The page ends in front of the block                              |

- **Adds only.** `null`, or a field left out, adds nothing to what the type's rule says. Neither
  can turn off what the rule turns on.
- **Answer quickly.** It is asked for every top-level block on every layout, so it should answer
  from what it has rather than walk the document.
- **From a style.** [Document Styles](/page-layout/extensions/document-styles/on-pages#line-and-page-breaks)
  brings one that reads the paragraph's style.

## Children side by side

If your Node's children sit beside each other, such as a row of cells or a strip of panels, a cut
through it is a height rather than a position. It falls at a different offset in each child.

```js
defineNodeLayout('panelStrip', {
  splitDepth: 'none',
  parallelChildren: true,
  parallelCutRank: 'equal',
  parallelCutNode: true,
})

defineNodeLayout('panel', {
  parallelCutNode: true,
  viewContent: 'block*',
})
```

| Field              | Description                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parallelChildren` | The children are side by side. Such a container is never cut between them, so `splitDepth` is `'none'`                                                                          |
| `parallelCutRank`  | `'equal'` weighs the cut like any other, so whichever option fills more of the page wins. `'lastResort'` moves the Node on whole and cuts it only when moving it would not help |
| `parallelCutNode`  | Names the types the cut reopens: the container and the children it divides                                                                                                      |
| `viewContent`      | The content expression a divided child takes while the cut is open                                                                                                              |

- **Empty halves.** Both halves of a cut keep every child, so the columns stay lined up. That can
  leave a child shorter than the cut with nothing in it.
- **Relax the content.** If your schema says `block+`, give the child `'block*'` in `viewContent`.
- **Only while cut.** That relaxation applies only while the boundary sits inside the Node, and
  never to the document you save.

### Content that spans several children

Use `childSpans` when content inside one child extends down through later children, as a merged
table cell does across rows. It takes an array, or a function of the Node that returns one.

| Field           | Type     | Description                                                                                                            |
| --------------- | -------- | ---------------------------------------------------------------------------------------------------------------------- |
| `contentOffset` | `number` | The descendant's opening-token offset inside the container's content. Count opening and closing tokens as well as text |
| `fromChild`     | `number` | The first covered direct-child index, from zero                                                                        |
| `toChild`       | `number` | The index after the last covered direct child                                                                          |

- **Containers only.** Each entry identifies a container with Tiptap child content. Do not point
  an entry at a leaf Node that renders content from attributes.
- **Where a page may end.** Between those children, or inside a later child, only after the
  earlier spanning content fits above the cut.
- **An empty container** does not block the cut.
- **Tables.** The table rule supplies these entries for merged cells. You do not configure them
  for tables.

## Repeating something on every continuation

`repeatedLead` is how many leading children every continuation repeats, as a table does with a
header row.

```js
defineNodeLayout('dataBlock', {
  splitDepth: 'betweenChildren',
  repeatedLead: (node) => (node.attrs.repeatHeading ? 1 : 0),
})
```

The repeated children are drawn above each continuation, and the page they are drawn on pays
their height out of its content space.

## Breaks of your own

For a Node that is a break rather than one affected by one. The engine's own page, column and
section breaks are in [Breaks](/page-layout/core-concepts/breaks).

```js
// A block that always starts a sheet and adds no height to it.
defineNodeLayout('chapterStart', {
  breakMarker: true,
  startsPage: true,
})

// An inline marker that ends the page where it sits.
defineNodeLayout('myPageBreak', {
  forcedCut: 'page',
})
```

| Field         | Description                                                                                                          |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| `breakMarker` | The block contributes no height to the page it starts. Blocks only                                                   |
| `startsPage`  | The page ends in front of it. Blocks only                                                                            |
| `forcedCut`   | For an inline marker: `'page'` ends the sheet, `'region'` ends the column. In a one-column section they are the same |

## Chapters

A Node that begins a chapter says at which level, for a section that writes the chapter in front
of its page numbers, such as `2-14`. Tiptap's `heading` already does, at its `level`.

```js
defineNodeLayout('chapterTitle', {
  chapterLevel: (node) => node.attrs.depth ?? 1,
})
```

`null` is a Node that begins none. See
[Page numbers](/page-layout/core-concepts/page-numbers#with-the-chapter-in-front) for how the number is chosen.

## Blocks that restyle the others

The editor measures a block again when the block changes. A block whose change makes other blocks
look different, such as definitions the rest of the document is drawn by, says so. Every block is
then measured again when it is added, removed or changed:

```js
defineNodeLayout('themeSettings', {
  breakMarker: true,
  remeasuresDocument: true,
})
```

- **Document Styles** does this for its definitions. See
  [Document Styles](/page-layout/extensions/document-styles/on-pages).
- **It is expensive.** Remeasuring the whole document costs as much as a change of the page width,
  so keep it to blocks that change rarely.
- **Top level.** It is asked of top-level blocks on every change, so the answer should be cheap.

## Nodes that must stay consistent

An edit made on the pages sees the part of a Node that is on one page. For a Node that has to be
consistent as a whole, such as a table whose rows all have the same width, such an edit can be
right for that part and wrong for the Node.

Say what consistent means, and an edit from the pages that would leave the Node inconsistent does
nothing instead:

```js
import { TableMap } from '@tiptap/pm/tables'

defineNodeLayout('table', {
  isWellFormed: (node) => TableMap.get(node).problems === null,
})
```

- **Already inconsistent.** A Node that is inconsistent already stays editable.
- **Counted.** `editor.storage.pageLayout.engine.getDiagnostics()` counts a refused edit in
  `refusedTransactions`, with `lastRefusedReason` set to `'inconsistent-in-the-document'`.
- **Reported.** An edit no command made is reported on the console once.

### Completing an edit

Where you can tell what such an edit meant for the whole Node, say so, and that is written instead
of refusing the edit. `completeEdit` receives the edit. It returns a Transaction on `state` that
does to the whole Node what the edit did to its part, or `null` to refuse it.

The usual answer is the command that made the edit, run again on the whole Node at the place the
reader ran it. That is what it does in an editor without pages.

```js
import { insertStep, removeStep } from './timeline-commands'

defineNodeLayout('timeline', {
  isWellFormed: (node) => node.childCount === node.attrs.steps,
  completeEdit: (edit) => {
    const command = [insertStep, removeStep].find(edit.ranOnThePages)
    return command ? edit.onTheDocument(command) : null
  },
})
```

The `NodeEdit` it receives:

| Field           | Type                                        | Description                                                                                |
| --------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `ranOnThePages` | `(command: Command) => boolean`             | `true` if the command, run where the reader ran it, makes exactly this edit                |
| `onTheDocument` | `(command: Command) => Transaction \| null` | Runs the command on the document at the reader's selection there. `null` where it declines |
| `state`         | `EditorState`                               | The editor state of the document before the edit. Build your own Transaction on it         |
| `pos`           | `number`                                    | Where the Node starts in `state.doc`                                                       |
| `before`        | `Node`                                      | The Node before the edit                                                                   |
| `after`         | `Node`                                      | The Node as the edit left it: right for the part on one page, inconsistent as a whole      |
| `transaction`   | `Transaction`                               | The edit itself, its steps applying to `state.doc`                                         |

- **Commands.** A command here has the form `(state, dispatch) => boolean`.
- **Checked like the edit.** If the returned Transaction leaves the Node inconsistent, the edit is
  refused all the same.
- **Only when needed.** `completeEdit` is asked only for an edit that would be refused, and only
  when `isWellFormed` is set.
- **Counted.** `getDiagnostics()` counts a completed edit in `completedEdits`.

### Tables

The engine's rule for `table` completes edits with the table extension's commands:
`addColumnBefore`, `addColumnAfter`, `deleteColumn`, `addRowBefore`, `addRowAfter`, `deleteRow`,
`mergeCells`, `splitCell` and the three header toggles. A table menu that runs them on
`editor.state` works unchanged.

- **A column added on one page** goes into every row.
- **`splitCell`** on a cell that spans rows across the page boundary splits the whole cell.
- **`addRowAfter`** from such a cell adds the row below the whole cell, not at the foot of the
  page.
- **Refused.** An edit that is not one of these commands on its own, such as a command followed by
  steps of the component's own in the same Transaction, is refused.
- **Also refused.** An edit two of the commands make alike on the page but differently on the
  whole table.

### A plugin that keeps the Node consistent

A plugin an extension registers runs on the pages the editor shows. An `appendTransaction` that
repairs a Node sees and repairs only the part of it on one page. Give such a pass to the layout
rule instead, and it runs on the document, where the Node is whole:

```js
import { Plugin } from '@tiptap/pm/state'

defineNodeLayout('timeline', {
  sourcePlugins: () => [
    new Plugin({
      appendTransaction: (transactions, oldState, newState) => numberStepsTransaction(newState),
    }),
  ],
})
```

- **New instances.** `sourcePlugins` is called once per editor whose schema has the type, so it
  returns new plugin instances each time.
- **One undo step.** What such a plugin appends goes into the same undo step as the change it
  answers.
- **Your own Extension.** An Extension of your own brings the same pass in `addDocumentPlugins`.
- **Tables.** The engine's rule for `table` adds one: a row inserted by a command gets the column
  widths of the rows around it, in every cell. Cells of a column without a width stay without one.

## Commands of your own Extension

Every command of an extension runs on the document, not on the pages.

- **Reading and writing.** It reads the document and the reader's selection in it, and writes
  through `tr` into the document.
- **Undoable.** The change is undoable, with the caret it placed kept.
- **`can()`** asks the document too.
- **Chains.** A command calling another through `commands` or `chain()` keeps writing into the same
  Transaction.
- **Positions.** A position a command takes or reads off the selection is a position in
  `editor.storage.pageLayout.engine.getSourceDocument()`.

### View commands

A few commands belong to what the editor shows rather than to the document:

- one that moves the caret through what is drawn,
- one that only sends a meta to a plugin of the editor, such as a toggle or a refresh of drawn
  labels. Run on the document, the meta reaches no plugin.

Name those in `addViewCommands`, and they run on the pages as they would in an editor without
pages. It is asked once, before the editor exists, and returns command names. An editor without
pages ignores it.

```js
const Comments = Extension.create({
  name: 'comments',
  addCommands() {
    return { addComment, resolveComment, removeComment, toggleComments }
  },
  addViewCommands() {
    return ['toggleComments']
  },
})
```

`addSourceCommands`, and `sourceCommands` in a layout rule, name commands that run on the document
even where a view list names them as well.

### TypeScript

Declare the fields once in your package:

```ts
declare module '@tiptap/core' {
  interface ExtensionConfig<Options, Storage> {
    addSourceCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
    addViewCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
  }
  interface NodeConfig<Options, Storage> {
    addSourceCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
    addViewCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
  }
}
```

Write it exactly like this. Other packages declare the same fields, and TypeScript merges the
declarations only when they are identical.

### Commands of another Extension

For an extension somebody else wrote, name its view commands in a layout rule under the
extension's name. Both lists are used together:

```js
defineNodeLayout('comments', {
  viewCommands: ['toggleComments'],
})
```

- **Tables.** The table extension's `goToNextCell` and `goToPreviousCell` run on the document,
  including when Tab adds a row before moving to its first cell.
- **Pro packages.** The commands of [Footnotes](/page-layout/extensions/footnotes/on-pages),
  [Cross-references](/page-layout/extensions/cross-references/on-pages),
  [Bookmarks](/page-layout/extensions/overview#bookmarks),
  [Outline numbering](/page-layout/extensions/outline-numbering/on-pages) and number formats are
  named by their packages.

### Tiptap's own commands

Tiptap's own commands, such as `insertContent`, `setTextSelection` and `toggleMark` called
directly, are not an extension's, and run on the pages. To write at a position in the document,
use `editor.commands.onSourceDocument(command)` or `engine.dispatchSourceTransaction(tr)`. See
[Components that change the document](/page-layout/getting-started/components).

### A view command that writes to the pages

A view command that writes something the editor cannot take back to the document as written is
reported. Without an `onCommandOnPages` option, the editor warns on the console once per command.
With one, it is called instead, with the command, its Extension and what went wrong:

```js
PageLayout.configure({
  onCommandOnPages: ({ command, extension, reason, refused }) => {
    reportToYourLogging(`${extension}.${command}: ${reason}`)
  },
})
```

- **`refused: true`** means nothing was written.
- **`refused: false`** means the edit was worked out from the difference between the two states.
  That is right for the text and may lose where the caret was.
- **Counted.** `editor.storage.pageLayout.engine.getDiagnostics()` counts them in
  `commandsOnPages` and holds the last one in `lastCommandOnPages`.

## What the engine needs from your rendering

A NodeView is fine, and so is anything a browser can lay out. The sections below are what to
watch.

### Heights that arrive late

The height on screen is the height the pages are planned from. A NodeView that renders late, such
as an image without dimensions, a chart drawn after a fetch, or a font that arrives afterwards, is
measured at whatever height it has at that moment.

- **React.** A React NodeView in an editor built with `usePageLayoutEditor` is measured again
  whenever its height changes.
- **Any other NodeView** says when its rendering changed, with `measureAgain`.

```js
image.addEventListener('load', () => {
  editor.storage.pageLayout.engine.measureAgain([dom])
})
```

- **What it does.** `measureAgain` takes the NodeView's elements and lays out the pages again if
  one of them came out at another height.
- **Reserve the space.** The pages move when the height arrives, so reserve the space in CSS where
  you know it.

### Do not decide layout in the rendering

No `page-break-inside`, no fixed height meant to make something fit, and no scrolling container
hiding part of the Node.

### A cut Node is rendered twice

A cut Node is rendered once per fragment, and the second fragment is marked as a continuation.

- **Per-mount state.** A NodeView that counts its instances, keeps state per mount or registers
  something globally on create will notice. Keep state on the Node.
- **Whole-Node actions.** `updateAttributes` and `deleteNode` act on the whole Node from either
  fragment.
- **Which fragment.** `engine.sourceNodeOfView(getPos())` says which fragment it is:
  `{ pos, node, piece: { index, count } }`.

### Changes the editor makes to a table

Every part of a table on a page gets the columns of the whole table, so the editor writes the
`<colgroup>` and the width on the `<table>` itself.

- **Your table NodeView.** One built on `TableView` from `@tiptap/pm/tables` is told to leave
  those changes alone. Its `ignoreMutation` still answers for everything else.
- **Your own DOM changes.** Code of yours that writes into the rendering of a Node another
  extension draws says which changes are its own, and every NodeView of that type lets them pass:

```js
defineNodeLayout('image', {
  ignoredMutation: (mutation) => mutation.target.classList?.contains('my-image-badge'),
})
```

### Labels drawn by a Decoration

A measurement is kept until the Node changes. A number a Decoration writes into an attribute for
CSS to print, such as a note mark or a figure number, changes without the Node changing. Name the
attribute, and the line is measured again when the number gets a digit longer.

This is the rule the footnote reference comes with:

```js
defineNodeLayout('footnoteReference', {
  labelAttribute: 'data-tt-footnote-number',
})
```

- **Sheets not drawn.** A label on a sheet that is not drawn is noticed when the sheet is drawn.
- **Only a label whose width varies.** A Decoration that adds a class or a color moves nothing.
- **Blocks too.** The Node may be a block, such as a heading whose outline number is drawn in
  front of its text:

```js
defineNodeLayout('heading', { labelAttribute: 'data-tt-outline-number' })
```

### Values per page

A Node in a header or footer is the same Node on every page. What should differ per page, such as
a number or a count, is asked per page with `pageText` and written into the `labelAttribute`:

```js
defineNodeLayout('pageVariable', {
  labelAttribute: 'page-variable-text',
  pageText: (node, page) => page.label,
})
```

- **`page`** is a `PageContext`, described under
  [Your own value per page](/page-layout/core-concepts/page-numbers#your-own-value-per-page).
- **Needs a label attribute.** A type without `labelAttribute` draws nothing from `pageText`.
- **Bands only.** Only Nodes in headers and footers are asked.
- **Height per mask.** A band is measured once per mask, so a value that wraps onto a second line
  on one page does not make that page's band taller.

### Counting Nodes

Counting Nodes of the Editor's document counts the pages' copy of them. A block cut across two
pages is two Nodes there, and the header or footer being edited is a Node too. An Extension that
numbers or lists Nodes leaves those out with `ignoreLayoutArtifacts`:

```js
import { ignoreLayoutArtifacts } from '@tiptap-pro/extension-page-layout'

editor.state.doc.descendants((node) => {
  const skip = ignoreLayoutArtifacts(node)
  if (skip === true) {
    return false // not a Node of the text, nor is anything in it
  }
  if (skip === 'descend') {
    return true // the rest of a list or quote: not a Node of the text, its items are
  }
  // …
})
```

## What must never go into the document

No page numbers, no "this is a continuation" flag, no measured height, and no break your code
inserted because something did not fit.

- **They change.** All of those change when a font loads, when the paper changes, or when a
  collaborator on a different screen edits the same text.
- **They would spread.** In the document they would be saved to your database and synchronized to
  everybody, and the next reader would see somebody else's page breaks.
- **Ask instead.** If your Node needs to know which page it is on, ask the
  [page map](/page-layout/core-concepts/page-numbers). It is worked out from the document, and it is up to date
  after every edit.
- **In a header or footer**, `pageText` is the way.
