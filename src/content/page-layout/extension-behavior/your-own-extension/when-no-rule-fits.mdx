The document is what the user writes and you save, without pages.

The pages are the copy of it that the editor shows and edits, each drawn on a sheet, an element of its own. So a node cut by the end of a page is one node in the document and two parts on the pages.

## Deciding per block

`blockBreaksOf` is a `PageLayout` option that says for one block what a layout rule says for a type, such as for a paragraph where the user set a `keepWithNext` attribute:

```js
import { PageLayout } from '@tiptap-pro/extension-page-layout'

PageLayout.configure({
  blockBreaksOf: (block, doc) => (block.attrs.keepWithNext ? { keepWithNext: true } : null),
})
```

`block` is a top-level block and `doc` the document it is in. The answer takes the booleans [`keepWithNext`](/page-layout/extension-behavior/your-own-extension/layout-rules#keeping-a-block-with-the-next) and [`keepTogether`](/page-layout/extension-behavior/your-own-extension/layout-rules#keeping-a-node-whole), which work as in a rule, and `pageBreakBefore`, which ends the page in front of the block.

`blockBreaksOf` only adds: `null` or a field left out adds nothing, and it cannot turn off what the type's rule turns on.

Page Layout asks it for every top-level block on every layout, so it has to answer quickly, and the same for the same block. [Document styles](/page-layout/extension-behavior/document-styles#line-and-page-breaks) brings one, `styleBlockBreaks`, which reads the paragraph's style.

## Nodes that must stay consistent

A node is consistent when it is valid as a whole, such as a table whose rows all have the same number of columns.

An edit made on the pages sees only the part of a node on one page. So a column added to a table cut across two pages lands in the rows of one page only.

`isWellFormed` tells Page Layout when a node of your type is consistent, so an edit from the pages that would make it inconsistent is refused and does nothing. This `timeline` is consistent when it has as many children as its `steps` attribute says:

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('timeline', {
  isWellFormed: (node) => node.childCount === node.attrs.steps,
})
```

A node that is already inconsistent stays editable. `isWellFormed` is asked of every node an edit touched, before and after it, so it should answer quickly. Without it, a node always counts as consistent.

`getDiagnostics()` on the engine, `editor.storage.pageLayout.engine`, counts refused edits in `refusedTransactions`, with `lastRefusedReason` set to `'inconsistent-in-the-document'`. [What happens to an edit made on the pages](/page-layout/getting-started/document-and-pages/writing#what-happens-to-an-edit-made-on-the-pages) describes the console warning.

### Completing an edit

`completeEdit` turns a refused edit into the edit the user meant for the whole node, so an "Add step" button works instead of doing nothing. It receives the edit and returns a transaction on the document, or `null` to refuse it.

The usual answer finds the command that made the edit and runs it again on the whole node. Here, `insertStep` and `removeStep` are your own functions `(state, dispatch) => boolean`, which ProseMirror calls commands, and the timeline's buttons run them on `editor.state`:

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'
import { insertStep, removeStep } from './timeline-commands'

defineNodeLayout('timeline', {
  completeEdit: (edit) => {
    const command = [insertStep, removeStep].find((command) => edit.ranOnThePages(command))
    return command ? edit.onTheDocument(command) : null
  },
})
```

`edit.ranOnThePages(command)` is `true` if the command, run on the pages where the user ran it, makes exactly this edit. `edit.onTheDocument(command)` runs it on the document, where the node is whole, at the user's selection there. It returns the transaction, or `null` if the command declines.

To build a transaction yourself, `edit` also has `state`, the document's `EditorState` before the edit, and `pos`, where the node starts in `state.doc`.

`before` and `after` are the node before and after the edit, `after` right for one page and inconsistent as a whole. `transaction` is the edit, its steps applying to `state.doc`.

`completeEdit` is asked only for an edit that would be refused. It is also asked only when the type has `isWellFormed`. A transaction that leaves the node inconsistent is refused all the same. `getDiagnostics()` counts completed edits in `completedEdits`.

### Tables

The table rule completes edits made with `addColumnBefore`, `addColumnAfter`, `deleteColumn`, `addRowBefore`, `addRowAfter`, `deleteRow`, `mergeCells`, `splitCell`, `toggleHeaderRow`, `toggleHeaderColumn` and `toggleHeaderCell`. So a table menu that runs them on `editor.state` works unchanged: a column added on one page goes into every row.

On a cell that spans rows across the end of a page, `splitCell` splits the whole cell, and `addRowAfter` adds the row after it.

It refuses a command plus other steps in one transaction, such as a component's own. It also refuses an edit that two commands make alike on the page but differently on the whole table, because it cannot tell which was meant.

### A plugin that keeps the node consistent

A plugin your extension registers runs on the pages, so an `appendTransaction` that repairs a node repairs only the part on one page.

Plugins from `sourcePlugins` in a layout rule run on the document, where the node is whole. Here, `numberStepsTransaction` is your own function that returns a transaction or `null`:

```js
import { Plugin } from '@tiptap/pm/state'
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('timeline', {
  sourcePlugins: () => [
    new Plugin({
      appendTransaction: (transactions, oldState, newState) => numberStepsTransaction(newState),
    }),
  ],
})
```

`sourcePlugins` is called once for each editor whose schema has the type, so create the plugins inside the function. What such a plugin appends is undone in one step with the change it answers.

In an extension you wrote, `addDocumentPlugins` does the same without a rule, called with `this` set to `{ name, options, storage, editor }`.

The table rule adds such a plugin. It gives a row a command inserts the column widths of the rows around it, and a column without a width stays without one.

## Commands of your own extension

Write the commands of your extension as in any Tiptap editor. They run on the document, not on the pages: they read the document and the user's selection there, and write through `tr` into the document.

The change can be undone and keeps the caret the command placed. `can()` asks the document too, and a command that calls another through `commands` or `chain()` writes into the same transaction.

So a position a command takes or reads off the selection is a position in the document, as `editor.storage.pageLayout.engine.getSourceDocument()` returns it, not in `editor.state`.

### View commands

A view command runs on the pages instead, because what it acts on exists only there. It moves the caret through what is drawn, such as to the next table cell on the screen.

Or it only sends a meta, a value on a transaction, to a plugin of the editor, such as a toggle or a refresh of drawn labels. The plugins run on the pages, so on the document none would read it.

Name these commands in `addViewCommands`, and they run on the pages as in an editor without pages. Here, `toggleAnnotations` only tells the extension's plugin to show or hide its highlights:

```js
import { Extension } from '@tiptap/core'

const Annotations = Extension.create({
  name: 'annotations',
  addCommands() {
    return {
      toggleAnnotations:
        () =>
        ({ tr }) => {
          tr.setMeta('annotations', 'toggle')
          return true
        },
    }
  },
  addViewCommands() {
    return ['toggleAnnotations']
  },
})
```

`addViewCommands` is asked once, before the editor exists, and returns command names. An editor without pages ignores it. To keep a command on the document although a view list names it, name it in `addSourceCommands`, or in `sourceCommands` in a rule. `addSourceCommands` wins over a rule's `viewCommands`.

### TypeScript

In TypeScript, declare `addViewCommands` and `addSourceCommands` so that your extension may have them. Write the declaration exactly like this, because TypeScript merges it with that of other packages only when they are identical:

```ts
declare module '@tiptap/core' {
  interface ExtensionConfig<Options, Storage> {
    addSourceCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
    addViewCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
  }
  interface NodeConfig<Options, Storage> {
    addSourceCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
    addViewCommands?: (this: { name: string; options: Options; storage?: Storage }) => string[]
  }
}
```

### A view command that writes to the pages

A view command should act only at the caret or only send a meta, as in [View commands](/page-layout/extension-behavior/your-own-extension/when-no-rule-fits#view-commands).

When it reads or writes more, such as the whole document, the end of it or every node of a type, it reads the pages instead of the document. The end of the document, for example, is behind the last sheet on the pages.

Page Layout then cannot copy its edit to the document as written. To find such a command, watch for its report through the `onCommandOnPages` option or a console warning, see [A command the pages could not carry](/page-layout/getting-started/document-and-pages/writing#a-command-the-pages-could-not-carry).

To fix a command for good, run it on the document: take it out of `addViewCommands`, or name it in `addSourceCommands`. To keep it on the pages and make one edit on the document, pass that edit to `editor.commands.onSourceDocument(command)` as a function `(state, dispatch) => boolean`, a ProseMirror command.

Page Layout either drops such an edit or works it out again from what changed on the pages. An edit worked out again has the right text, but may lose the caret. `getDiagnostics()` counts the reports in `commandsOnPages` and keeps the last in `lastCommandOnPages`.

## Commands of another extension

For an extension somebody else wrote, name its view commands in a layout rule under the extension's name. Page Layout uses this `viewCommands` list together with the extension's own `addViewCommands`:

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('annotations', { viewCommands: ['toggleAnnotations'] })
```

The table extension's `goToNextCell` and `goToPreviousCell` run on the document, also when Tab adds a row first. Footnotes, Cross-references, Bookmarks, Outline numbering and Number formats name their own view and source commands.

### Tiptap's own commands

Tiptap's own commands, such as `insertContent`, `setTextSelection` or `toggleMark` called directly, belong to no extension, so they run on the pages. A position you pass them is a position in the pages.

To write at a position in the document, use `editor.commands.onSourceDocument(command)` or `engine.dispatchSourceTransaction(tr)`, as [Writing at a position](/page-layout/getting-started/document-and-pages/writing#writing-at-a-position) shows. With the `experimentalSourceState` option, they run on the document. See [editor.state as the document](/page-layout/getting-started/document-and-pages/writing#editorstate-as-the-document).

## What the engine needs from your rendering

A NodeView, the code that renders a node, works on pages, and so does anything a browser can lay out. Page Layout plans the pages from the height a node has on screen.

### Heights that arrive late

A NodeView that renders late, such as a chart drawn after a fetch, is measured at the height it has at that moment, so call `measureAgain` when its height changes. Here, `fetchData` and `drawChart` are your own, and `dom` is the NodeView's element:

```js
fetchData().then((data) => {
  drawChart(dom, data)
  editor.storage.pageLayout.engine.measureAgain([dom])
})
```

`measureAgain` lays the pages out again if one of the elements came out at another height. It passes over elements in a header, footer or footnote, on a sheet that is not drawn, or no longer in the editor.

Reserve the space in CSS where you know it, because the pages move when the height arrives.

Page Layout measures again by itself when an `IMG`, `VIDEO`, `IFRAME`, `OBJECT` or `EMBED` fires `load`, `error` or `loadedmetadata`, and when a [React NodeView](/page-layout/extension-behavior/your-own-extension/react-nodeviews) changes height.

### Do not decide layout in the rendering

Leave where pages end to Page Layout: no `page-break-inside`, no fixed height meant to make something fit, and no scrolling container that hides part of the node.

### A cut node is rendered twice

A cut node is rendered once per part, and the part on the later page carries `data-tt-split-continuation`, for a label or indent that should not repeat.

A NodeView that counts instances, keeps state per mount or registers something globally on create notices the second render. So keep such state in the node's attributes, which both parts share.

`updateAttributes` and `deleteNode` act on the whole node from either part. `getPos()` is a position in the pages, so a transaction of your own at `getPos()`, or a command, writes only the part it is on.

To write to the whole node, get its position in the document from [`engine.sourceNodeOfView(getPos())`](/page-layout/extension-behavior/your-own-extension/react-nodeviews#the-node-behind-a-component), and pass it to `onSourceDocument` or `dispatchSourceTransaction`.

### DOM changes Page Layout makes

Code of yours that writes into the rendering of another extension's node names its DOM changes with `ignoredMutation`, and every NodeView of that type lets them pass:

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('image', {
  ignoredMutation: (mutation) => mutation.target.classList?.contains('my-image-badge'),
})
```

Page Layout itself writes the `<colgroup>` and the width of the `<table>` on every part of a table, so each part has the columns of the whole table. Every NodeView of the table lets these changes pass, and its own `ignoreMutation` answers for the rest.

### Labels drawn by a decoration

A decoration draws something over the document without changing it. When it writes a number into an attribute for CSS to draw, such as a footnote mark, the node does not change, so Page Layout keeps its old measurement.

Name the attribute in `labelAttribute`, and the line is measured again when the label gets wider, such as by one digit:

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('footnoteReference', { labelAttribute: 'data-tt-footnote-number' })
```

The footnote reference comes with this rule. A block works too, such as a heading with an outline number: `defineNodeLayout('heading', { labelAttribute: 'data-tt-outline-number' })`.

A label on a sheet that is not drawn is noticed when it is drawn. Use `labelAttribute` only for a label whose width varies, because a class or a color moves nothing.

## Values per page

A node in a header or footer is the same node on every page. For a value that differs per page, such as "Page iv of 12", give the type a `pageText` function and a `labelAttribute`.

Page Layout calls `pageText` with the node and the page on every page, and writes the answer into that attribute for your CSS to draw. Here, `pageVariable` stands for your node type:

```js
import { defineNodeLayout } from '@tiptap-pro/extension-page-layout'

defineNodeLayout('pageVariable', {
  labelAttribute: 'page-variable-text',
  pageText: (node, page) => `Page ${page.label} of ${page.pageCount}`,
})
```

`page.label` is the page number in its section's format, and `page.pageCount` the number of pages. [Your own value per page](/page-layout/features/page-numbers#your-own-value-per-page) shows the CSS and every field of `page`.

## Counting nodes

Counting the nodes of `editor.state.doc` counts the pages, where a block cut across two pages is two nodes, and the header or footer being edited is a node too. `ignoreLayoutArtifacts` skips what exists only on the pages:

```js
import { ignoreLayoutArtifacts } from '@tiptap-pro/extension-page-layout'

editor.state.doc.descendants((node) => {
  const skip = ignoreLayoutArtifacts(node)
  if (skip === true) {
    return false
  }
  if (skip === 'descend') {
    return true
  }
  // Count the node here.
})
```

[Packages that work without pages](/page-layout/extension-behavior#packages-that-work-without-pages) explains each answer and `isLayoutArtifact`.

## What is not possible

No rule keeps a nested node together, because `keepTogether`, `keepWithNext`, `startsPage` and `blockBreaksOf` apply to top-level blocks only. No rule keeps a minimum number of lines on either side of a cut, so there is no widow and orphan control.

Repeated children are drawn for `table` only, and the table's merged cells cannot be reused, as [fragmentAdapter](/page-layout/extension-behavior/your-own-extension/node-layout-reference#fragmentadapter) explains. [Your own extension](/page-layout/extension-behavior/your-own-extension) lists the other limits: clipped nodes, and rules shared by every editor and needed before the editor is created.

## What must never go into the document

Never put page numbers, a continuation flag, a measured height or a break inserted because something did not fit into the document. These change when a font loads, the paper changes, or a collaborator on another screen edits the same text.

In the document they would be saved and synchronized, and the next user would see somebody else's page breaks.

To know which page a node is on, ask [the page map](/page-layout/getting-started/document-and-pages/reading#the-page-map). It is worked out from the current layout of the document, so ask it again after an edit. In a header or footer, use [`pageText`](/page-layout/extension-behavior/your-own-extension/when-no-rule-fits#values-per-page).
