Exports from `@tiptap-pro/extension-slot`.

## Extension

`Slot` installs `blockSlot`, `inlineSlot`, indexing, editing mechanics, clipboard
identity handling and optional input rules. Its extension/storage name is `slot`.
Use one `Slot` instance. The package also exports `BlockSlot` and `InlineSlot`
as ordinary Tiptap Node extensions, which developers can independently
`.configure()` and `.extend()`. Pass customized instances to `Slot` through its
`blockSlot` and `inlineSlot` options; `Slot` installs each exactly once. Do not
also register those instances in the Editor's top-level extensions array.
No validation rule changes the Schema dynamically. See
[Rendering and customization](/compose/slots/rendering) for default styling, custom
NodeViews, HTML serialization and reactive view updates.

```ts
import { Slot } from '@tiptap-pro/extension-slot'

const extensions = [
  StarterKit,
  Slot.configure({
    validators: { registeredPerson },
    crossFieldValidators: { deviationNeedsJustification },
  }),
]
```

## Configuration types

```ts
type JsonValue =
  | null
  | boolean
  | number
  | string
  | JsonValue[]
  | {
      [key: string]: JsonValue
    }
type SlotKind = 'block' | 'inline'

interface SlotContentType {
  type: string
  attributes?: Record<string, JsonValue[]>
}

interface ValidatorReference {
  name: string
  params?: JsonValue
}

interface CrossFieldRule {
  id?: string
  validator: string
  fields: string[]
  params?: JsonValue
}

interface SlotConfig {
  version: 1
  label?: string
  instructions?: string
  placeholder?: string
  defaultContent?: JSONContent[]
  required?: boolean
  allowedBlocks?: SlotContentType[]
  allowedInline?: SlotContentType[]
  allowText?: boolean
  allowedMarks?: SlotContentType[]
  constraints?: {
    minLength?: number
    maxLength?: number
    minChildren?: number
    maxChildren?: number
    pattern?: { source: string; flags?: string; message?: string }
    values?: string[]
  }
  nesting?: {
    allowed: boolean
    kinds?: SlotKind[]
    maxDepth?: number
  }
  validators?: ValidatorReference[]
  crossFieldRules?: CrossFieldRule[]
  metadata?: Record<string, JsonValue>
}
```

Counts/depth are nonnegative integers. Minima do not exceed maxima. Duplicate
entries in lists are harmless except duplicate cross-field rule IDs, which are
configuration errors. `allowedMarks` uses the same type/attribute matching as
Nodes. A named attribute's value list cannot be empty. Params default to `null`.
All configuration data must be finite JSON; `undefined` is omitted, and NaN,
Infinity, class instances and functions are rejected by configuration parsers.

## Read types

`JSONContent`, `Editor`, `Schema`, and ProseMirror `Node` in these signatures are
the types exported by `@tiptap/core` and `@tiptap/pm/model`. `Transaction` is from
`@tiptap/pm/state`. Snapshots and returned collections are deeply read-only to
callers; implementations do not expose live mutable storage.

```ts
interface SlotEntry {
  id: string | null
  kind: SlotKind
  path: number[] // child indexes from the Document root
  parentId: string | null // nearest containing Slot
  depth: number // top-level Slot = 0
  pos: number
  contentFrom: number
  contentTo: number
  config: SlotConfig | null // null when raw configuration cannot be parsed
  rawConfig: JsonValue
  content: JSONContent[]
  text: string
  empty: boolean
}

interface SlotSnapshot {
  id: string // opaque token, unique for this snapshot
  document: JSONContent
  slots: SlotEntry[]
  documentRevision: number | null
  contextRevision: number | null
}

interface SlotIssue {
  code: string
  severity: 'error' | 'warning'
  category: 'content' | 'configuration' | 'identity' | 'unavailable'
  slotId: string | null
  path: number[] | null
  message: string
  source: 'builtin' | 'validator' | 'crossField'
  validator?: string
  ownerId?: string
  ruleId?: string
  ruleIndex?: number
  details?: Record<string, JsonValue>
}

interface SlotValidationEntry {
  slotId: string | null
  path: number[]
  empty: boolean
  status: 'valid' | 'invalid' | 'unavailable'
  issues: SlotIssue[]
}

interface SlotValidationResult {
  snapshotId: string
  documentRevision: number | null
  contextRevision: number | null
  valid: boolean
  status: 'valid' | 'invalid' | 'unavailable'
  scope: 'document' | 'slot'
  entries: SlotValidationEntry[]
  issues: SlotIssue[] // includes expected fields absent from the Document
}
```

Positions follow ProseMirror positions and are valid only for that snapshot.
Paths distinguish malformed duplicate-ID entries. A document's empty Slot list
validates successfully unless `expectedIds` requires fields that are absent.
`rawConfig` preserves malformed JSON values; imported non-JSON data is rejected
as invalid input rather than coerced.

### Diagnostic codes

Built-in stable codes are `required`, `disallowedBlock`, `disallowedInline`,
`disallowedText`, `disallowedMark`, `disallowedAttributes`, `minLength`,
`maxLength`, `minChildren`, `maxChildren`, `pattern`, `value`, `nestedSlot`,
`nestedKind`, `maxDepth`, `missingId`, `duplicateId`, `missingSlot`,
`invalidConfiguration`, `unsupportedConfigVersion`, `unknownNodeType`,
`unknownMarkType`, `missingValidator`, `validatorFailed`, and
`invalidValidatorResult`. Custom codes must start with `custom.`.

Messages are fallback display text. Hosts can localize using code/details.
Built-in details contain counts, type/attribute names and paths, never whole
content values. Custom validators control their own messages and must avoid
leaking content into UI that a policy hides.

## Validator types

```ts
interface ValidationFinding {
  code: string // custom.*
  message: string
  severity?: 'error' | 'warning' // default error
  details?: Record<string, JsonValue>
}

interface SlotValidatorInput {
  slot: SlotEntry
  params: JsonValue
  context: unknown
  signal: AbortSignal
}

type SlotValidator = (
  input: SlotValidatorInput,
) => ValidationFinding[] | Promise<ValidationFinding[]>

interface CrossFieldFinding extends ValidationFinding {
  slotId: string
}

interface CrossFieldValidatorInput {
  owner: SlotEntry
  fields: ReadonlyMap<string, SlotEntry>
  params: JsonValue
  context: unknown
  signal: AbortSignal
}

type CrossFieldValidator = (
  input: CrossFieldValidatorInput,
) => CrossFieldFinding[] | Promise<CrossFieldFinding[]>
```

No findings means the check passes. Single-field validators only see their Slot;
cross-field validators see the declared fields. Neither receives a mutable
Editor. `context` is captured once per request, defaults to `undefined`, and is
host-owned; the host must provide a stable snapshot of external data or
invalidate validation when it changes. The package does not fetch records or
retry failed validators.

## Extension options

| Option                 | Type                                         | Default and consequence                                                                                   |
| ---------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `blockSlot`            | Tiptap `Node` extension instance             | `BlockSlot`; installs the default block rendering. Accepts a configured/extended `BlockSlot` instance.    |
| `inlineSlot`           | Tiptap `Node` extension instance             | `InlineSlot`; installs the default inline rendering. Accepts a configured/extended `InlineSlot` instance. |
| `generateId`           | `() => string`                               | UUID generator; new Slots get document-unique opaque IDs                                                  |
| `validators`           | `Record<string, SlotValidator>`              | `{}`; named custom rules are unavailable until provided                                                   |
| `crossFieldValidators` | `Record<string, CrossFieldValidator>`        | `{}`; named cross-field rules are unavailable until provided                                              |
| `getValidationContext` | `() => unknown`                              | Returns `undefined`; no external data                                                                     |
| `shortcuts`            | `false \| SlotShortcuts`                     | `false`; no typed notation is intercepted                                                                 |
| `onSlotsUpdate`        | `(event: SlotsUpdateEvent) => void`          | No-op; convenience listener for `slotsUpdate`                                                             |
| `onActiveSlotChange`   | `(event: ActiveSlotChangeEvent) => void`     | No-op; convenience listener for `activeSlotChange`                                                        |
| `onValidationUpdate`   | `(event: SlotValidationUpdateEvent) => void` | No-op; convenience listener for `slotValidationUpdate`                                                    |
| `onValidationError`    | `(event: SlotValidationErrorEvent) => void`  | No-op; convenience listener for `slotValidationError`                                                     |
| `onCommandRejected`    | `(event: SlotCommandRejectedEvent) => void`  | No-op; convenience listener for `slotCommandRejected`                                                     |

Notification callbacks run after the associated state update and do not mutate returned
objects. Reentrant writes are host-scheduled, not performed inside a guard.
All notification options also emit typed Tiptap Editor events, with the same
payloads. See [Editor events](/compose/slots/events) for exported payload types, `.on()`/
`.off()` usage, initialization and refusal timing, and cleanup. Behavior providers
such as validators and the ID generator are not events.
Generator errors/empty IDs/collisions refuse the operation; generation retries
at most five times for collisions, then reports `idGenerationFailed`.

The Node-instance options are resolved at Editor construction, not replaced at
runtime. Both are required; `false` is not supported. Custom instances must
preserve the canonical Node names and Slot Schema contract. Invalid instances
or duplicate registrations fail initialization with a descriptive error.
Rendering customization does not replace Commands, validation or indexing.

### Node options

`BlockSlot.configure()` and `InlineSlot.configure()` each accept
`HTMLAttributes: Record<string, string>`, default `{}`. These attributes customize
the default outer element independently for each kind. Required `data-slot-*`
attributes win conflicts. `HTMLAttributes` is a Node option, not a `Slot` option.
Developers may override `renderHTML`, `parseHTML`, or `addNodeView` through
Tiptap's `.extend()`; the requirements are defined in the rendering contract.

```ts
interface SlotShortcuts {
  inline?: { open: string; close: string; config?: SlotConfig }
  block?: { open: string; close: string; config?: SlotConfig }
}
interface SlotValidationError {
  snapshotId: string
  validator: string
  ownerId: string | null
  error: unknown
}
interface SlotCommandRejection {
  command: string
  code:
    | 'missingSlot'
    | 'ambiguousSlot'
    | 'invalidInput'
    | 'schemaMismatch'
    | 'idGenerationFailed'
    | 'protected'
    | 'overlappingTargets'
    | 'invalidSelection'
    | 'unsupportedContext'
  slotIds: string[]
}
```

A delimiter pair wraps the text between it into a newly identified Slot using
the configured template. The text remains content; it is not interpreted as a
configuration ID or a name. Omitted template is `{ version: 1 }`. A block pair
must occupy the entire textblock; inline pairs may occur within a line. Open
and close strings are nonempty, distinct, and do not overlap another opening
by prefix. Invalid shortcut configuration throws on initialization. There is
no bare-opening naming workflow in this release; the demo can offer a control
to name a new field through `updateSlotConfig`.

## Commands

All Commands are available through `editor.commands`, chains and `editor.can()`.
They return boolean, write at most one Transaction per call, and create no undo
entry when they change nothing. `can()` must produce no callbacks, validation
requests, ID generation or side effects. Dispatch repeats collision checks.

For operations that will generate IDs, a dry run uses temporary unique IDs and
is advisory: the actual generated IDs may match different protection selectors.
Dispatch rechecks the complete proposal using its real IDs. Supplying IDs makes
ID-dependent preflight deterministic. A refusal by a Slot Command inside a chain
must cancel all writes assembled in that chain, even without ContentProtection
installed; returning false after leaving earlier Steps dispatchable is not
sufficient to satisfy this contract.

Targets are IDs unless stated otherwise. Missing or duplicate targets return
false and report a structured rejection. Well-formed but invalid Slot values
are accepted. Malformed API arguments are refused. JSON content arguments must
fit the Schema exactly: no HTML parsing or lossy schema coercion is implicit.

| Command                               | Arguments                                      | Behavior                                                                                                                                                                                             |
| ------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `insertSlot`                          | `{ kind, id?, config?, content?, at? }`        | Insert at a numeric document position, or replace current selection when `at` is omitted. Defaults to empty config; omitted content uses configured default content or kind's empty content.         |
| `wrapInSlot`                          | `{ kind, id?, config?, range? }`               | Wrap the nonempty current selection or `{ from, to }`. Inline wrapping requires one inline parent; block wrapping requires complete sibling blocks. No automatic expansion or splitting.             |
| `fillSlot`                            | `{ id, content: JSONContent[] }`               | Replace contents; preserve owner ID and config. Empty array becomes an empty paragraph for a block Slot.                                                                                             |
| `fillSlots`                           | `{ values: { id, content: JSONContent[] }[] }` | Atomic batch; duplicate IDs or ancestor/descendant targets refuse. An empty batch succeeds without writing.                                                                                          |
| `clearSlot`                           | `{ id }`                                       | Replace contents with kind's empty content; nested fields are removed.                                                                                                                               |
| `dissolveSlot`                        | `{ id }`                                       | Remove wrapper, preserve contents.                                                                                                                                                                   |
| `removeSlot`                          | `{ id }`                                       | Remove wrapper and contents; refuse if the parent cannot remain Schema-valid, rather than adding arbitrary filler.                                                                                   |
| `moveSlot`                            | `{ id, to: number }`                           | Move the complete Node; `to` uses pre-Transaction coordinates. Reject a destination within the Node or an invalid parent.                                                                            |
| `updateSlotConfig`                    | `{ id, config: SlotConfig }`                   | Replace complete configuration, not a shallow/deep patch.                                                                                                                                            |
| `repairSlotIds`                       | none                                           | Keep first occurrence of each valid ID; assign new IDs to missing/later duplicates. Keep ambiguous cross-field references unchanged and report them in validation. Atomic and subject to protection. |
| `focusSlot`                           | `{ id, edge?: 'start' \| 'end' }`              | Default start; find a text or Node selection inside and scroll into view. False if concealed or no reachable content position.                                                                       |
| `focusNextSlot` / `focusPreviousSlot` | `{ fromId?, wrap?: boolean }`                  | Document-order traversal including nested Slots; from current innermost Slot if omitted. Skip concealed Slots. Default no wrap; from no active Slot use first/last.                                  |
| `selectSlotContent`                   | `{ id }`                                       | Select contents without wrapper; refuse if content is concealed.                                                                                                                                     |
| `invalidateSlotValidation`            | none                                           | Increment context revision, abort pending validation, clear current result; no document/history change.                                                                                              |

`insertSlot`, `wrapInSlot`, and `moveSlot` do not implicitly wrap/lift unrelated
content to find a valid placement. Schema failures are explicit. Slots supplied
inside Command content must already have valid unique IDs, or omit IDs to have
them minted; references to omitted IDs cannot be inferred. Clipboard cloning is
the separate identity path described in the Slot contract.

If Content Protection is installed, Slot Commands preflight the assembled
Transaction using `editor.storage.contentProtection.checkTransaction`. This is
the documented optional runtime composition contract: Slots structurally use
only its `{ allowed: boolean }` answer and do not import the other package.
The protection filter remains authoritative at dispatch. Chains are checked
against their complete proposed Transaction, not against the original document
once per isolated command. Other third-party filters may still refuse writes;
there is no general promise about their boolean Command results.

## Storage

`editor.storage.slot` exposes read-only getters:

```ts
interface SlotValidationState {
  status: 'unvalidated' | 'pending' | 'current'
  snapshotId: string | null
  result: SlotValidationResult | null
}

interface SlotStorage {
  snapshot: SlotSnapshot
  activeSlot: SlotEntry | null
  validation: SlotValidationState
}
```

The initial validation state is `unvalidated`; no custom validator runs during
editor creation or typing. Editing clears any cached result. Hosts may retain
old results themselves, but must label them as stale. Active Slot uses the
selection head for text selections; a selected Slot Node is itself active.

## Utilities

All listed functions are named exports. Functions accepting JSON validate its
structural shape and throw `SlotInputError` with `issues: InputIssue[]` for
malformed input; they do not silently parse invalid Nodes as paragraphs.

```ts
interface InputIssue {
  path: string
  code: string
  message: string
}
interface SlotInputError extends Error {
  issues: InputIssue[]
}

type SlotDocument = JSONContent | Node

interface ValidationOptions {
  snapshot: SlotSnapshot
  validators?: Record<string, SlotValidator>
  crossFieldValidators?: Record<string, CrossFieldValidator>
  context?: unknown
  expectedIds?: string[]
  signal?: AbortSignal
  onValidationError?: (event: SlotValidationError) => void
}

function createSlotSnapshot(options: { document: SlotDocument; schema?: Schema }): SlotSnapshot
function getSlots(options: { document: SlotDocument; schema?: Schema }): SlotEntry[]
function getSlot(options: { document: SlotDocument; id: string; schema?: Schema }): SlotEntry | null
function validateSlotConfig(options: { config: unknown; kind: SlotKind; schema?: Schema }): {
  valid: boolean
  issues: InputIssue[]
}
function validateSlots(options: ValidationOptions): Promise<SlotValidationResult>
function validateSlot(
  options: ValidationOptions & {
    id: string
  },
): Promise<SlotValidationResult>
function validateEditorSlots(options: {
  editor: Editor
  expectedIds?: string[]
  signal?: AbortSignal
}): Promise<SlotValidationResult>
function isSlotValidationCurrent(options: { editor: Editor; result: SlotValidationResult }): boolean
function subscribeSlotViewUpdates(options: { editor: Editor; onUpdate: () => void }): () => void
```

`getSlot` returns null for absent IDs, throws `SlotInputError` for duplicate
matches. `validateSlot` returns unavailable issues for missing/ambiguous IDs
instead of throwing. Configuration-validation errors in the persisted Document
are returned as issues, not thrown. A supplied Schema checks installed types
and structural validity. For a ProseMirror Node its Schema is implicit; for JSON
without a Schema, structural validation covers the standard JSON shape and Slot
format, and unknown-type checks are explicitly omitted. Such a result is not
certification that an arbitrary editor Schema will accept the JSON.

`validateEditorSlots` requires Slot to be installed. It captures the current
snapshot and context once, uses configured validators, updates validation
storage through pending/current states and returns the result. Pure validation
utilities never touch an Editor or emit extension callbacks. Neither path
submits, saves, repairs or edits content. Aborting rejects with `AbortError`;
other validator failures are represented in a resolved unavailable result.

Snapshot creation from JSON assigns null editor revisions; results from it
cannot be current for an Editor. A snapshot is immutable and captures all
configuration, contents and Schema information required for its validation.
Validation result bodies and currentness tokens are not intended for persistence.

`subscribeSlotViewUpdates` is editor-bound and requires Slot to be installed.
Unlike the pure readers, it registers a listener and returns its teardown.
Its initial notification, update triggers and lifecycle are specified in
[Rendering and customization](/compose/slots/rendering#validation-and-permission-updates).

## createSlotFillingPolicy

A named, pure export for the common case of filling existing fields without
changing their definitions or surrounding document. The helper returns ordinary
CPP JSON; it does not install a guard or change the Editor. ContentProtection
must be installed to enforce the returned policy.

```ts
interface SlotFillingPolicyOptions {
  editableSlotIds?: string[]
  documentType?: string
  ruleIdPrefix?: string
}

interface SlotFillingNodeMatch {
  types: string[]
  attributes?: { name: 'id'; operator: 'in'; values: string[] }[]
}

interface SlotFillingRule {
  id: string
  priority: number
  selector:
    | { target: 'node'; node: SlotFillingNodeMatch }
    | { target: 'content'; node: SlotFillingNodeMatch; stopAt?: SlotFillingNodeMatch }
    | { target: 'attribute'; node: SlotFillingNodeMatch; names?: string[] }
  permissions: { edit: boolean }
  reason?: string
}

interface SlotFillingPolicy {
  version: 1
  rules: SlotFillingRule[]
}

function createSlotFillingPolicy(options?: SlotFillingPolicyOptions): SlotFillingPolicy
```

`SlotFillingPolicy` is structurally assignable to `ContentProtectionPolicy`.
The helper and its types are defined in the Slot package without a runtime or
peer dependency on ContentProtection. A cross-package type/contract test must
verify assignability and that generated JSON compiles under the CPP contract.
This does not add another policy evaluator or a third package.

| Option            | Default and consequence                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `editableSlotIds` | Omitted: every existing block and inline Slot is fillable. A supplied list allows exactly those IDs; `[]` allows no content edits. |
| `documentType`    | `"doc"`; selects the root Document for the baseline deny. Supply the root type's actual name for a custom Document extension.      |
| `ruleIdPrefix`    | `"slotFilling"`; namespaces generated rule IDs for composition with application rules.                                             |

Arguments are copied, never retained by reference. Duplicate IDs are deduplicated
and sorted for deterministic JSON; IDs remain exact and case-sensitive. Empty
IDs/type names/prefixes or malformed arguments throw `SlotInputError`. The helper
does not inspect a Document or Schema, generate Slot IDs, emit events or use a
DOM. Unknown IDs simply match no Slot. Policy compilation validates that the
named root type and both Slot Node types exist in the host Schema.

The helper generates these five rules, in this stable order. Rule IDs are
`<ruleIdPrefix>.<suffix>`. Priority and behavior do not depend on list order.

| Suffix               | Priority | Selector and permission                                                                                                             |
| -------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `documentContent`    | 0        | Deny edits to root Document `content`.                                                                                              |
| `documentAttributes` | 0        | Deny edits to root Document `attribute`, omitting `names` to protect all root attributes.                                           |
| `fillableContent`    | 10       | Allow `content` of `blockSlot`/`inlineSlot`, filtered by ID when provided; always `stopAt` any descendant `blockSlot`/`inlineSlot`. |
| `slotStructure`      | 20       | Deny `node` edits to every `blockSlot`/`inlineSlot`, including new insertions.                                                      |
| `slotAttributes`     | 20       | Deny every Slot `attribute`, omitting `names` to protect `id`, `config` and any host-added attributes.                              |

No rule states `read`, so the generated policy leaves everything readable. It
does not override read restrictions from other composed rules. It contains
only generic CPP selectors: ContentProtection does not learn Slot-specific
syntax or import the Slot package. `stopAt` is defined in the
[policy contract](/content-protection/api-reference/policy#boundaries-within-a-content-selector).

### Resulting behavior

- Existing Slots can be filled, cleared, formatted and edited, subject to the
  ID list and any additional policy. Slot validation remains non-blocking.
- Surrounding content, root attributes, Slot identities and configurations stay
  fixed. Inserting, moving, dissolving, removing or copying/pasting new Slots is
  refused. Pasting ordinary content into an editable Slot remains possible.
- A listed parent allows its own content but not unlisted descendants. A listed
  child can be filled even if its parent is unlisted. Omitting the list gives
  each Slot its own allow, including nested Slots.
- Replacing or clearing a parent do not remove nested Slot Nodes. The whole
  write is refused if it would; the helper does not turn replacement into a
  partial fill. Fill nested fields individually or use a non-overlapping batch.
- Selection and copying remain available for readable content. A document with
  no Slots has no editable content under this policy.
- IDs are selectors, not proof of uniqueness. Validate imported identity issues
  before enabling an assigned-field workflow: duplicate IDs match every
  occurrence, while ID-targeted Slot Commands continue to refuse ambiguity.

### Composition and runtime changes

To change assignments, generate a new policy and pass it to
`setContentProtectionPolicy`; do not mutate an installed policy object. Omitted
IDs select all Slots dynamically; there is no captured list of current fields.
The helper cannot add or remove Slots through the generated policy itself.

Developers may append ordinary rules or transform the returned JSON. Rules at
priority 10 that deny an assigned field win ties with its content allow. Higher
priority allows can intentionally override the helper's restrictions, including
the structure/attribute restrictions at 20; this is explicit composition, not an
immutable permission ceiling. Duplicate rule IDs remain invalid. Use a different
prefix when combining generated rules, and avoid combining conflicting filling
presets when a single merged assignment list expresses the intended access.

Returning to authoring is a host policy replacement, normally an empty policy
or the host's authoring policy. No persisted mode flag or independent Slot
permission system is introduced.
