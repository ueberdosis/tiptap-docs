Slots can include rules to describe what content is valid. After the user fills the slots, call `validateEditorSlots` to validate the content.

Define requiredness, length, content types and patterns in `attrs.config`:

```ts
const config = {
  version: 1,
  required: true,
  constraints: {
    pattern: { source: '^ORD-\\d{4}$', message: 'Use ORD-0000' },
  },
}
```

For application-specific checks, persist a validator name and register its implementation:

```ts
Slot.configure({
  validators: {
    registeredPerson: async ({ slot, signal }) => {
      const found = await directory.find(slot.text, { signal })
      return found
        ? []
        : [
            {
              code: 'custom.person',
              message: 'Choose a registered person.',
            },
          ]
    },
  },
})

// In the field's configuration:
// validators: [{ name: 'registeredPerson' }]
```

For checks between fields, add a `crossFieldRules` entry to an owning Slot and register a `crossFieldValidators` function. It receives only the declared field IDs and returns findings with a `slotId`.

Missing or failed validators produce `status: 'unavailable'`. Do not treat that as valid. Edits invalidate cached results; call `invalidateSlotValidation()` when external records change. See [validator types and lifecycle](/compose/slots/api-reference/validation#slotvalidator).
