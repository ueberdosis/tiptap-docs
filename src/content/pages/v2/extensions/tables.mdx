A table that is longer than the space left on a page breaks between its rows and continues on the next page. A single row taller than that space is cut through at one height in all of its cells, so the columns stay lined up. That is what a word processor does, and it keeps a table of paragraph-length cells readable across a boundary.

The document stores none of this. It holds the table and two settings an author can make. Page Layout works out where the table breaks from the paper each time.

## Set it up

Tables come from `@tiptap/extension-table`. Add it as you would in any Tiptap editor:

```js
import StarterKit from '@tiptap/starter-kit'
import { TableKit } from '@tiptap/extension-table'
import { createPageLayoutEditor, PageLayout, pageSetup } from '@tiptap-pro/extension-page-layout'

createPageLayoutEditor({
  element,
  content,
  extensions: [
    StarterKit,
    TableKit.configure({ table: { resizable: true } }),
    PageLayout.configure({ setup: pageSetup('A4') }),
  ],
})
```

That is all. There is no package to install besides Page Layout. The engine recognizes the table by its type name and adds the two attributes below to it, and your own configuration of the table extension stays as it is.

The commands of the table extension work unchanged, including while a row is cut across a boundary. That covers `addColumnAfter`, `deleteRow`, `mergeCells`, `toggleHeaderRow` and the rest.

`PageLayout.configure({ tablePagination: false })` takes both settings below away.

## Let a row break, or not

A row can be cut by default. An author can forbid it per row:

```js
editor.commands.setRowBreakAcrossPages(false)
```

This is Word's Allow row to break across pages, and it applies to the row the cursor is in. The row stores it as the `breakAcrossPages` attribute on `tableRow`. The command returns `false` when the cursor is not in a table. See [commands](/pages/v2/api/commands#tables-columns-and-lists).

It is a preference and not a prohibition. A row that fits on no page is cut anyway, because the alternative is a row hanging off the bottom of a sheet. With the setting off, the engine first moves the row to the next page whole, and cuts it only if that doesn't help.

A toolbar that offers the switch should be ready to say it couldn't be honored:

```js
const engine = editor.storage.pageLayout.engine
const context = engine.getTableContext()

if (context && !context.breakAcrossPages) {
  const cut = engine.isDividedInView(
    context.rowPosition,
    context.rowPosition + context.row.nodeSize,
  )

  if (cut) {
    // The row is taller than a page. Tell the author instead of leaving the switch looking broken.
  }
}
```

## Repeat the header row

```js
editor.commands.setRepeatHeaderRow(true)
```

The leading header rows of the table are then drawn at the top of every page the table continues onto. The table stores the setting as `repeatHeaderRow`. The command returns `false` outside a table.

Which rows count as the header isn't a separate setting. It is every leading row whose cells are all header cells. So `toggleHeaderRow` from the table extension makes a row eligible, and two header rows at the top of a table both repeat.

The repeated rows are drawn, not inserted. The document keeps one header row however many pages the table covers. The page a continuation lands on pays for their height, so a table with a tall header fits fewer rows per page.

## What the cursor is in

```js
const context = editor.storage.pageLayout.engine.getTableContext()
```

`getTableContext()` returns `null` when the cursor is not in a table. Otherwise it returns:

| Field                    | What it holds                                  |
| ------------------------ | ---------------------------------------------- |
| `table`, `tablePosition` | The table node and where it starts.            |
| `row`, `rowPosition`     | The row the cursor is in, and where it starts. |
| `breakAcrossPages`       | Whether this row may be cut.                   |
| `repeatHeaderRow`        | Whether this table repeats its header.         |

A toolbar reads this to show the two switches in the right state. The value is up to date after every change.

A table menu of your own reads the table from the document and runs the functions of the table extension there, since `editor.state` holds only the rows of one page. See [components that change the document](/pages/v2/getting-started/components#example-a-table-menu).

## What a cut row looks like

Both halves of a cut row keep every cell, so the columns line up. A cell whose content ends above the cut has nothing in its lower half. A cell whose content begins below the cut has nothing in its upper half. One of the two pages shows an empty cell, as Word does.

Working across the cut behaves as if the row were whole:

- Selecting across the boundary selects the text between the two points, drawn on both pages.
- A cell selection works from either half. A selection that starts in the top half and ends in the bottom half is one selection of those cells.
- Copying gives you the cells as a table, so you can paste it into another table or another document.
- Typing, deleting and pasting apply to the document and not to the fragment, so an edit made in the lower half is an edit to that row.

## Drag a column width

With `resizable: true`, the drag handles of the table extension work, and the width lands on the cells of the document. A drag on a table that is cut across pages changes the column of the whole table, not only the fragment under the pointer.

## Limitations

A table inside a table cell isn't supported at a page boundary.
