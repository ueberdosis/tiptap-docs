A table that is longer than the space left on a page breaks between its rows and continues on the next page. Page Layout splits a single row taller than that space at one height in all of its cells, so the columns stay lined up. Word does the same, and it keeps a table of paragraph-length cells readable across a boundary.

The source document stores none of this. It holds the table and two settings a user can make. Page Layout works out where the table breaks from the paper each time.

## Set it up

Tables come from `@tiptap/extension-table`. Add it as you would in any Tiptap editor:

```js
import StarterKit from '@tiptap/starter-kit'
import { TableKit } from '@tiptap/extension-table'
import { createPageLayoutEditor, PageLayout, pageSetup } from '@tiptap-pro/extension-page-layout'

createPageLayoutEditor({
  element,
  content,
  extensions: [
    StarterKit,
    TableKit.configure({ table: { resizable: true } }),
    PageLayout.configure({ setup: pageSetup('A4') }),
  ],
})
```

You don't need another package. Page Layout recognizes the table by its type name and adds the two attributes below to it. Your own table extension configuration stays as it is.

The table extension's commands work unchanged, including while a row is split across a boundary. That covers `addColumnAfter`, `deleteRow`, `mergeCells`, `toggleHeaderRow` and the rest.

`PageLayout.configure({ tablePagination: false })` takes both settings below away.

## Let a row break, or not

A row can split by default. A user can forbid it per row:

```js
editor.commands.setRowBreakAcrossPages(false)
```

This is Word's "Allow row to break across pages". It applies to the row the cursor is in. The row stores it as the `breakAcrossPages` attribute on `tableRow`. The command returns `false` when the cursor is not in a table. See [commands](/pages/v2/api/commands#tables-columns-and-lists).

Like every keep-together setting, it is a [preference](/pages/v2/extensions/overview#keep-together-is-a-preference). Page Layout splits a row that fits on no page anyway. With the setting off, it first moves the row to the next page whole, and splits it only if that doesn't help.

A toolbar that offers the switch should tell the user when Page Layout split the row anyway:

```js
const engine = editor.storage.pageLayout.engine
const context = engine.getTableContext()

if (context && !context.breakAcrossPages) {
  const split = engine.isDividedInView(
    context.rowPosition,
    context.rowPosition + context.row.nodeSize,
  )

  if (split) {
    // The row is taller than a page. Tell the user instead of leaving the switch looking broken.
  }
}
```

## Repeat the header row

```js
editor.commands.setRepeatHeaderRow(true)
```

Page Layout then draws the table's leading header rows at the top of every page the table continues onto. The table stores the setting as `repeatHeaderRow`. The command returns `false` outside a table.

Which rows count as the header isn't a separate setting. It is every leading row whose cells are all header cells. So `toggleHeaderRow` from the table extension makes a row eligible, and two header rows at the top of a table both repeat.

Page Layout draws the repeated rows without inserting them. The source document keeps one header row however many pages the table covers. The repeated rows take space on each page, so a table with a tall header fits fewer rows per page.

## What the cursor is in

```js
const context = editor.storage.pageLayout.engine.getTableContext()
```

`getTableContext()` returns `null` when the cursor is not in a table. Otherwise it returns:

| Field                    | What it holds                                  |
| ------------------------ | ---------------------------------------------- |
| `table`, `tablePosition` | The table node and where it starts.            |
| `row`, `rowPosition`     | The row the cursor is in, and where it starts. |
| `breakAcrossPages`       | Whether this row may split.                    |
| `repeatHeaderRow`        | Whether this table repeats its header.         |

A toolbar reads this to show the two switches in the right state. The value is up to date after every change.

A table menu of your own reads the table from the source document and runs the table extension's functions there, since `editor.state` holds only the rows of one page. See [components that change the document](/pages/v2/getting-started/components#example-a-table-menu).

## What a split row looks like

Both pieces of a split row keep every cell, so the columns line up. A cell whose content ends above the split is empty in the lower piece. A cell whose content begins below the split is empty in the upper piece. One of the two pages shows an empty cell, as Word does.

Working across the split behaves as if the row were whole:

- Selecting across the boundary selects the text between the two points, drawn on both pages.
- A cell selection works from either piece. A selection that starts in the upper piece and ends in the lower piece is one selection of those cells.
- Copying gives you the cells as a table, so you can paste it into another table or another document.
- Typing, deleting and pasting apply to the source document, so an edit in the lower piece is an edit to that row.

## Drag a column width

With `resizable: true`, the table extension's drag handles work, and the width lands on the cells in the source document. A drag on a table split across pages changes the column in the whole table, including the pieces on other pages.

## Limitations

A table inside a table cell isn't supported at a page boundary.
