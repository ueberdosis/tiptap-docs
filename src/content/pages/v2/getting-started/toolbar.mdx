A toolbar works as it does in an editor without pages. A button runs a command, and its state comes from `editor.can()` and `editor.isActive()`. Page Layout adds a few commands of its own. It also adds readers for what only pages have. These tell you the page the cursor is on, its section, and whether a header or footer is being edited.

## Buttons

```js
button.addEventListener('click', () => editor.commands.insertPageBreak())

function render() {
  button.disabled = !editor.can().insertPageBreak()
  boldButton.classList.toggle('is-active', editor.isActive('bold'))
}

editor.on('transaction', render)
```

- A command acts on the whole node at the cursor, also where a page boundary runs through it. `addRowAfter` adds the row below the cursor's row to the table on every page it is drawn on.
- `editor.can()` asks the same document, so a button is disabled exactly where the command would do nothing.
- In React, `useEditorState` re-renders on the same event.
- Keep the focus in the editor when a button is pressed. Prevent the default of `mousedown` on the toolbar's buttons. The `click` still arrives. See [positions and events](/pages/v2/core-concepts/positions-and-events).

```js
toolbar.addEventListener('mousedown', (event) => {
  if (event.target.closest('button')) {
    event.preventDefault()
  }
})
```

If a button takes the focus, the browser restores the selection from before the command once the editor is focused again. The cursor the command placed is lost. After `insertPageBreak()`, it jumps from the new page back to the foot of the page above.

The page commands `insertPageBreak()`, `insertColumnBreak()`, `insertSectionBreak()`, `undo()` and `redo()` answer `editor.can()` the same way. See [breaks](/pages/v2/core-concepts/breaks) and [sections](/pages/v2/core-concepts/sections).

## Read where the cursor is

```js
const engine = editor.storage.pageLayout.engine

engine.getActivePageIndex() // the page the cursor is on, counting from 0
engine.getPageCount()
engine.getActiveSectionIndex() // its section, or the one whose header or footer is open
engine.getFurnitureTarget() // the header or footer being edited, or null
engine.getTableContext() // the table and row at the cursor, or null
```

The pages are laid out again after a change, so a page number read during the `transaction` event can still be the one before it. The `onChange` option of `createPageLayoutEditor` runs once the pages are drawn. Read the page count there for a status bar.

```js
const editor = createPageLayoutEditor({
  element,
  content,
  extensions: [StarterKit, PageLayout.configure({ setup: pageSetup('A4') })],
  onChange: (editor) => {
    const engine = editor.storage.pageLayout.engine
    status.textContent = `Page ${engine.getActivePageIndex() + 1} of ${engine.getPageCount()}`
  },
})
```

Every number these methods return is true of the layout it was read from. Read it again after a change instead of keeping it.

## In a header or footer

While a header or footer is being edited, the toolbar acts there. A table, a list, a mark or a footnote goes into the header, and `editor.can()` and `editor.isActive()` answer for the cursor in it. A button that only belongs in the body text can hide itself while `getFurnitureTarget()` is not `null`. A button that leaves the header runs `editor.commands.closeFurniture()`. See [headers and footers](/pages/v2/core-concepts/header-and-footer).

## When a command cannot be carried

A command that builds its change from what is drawn on one page, instead of from the document, can write something the editor cannot carry back. The `onCommandOnPages` option of `PageLayout` runs when that happens. It receives the command's name, which is how you find the command. See the [options](/pages/v2/api/options).
