A component written for an editor without pages usually reads `editor.state` and dispatches on `editor.view`. In a paginated editor, `editor.state` holds the pages. A table that runs over a page boundary is one table per page there. Each has only the rows of its page. A paragraph cut by the boundary is two paragraphs. Code that reads that state sees one page's rows, so it can edit the wrong table.

You have two ways to run such code on the document instead: a command, or a transaction of your own.

## Run a command on the document

Any command of the form `(state, dispatch) => boolean` runs on the document through `onSourceDocument`.

```js
import { addColumnAfter } from '@tiptap/pm/tables'

editor.commands.onSourceDocument(addColumnAfter)
```

- The command reads the document and its cursor, so a cell that spans rows over a page boundary is one cell, and a table has all its rows.
- It is the reader's own edit. You can undo it, the selection it sets is kept, and the page scrolls to where the transaction asks.
- The pages are drawn again before the call returns.
- `editor.can().onSourceDocument(command)` asks the document too, so a menu can disable an item with it.

## Dispatch a transaction of your own

Build the transaction on `engine.getSourceState()` and pass it to `dispatchSourceTransaction`.

```js
const engine = editor.storage.pageLayout.engine
const state = engine.getSourceState()

engine.dispatchSourceTransaction(state.tr.insertText('Note: ', state.selection.from))
```

It applies the way `onSourceDocument` applies a command. You can undo it, its selection is kept, and the pages are drawn again before it returns. It returns `false` when the editor has been destroyed.

`dispatchSourceTransaction` throws for a transaction built on any other state. A transaction built on `editor.state` holds positions in the pages. Those mean something else in the document. A transaction built on a state read before another change would apply its steps where the text has since moved. The error says which of the two it was.

```txt
[page-layout] dispatchSourceTransaction takes a Transaction built on engine.getSourceState(),
and this one was built on editor.state, which holds the pages rather than the document. Build it
again from engine.getSourceState().tr.
```

Read the state, build the transaction and dispatch it in one go. A state kept across an `await` is out of date by the time you use it.

`applySourceTransaction` also takes a transaction. It is meant for changes that are not the reader's. It leaves the undo history alone unless you pass `addToHistory: true`, and it keeps the reader's selection where it was. It throws for a transaction built on another state as well.

## Combine commands in a chain

The commands an extension brings run on the document. Tiptap's core commands, such as `insertContent`, run on the pages. A chain can mix the two.

```js
editor.chain().goToNextCell().insertContent('X').run()
```

The editor writes `X` into the next cell. A core command in the chain still reads an explicit position as a position in the pages. The chain commits each run of document commands and each run of core commands on its own, so undoing the chain can take more than one step.

During IME composition, a chain that goes from a document command to a core command returns `false` before the core command writes. The document command is already committed. Run the core command after composition ends.

In a custom callback, finish writing to a captured `tr` before you call a command of the other kind. Changing content, the selection or stored marks through that `tr` afterwards makes `run()` return `false`. What the chain committed before stays in the document.

Only `editor.chain()`, and the same chain under `can()`, work this way. Inside `editor.commands.command(...)` or `editor.commands.first(...)`, a core command that follows a document command writes nothing, although the call returns `true`. Use a chain for that sequence.

```js
editor.chain().goToNextCell().insertContent('X').run() // writes X
editor.commands.command(({ commands }) => commands.goToNextCell() && commands.insertContent('X')) // does not
```

## Example: a table menu

This example reads the table at the cursor and runs actions on it.

```js
import { addColumnAfter, deleteRow, findTable, TableMap } from '@tiptap/pm/tables'

const engine = editor.storage.pageLayout.engine

function tableAtCursor() {
  const state = engine.getSourceState()
  const table = findTable(state.selection.$from)

  return table && { ...table, map: TableMap.get(table.node) }
}

// Columns and rows of the whole table, not of the part on this page
const table = tableAtCursor()
const columns = table?.map.width
const rows = table?.map.height

// Menu items
const canDeleteRow = editor.can().onSourceDocument(deleteRow)
editor.commands.onSourceDocument(addColumnAfter)

// Write into the first cell, inside its first paragraph
const state = engine.getSourceState()
const { start, map } = tableAtCursor()
engine.dispatchSourceTransaction(state.tr.insertText('Total', start + map.map[0] + 2))
```

`tableAtCursor()` is read again before the transaction, because the command before it changed the document. `map.map` holds positions, and they are valid only for the document they were read from.

## What happens to an edit made on the pages

An edit dispatched on `editor.view` still reaches the document where it can be applied there. This covers typing, deleting, pasting, a mark and an attribute on one node. Two kinds of edit are refused and change nothing:

- An edit that would leave a table inconsistent, such as a column added to the rows of one page only. You can set the same rule for your own nodes with [`defineNodeLayout`](/pages/v2/guides/custom-nodes#nodes-that-must-stay-consistent).
- An edit that would put a page into the document.

The console says so once per kind, and names `getSourceState()` and `dispatchSourceTransaction`. The commands that Page Layout and the table extension put on `editor.commands` already run on the document, so they are not affected.

## editor.state as the document

This option is experimental and off by default.

```js
PageLayout.configure({ setup: pageSetup('A4'), experimentalSourceState: true })
```

`editor.state` then holds the document, so code written for an editor without pages works on it unchanged.

- Tiptap's own commands run on the document. A position you pass to `setTextSelection`, `insertContentAt` or `deleteRange` is a position in the document.
- `editor.view.dispatch(editor.state.tr.insertText('Note: '))` changes the document, as the reader's own edit.
- `isActive()` and `getAttributes()` answer for the document, so a paragraph cut by a page boundary is one paragraph.

`editor.view.state` still holds the pages. A position read off `editor.state` and passed to the editor view is wrong there, because those methods take positions in the pages. This applies to `editor.view.coordsAtPos()`, `domAtPos()` and `nodeDOM()`, and to `editor.$pos()`. The engine's readers take positions in the document instead. See [positions and events](/pages/v2/core-concepts/positions-and-events).
