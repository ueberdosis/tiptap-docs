`POST /v3/convert/export/docx` turns a Tiptap document into a `.docx` file on the Conversion service. Call it from your backend when there is no editor, such as in a job that exports stored documents. The [Export DOCX](/conversion/v3/docx/export) extension calls the same endpoint from the editor.

The [REST API overview](/conversion/v3/rest-api/overview) explains the base URLs, the token and the errors every call shares.

## Send a document

The smallest request is a JSON body with the Tiptap document in `document`. [What Word elements become](/conversion/v3/docx/elements) lists the node types the service writes to Word.

This Node.js script exports a heading and a paragraph and saves the file. `CONVERSION_TOKEN` is an environment variable with a token that allows `Convert:Export:Docx`, as [Get a token](/conversion/v3/rest-api/overview#get-a-token) explains:

```js
import { writeFile } from 'node:fs/promises'

const response = await fetch('https://api.tiptap.dev/v3/convert/export/docx', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${process.env.CONVERSION_TOKEN}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    document: {
      type: 'doc',
      content: [
        { type: 'heading', attrs: { level: 1 }, content: [{ type: 'text', text: 'My report' }] },
        { type: 'paragraph', content: [{ type: 'text', text: 'Hello from Tiptap.' }] },
      ],
    },
  }),
})

if (!response.ok) throw new Error(`Export failed: ${response.status} ${await response.text()}`)
await writeFile('report.docx', new Uint8Array(await response.arrayBuffer()))
```

The file has an A4 page with Word's default margins. With `curl`, put the same JSON into a file, here `request.json`. `-D` saves the response headers, which hold the [warnings](#warnings):

```bash
curl -X POST https://api.tiptap.dev/v3/convert/export/docx \
  -H "Authorization: Bearer $CONVERSION_TOKEN" \
  -H 'Content-Type: application/json' \
  -d @request.json -o report.docx -D headers.txt
```

A document from an import may hold preserved content, which keeps what the importing editor had no extension for. The service doesn't know it, so turn it back first with `unpreservedContent(document)` from `@tiptap-pro/extension-preserved-content`. The Export DOCX extension does this on its own.

The request takes these headers:

| Header          | Value                                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `Authorization` | `Bearer <token>`.                                                                                                                           |
| `Content-Type`  | `application/json`, or `multipart/form-data` when you [upload fonts and images](#upload-fonts-and-images). Any other type fails with `400`. |
| `X-App-Id`      | Your app ID, only with a legacy token.                                                                                                      |

## Body fields

Every field is optional except `document`. A field the endpoint doesn't know fails the request with `400` and `INVALID_EXPORT_OPTIONS`, so a typo shows up instead of being ignored. These are the fields a backend sends:

| Field                                                                                                                   | Type                | Description                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `document`                                                                                                              | `object`            | Required. The Tiptap document as JSON, with `type: "doc"`.                                                                                                                                                                                                                                           |
| `pageSize`, `pageMargins`                                                                                               | `object`            | The page. See [Page size and margins](#page-size-and-margins).                                                                                                                                                                                                                                       |
| `pageColor`                                                                                                             | `string`            | The page background, as a CSS color. It wins over the page color of the first [`sectionBreak`](#headers-and-footers), the node that starts a section.                                                                                                                                                |
| `footnotes`, `endnotes`, `comments`                                                                                     | `object`            | See [Notes and comments](#notes-and-comments).                                                                                                                                                                                                                                                       |
| `styleOverrides`                                                                                                        | `object`            | Word styles, such as Normal or Heading 1, in the shape of the `IStylesOptions` type of `docx`, the npm library the service writes the file with. The service passes it on without checking it. See [Set Word styles](/conversion/v3/docx/export-styles#set-word-styles).                             |
| `cssStyles`                                                                                                             | `object`            | `{ styles?, baseFontSize? }`: CSS properties per element, such as `p` or `h1`. `styleOverrides` wins. See [Describe styles with CSS](/conversion/v3/docx/export-styles#describe-styles-with-css).                                                                                                    |
| `defaultTabStop`                                                                                                        | `number`            | The distance between default tab stops, in twips (1/1440 inch). Greater than 0.                                                                                                                                                                                                                      |
| `listLevels`                                                                                                            | `object`            | The indents of bullet, ordered and task lists. Not checked. See [Lists and task lists](/conversion/v3/docx/elements/lists).                                                                                                                                                                          |
| `paragraphOverrides`, `textRunOverrides`, `imageOverrides`, `tableOverrides`, `tableRowOverrides`, `tableCellOverrides` | `object`            | Applied to every paragraph, text run, image, table, table row or table cell. [Set default formatting](/conversion/v3/docx/export-styles#set-default-formatting) lists their fields.                                                                                                                  |
| `headerFooterOverrides`                                                                                                 | `object`            | Applied to the content of headers and footers. See [Header and footer formatting](/conversion/v3/docx/export-styles#header-and-footer-formatting).                                                                                                                                                   |
| `repeatTableHeaderRows`                                                                                                 | `boolean`           | `true` repeats a table's leading rows of `tableHeader` cells on every page. On your own server, it needs the Conversion service 2.50.0 or later. |
| `customNodeDsl`                                                                                                         | `object`            | Rules for node types of your own. See [Custom nodes in Word files](/conversion/v3/docx/custom-nodes).                                                                                                                                                                                                |
| `embedFonts`                                                                                                            | `boolean`           | Also embeds the fonts the document uses that you don't upload. Defaults to `false`. See [Upload fonts and images](#upload-fonts-and-images).                                                                                                                                                         |
| `onImageError`                                                                                                          | `"skip" \| "throw"` | `"skip"`, the default, leaves out an image the service can't use. `"throw"` fails the export.                                                                                                                                                                                                        |
| `assets`                                                                                                                | `object[]`          | One entry for each uploaded file. See [Upload fonts and images](#upload-fonts-and-images).                                                                                                                                                                                                           |

The editor extension sends a few more fields, which [Fields the editor extension sends](#fields-the-editor-extension-sends) lists.

### Page size and margins

`pageSize` and `pageMargins` set the page of a document without section breaks. These fields, next to `document`, give an A4 page with 2 cm margins on the sides:

```json
{
  "pageSize": { "width": "21cm", "height": "29.7cm" },
  "pageMargins": { "top": "2.5cm", "bottom": "2.5cm", "left": "2cm", "right": "2cm" }
}
```

Each value is a number in twips, or a string with `mm`, `cm`, `in`, `pt` or `pc`, such as `"2.5cm"`. A string of digits is twips too, and `px` is refused.

`pageSize` takes `width` and `height`. `pageMargins` takes `top`, `bottom`, `left` and `right`, and `header` and `footer`, the distances of the header and footer from the page edge. Every value is 0 or more, except `top` and `bottom`, which may be negative.

A value left out keeps the default: A4, with margins of 2.54 cm at the top and bottom and 3.17 cm left and right. `header` and `footer` have no default. The number `0` gives the default too, so write a margin of 0 as `"0cm"`.

The page of the first section comes from the first of these that the request has:

1. A [`sectionBreak`](#headers-and-footers) node at the start of `document`.
2. `pageSetup`, from the editor extension.
3. `pageSize` and `pageMargins`.
4. The A4 default.

Every later section takes its page from the attributes of its own `sectionBreak` node, which [Import sections](/conversion/v3/docx/page-layout#import-sections) lists.

### Headers and footers

Headers and footers come from `sectionBreak` nodes in `document`. A `sectionBreak` starts a section, a part of the document with its own page setup, as in Word. It holds the section's headers and footers as `pageFurniture` nodes, and the section's content follows it.

Content before the first `sectionBreak` has no headers or footers, so a document that needs them starts with one. This document has a header and a footer with the page number:

```json
{
  "type": "doc",
  "content": [
    {
      "type": "sectionBreak",
      "content": [
        {
          "type": "pageFurniture",
          "attrs": { "zone": "header", "slot": "default" },
          "content": [
            { "type": "paragraph", "content": [{ "type": "text", "text": "Quarterly report" }] }
          ]
        },
        {
          "type": "pageFurniture",
          "attrs": { "zone": "footer", "slot": "default" },
          "content": [
            {
              "type": "paragraph",
              "content": [
                { "type": "text", "text": "Page " },
                { "type": "pageNumber", "attrs": { "kind": "page" } }
              ]
            }
          ]
        }
      ]
    },
    { "type": "paragraph", "content": [{ "type": "text", "text": "Hello from Tiptap." }] }
  ]
}
```

[Page Layout](/features/page-layout/getting-started/overview), the extension that shows the editor as pages, stores headers and footers in these nodes. They are plain JSON, so a backend sends them without Page Layout.

[Headers and footers](/conversion/v3/docx/page-layout#headers-and-footers) lists the other `slot` values, `first` and `even`, and the `kind` values of `pageNumber`, such as `pages` for the number of pages.

### Notes and comments

`footnotes` and `endnotes` map a note ID to the note's content as Tiptap JSON. A `footnoteReference` or `endnoteReference` node with that ID in its `noteId` attribute places the note mark in `document`:

```json
{
  "document": {
    "type": "doc",
    "content": [
      {
        "type": "paragraph",
        "content": [
          { "type": "text", "text": "Sales grew." },
          { "type": "footnoteReference", "attrs": { "noteId": "1" } }
        ]
      }
    ]
  },
  "footnotes": {
    "1": {
      "type": "doc",
      "content": [
        { "type": "paragraph", "content": [{ "type": "text", "text": "Source: annual report." }] }
      ]
    }
  }
}
```

A note without a reference to it is left out of the file.

`comments` holds the comment threads. A thread attaches to the text in `document` that carries an `inlineThread` mark with the thread's `id` in its `data-thread-id` attribute:

```json
{
  "document": {
    "type": "doc",
    "content": [
      {
        "type": "paragraph",
        "content": [
          {
            "type": "text",
            "text": "Sales grew.",
            "marks": [{ "type": "inlineThread", "attrs": { "data-thread-id": "t1" } }]
          }
        ]
      }
    ]
  },
  "comments": {
    "threads": [
      {
        "id": "t1",
        "resolvedAt": null,
        "comments": [
          {
            "id": "c1",
            "content": "Which quarter?",
            "createdAt": "2026-03-02T09:30:00Z",
            "data": { "author": "Ada Lovelace", "initials": "AL" }
          }
        ]
      }
    ]
  }
}
```

A comment's `content` is a string or Tiptap JSON. Dates are ISO 8601 strings, and a thread with a `resolvedAt` date exports as resolved. [Tracked changes and comments](/conversion/v3/docx/tracked-changes-and-comments) describes what Word keeps.

### Removed fields

These fields belonged to the v2 REST API or the 0.x extension. Each one fails the request with `400` and `REMOVED_EXPORT_OPTION`, and `path` names the field:

| Field                 | Instead                                                                                                  |
| --------------------- | -------------------------------------------------------------------------------------------------------- |
| `headers`, `footers`  | `sectionBreak` and `pageFurniture` nodes in `document`. See [Headers and footers](#headers-and-footers). |
| `placeholders`        | `pageNumber` nodes in the headers and footers.                                                           |
| `exportType`          | None. The response is the file.                                                                          |
| `doc`                 | `document`.                                                                                              |
| `customNodes`         | `customNodeDsl`. The error also has a `docsUrl`.                                                         |
| `customNodeDslLimits` | None. The service applies its own limits.                                                                |

## Upload fonts and images

A multipart request uploads font and image files together with the document. Send it as `multipart/form-data` with these parts:

- One `options` part with the JSON you would send as the body, as text.
- One file part for each entry in `assets`, named after the entry's `part`.

In this Node.js script, `assets` lists an image and a font file. `JSON.stringify()` makes the `options` part a string, which `FormData` sends as text, and `fetch` sets the `Content-Type` header with its boundary:

```js
import { readFile } from 'node:fs/promises'

const options = {
  document: {
    type: 'doc',
    content: [{ type: 'image', attrs: { src: 'logo.png' } }],
  },
  assets: [
    { id: 'logo', kind: 'image', part: 'logo', src: 'logo.png' },
    { id: 'inter', kind: 'font', part: 'inter', name: 'Inter' },
  ],
}

const form = new FormData()
form.append('options', JSON.stringify(options))
form.append('logo', new Blob([await readFile('logo.png')]), 'logo.png')
form.append('inter', new Blob([await readFile('Inter-Regular.ttf')]), 'Inter-Regular.ttf')

const response = await fetch('https://api.tiptap.dev/v3/convert/export/docx', {
  method: 'POST',
  headers: { Authorization: `Bearer ${process.env.CONVERSION_TOKEN}` },
  body: form,
})
```

With `curl`, send the JSON from a file as `-F 'options=<options.json'`. The `<` sends the file's text, and `@` would send it as a file, which fails.

Each kind of entry has its own fields and accepted files. `id` is a name of your choice:

| Kind  | Entry                                             | Accepted files             |
| ----- | ------------------------------------------------- | -------------------------- |
| Font  | `{ id, kind: "font", part, name, characterSet? }` | TTF, OTF or WOFF2          |
| Image | `{ id, kind: "image", part, src }`                | PNG, JPEG, GIF, BMP or SVG |

The service checks the entries and files before it exports:

- `id` and `part` are unique across the entries. Every part has an entry, every entry has its file, and each part comes once.
- A font's `name` matches a font family the document uses, such as the `fontFamily` of a `textStyle` mark or a font in `styleOverrides`. The optional `characterSet` takes one of Word's character set values, such as `"00"` for ANSI, which [`DocxFontCharacterSet`](/conversion/v3/docx/export-options/types#docxfontcharacterset) lists. An unknown value fails the request with `400`.
- An image entry takes the place of the image whose `src` it names, so use the same `src` as the document. The service compares them as text, so an image with no URL can use any name, such as `logo.png`.
- The service checks each file's content. An uploaded image of another type, such as WebP, fails the whole request with `400`, whatever `onImageError` says. The same image as a URL in the document is skipped instead.
- A JSON request with entries in `assets` fails, because it has no files.

Uploaded fonts are embedded with or without `embedFonts`. `embedFonts: true` also embeds the fonts you don't upload. The service looks them up on Google Fonts, up to 20 families in their regular weight, and leaves out a family it can't find, without a warning.

## Limits

One export takes at most these sizes and counts:

| Limit                         | Value                                                                                           |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| Request body                  | 100 MB.                                                                                         |
| `options` part                | 10 MB.                                                                                          |
| Entries in `assets`           | 64, fonts and images together.                                                                  |
| One uploaded font             | 25 MB.                                                                                          |
| One uploaded image            | 20 MB.                                                                                          |
| One `data:` image in the JSON | About 5 MB. A larger one fails with `400`, and `path` points at its `src`. Upload it as a part. |
| Images the service downloads  | 200, and 100 MB in total. Each download may take 15 seconds.                                    |

The service downloads images only from public addresses, not from a private network. An image over a download limit is skipped with an `image-request-failed` warning, or fails the export with `422` when `onImageError` is `"throw"`.

On your own server, environment variables change some limits: `MAX_REQUEST_BODY_MB` for the body, `EXPORT_MAX_IMAGE_PART_MB` for an uploaded image, and `EXPORT_MAX_IMAGES`, `EXPORT_MAX_IMAGE_MB` and `EXPORT_FETCH_TIMEOUT_MS` for downloads. The other limits are fixed.

`EGRESS_GUARD=off` allows downloads from private addresses, and `EGRESS_ALLOWED_HOSTS` allows single private hosts, addresses or CIDR blocks. The limits of `customNodeDsl` are in [Custom nodes in Word files](/conversion/v3/docx/custom-nodes#validation-and-limits).

## Response

A successful export returns `200` with the file as the body, and these headers:

| Header                        | Value                                                                     |
| ----------------------------- | ------------------------------------------------------------------------- |
| `Content-Type`                | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| `Content-Disposition`         | `attachment; filename=export-<timestamp>.docx`                            |
| `X-Export-Warnings`           | The warnings, as Base64 of a JSON array. Missing when there are none.     |
| `X-Export-Warnings-Truncated` | `true` when some warnings did not fit into `X-Export-Warnings`.           |

### Warnings

A warning says what an export left out or changed, while the export still succeeds. The service puts the warnings into the `X-Export-Warnings` header, which this Node.js code decodes:

```js
const header = response.headers.get('X-Export-Warnings')
const warnings = header ? JSON.parse(Buffer.from(header, 'base64').toString('utf8')) : []
```

Each warning has a `code` and a `message`, and some carry more fields, such as `nodeType`, `src`, `path` or `formatId`. [Warnings and errors](/conversion/v3/reference/warnings-and-errors) lists the codes.

The header holds about 8 KB and is cut only between warnings, so it decodes as JSON even when some are missing. When some warnings don't fit, `X-Export-Warnings-Truncated` is `true`, and the header holds the ones that fit or is missing. A browser can read both headers too.

## Errors

A failed export returns the error shapes of the [REST API overview](/conversion/v3/rest-api/overview#errors), which also lists the authentication, size and rate limit errors.

A failed custom node rule has a shape of its own: `error` and a `code` that starts with `DOCX_DSL_`, but no `success`. Its `dslPath` names the place in the rules, and on a `422`, `nodePath` and `nodeType` name the node when the service knows it.

These codes come from the export itself:

| Status | `code`                       | When                                                                                                        |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 400    | `INVALID_EXPORT_OPTIONS`     | The body can't be read, a field is unknown or invalid, or an upload breaks a rule or a limit.               |
| 400    | `REMOVED_EXPORT_OPTION`      | The body has a [removed field](#removed-fields).                                                            |
| 400    | `DOCX_DSL_*`                 | A custom node rule fails its check.                                                                         |
| 422    | `DOCX_DSL_*`                 | A custom node rule fails while it renders a node.                                                           |
| 422    | `FAILED_TO_EXPORT_DOCX_FILE` | The export failed, or `onImageError` is `"throw"` and an image can't be used. Then `error` names its `src`. |

A validation error's `error` ends with the field's path in parentheses, such as `(document)`, and `path` holds it too.

## Fields the editor extension sends

The Export DOCX extension also sends these fields, which it reads from the editor and from Page Layout. A backend rarely needs them:

| Field                    | Type       | Description                                                                                                                                                                                                                                                          |
| ------------------------ | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pageSetup`              | `object`   | Page Layout's page setup, in CSS pixels: `{ format: { id, width, height }, orientation, margins: { top, right, bottom, left }, columns?: { count, gaps, rule, widths }, pageNumbering? }`. An object of another shape is read as the attributes of a `sectionBreak`. |
| `outline`                | `object`   | The outline numbering of headings: `{ types, levels, ignore }`.                                                                                                                                                                                                      |
| `numberingFormats`       | `object[]` | The list numbering formats. One the service can't build falls back to the default, with a `numbering-format-invalid` warning whose `formatId` names it.                                                                                                              |
| `documentCss`            | `object`   | The CSS the editor measured. One the service can't read fails with `400`.                                                                                                                                                                                            |
| `cellParagraphIds`       | `string[]` | The `id` attributes of the paragraphs inside tables, so the service styles them as table cell text from `documentCss`.                                                                                                                                               |
| `listParagraphOverrides` | `object[]` | `[{ path, overrides }]` for single list paragraphs. A `path` holds child indexes from the document root, each path once. A `path` that points at no node gives a `list-paragraph-path-missing` warning.                                                              |
