Conversion v2 is the version with the 0.x packages of Export DOCX and Import DOCX, which call the v2 API of Tiptap Conversion. The 1.0 packages call v3, the version these pages describe. So moving to v3 means updating each package to 1.0, then the code that uses it.

At the end of this guide, your editor exports and imports with 1.0 and reports anything left from 0.x as a warning. The guide has two parts, [Export](#export) and [Import](#import). An editor that uses only one of the packages needs only its part.

First, update the packages. 1.0 needs Tiptap 3, `@tiptap/core` 3.0.7 or later:

```bash
npm install @tiptap-pro/extension-export-docx@^1.0.0 @tiptap-pro/extension-import-docx@^1.0.0
```

To stay on Conversion v2 for now, keep the 0.x packages. Pin Export DOCX to `0.34`, and install Import DOCX from its `maintenance` tag. The v2 REST endpoint, `POST /v2/convert/export/docx`, stays available, so a backend that calls it directly keeps working:

```bash
npm install @tiptap-pro/extension-export-docx@0.34 @tiptap-pro/extension-import-docx@maintenance
```

In the examples, `CONVERSION_TOKEN` stands for your token, and `save` for your own function that stores the file. `editor` stands for an editor with the `ExportDocx` or `ImportDocx` extension, and `file` for a `.docx` file the user picked.

## Export

Export DOCX 1.0 no longer builds the `.docx` file in the browser. The `exportDocx` command sends the document to the Conversion service, in Tiptap Cloud or on your own server, and gets the file back. So the options that ran code in the browser are gone.

### 1. Add a Conversion token

Every export in 1.0 calls the Conversion service, so it needs a `token`: a JWT, a signed token your server creates, that allows the `Convert:Export:Docx` action. [Get a Conversion token](/conversion/v3/getting-started/install#3-get-a-conversion-token) shows how to sign one and get it into the browser.

Add the token to `ExportDocx.configure()`:

```ts
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

// 0.x
ExportDocx.configure({
  onCompleteExport: (result) => save(result),
})

// 1.0
ExportDocx.configure({
  token: CONVERSION_TOKEN,
  onCompleteExport: (result) => save(result),
})
```

After this step, the export reaches the Conversion service in Tiptap Cloud's EU region. A token in `configure()` stops working when it expires, so a long session passes a fresh one per call instead, as `exportDocx({ token })`.

Add more options for these setups:

- **US region.** Add `region: 'us'`.
- **Your own server.** Set `endpoint` to its base URL. A base URL of a v2 service, ending in `/v2`, works without a change, as [Region and endpoint](/conversion/v3/getting-started/install#region-and-endpoint) explains.
- **A token from [Legacy authentication](/authentication/legacy)**, with an App ID. Add `appId`.

### 2. Replace the standalone `exportDocx` function

1.0 removed the 0.x function that turned a JSON document into a file without an editor. It has two replacements, and both run on a server:

- **The [Export DOCX REST API](/conversion/v3/rest-api/export-docx).** Your backend sends the JSON to the Conversion service and gets the file back, with no editor. It suits a backend that isn't written in JavaScript, or one that needs no Tiptap packages. A document from an import may hold preserved content, which your code turns back first, as the REST page shows.
- **An editor that isn't mounted.** The command runs as in the browser, with the options of `ExportDocx.configure()`, and turns preserved content back on its own. It suits a backend that shares its configuration with your browser editor.

The editor version works in Node.js 18 or later, because it needs no DOM, only `fetch`, `Blob` and `FormData`. It loads the JSON with `element: null`, exports it, and destroys the editor when the export ends:

```ts
// 0.x
import { exportDocx } from '@tiptap-pro/extension-export-docx'

const file = await exportDocx({
  document: json,
  exportType: 'buffer',
  customNodes: [],
  styleOverrides: {},
})

// 1.0
import { Editor } from '@tiptap/core'
import StarterKit from '@tiptap/starter-kit'
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

const editor = new Editor({
  element: null,
  content: json,
  extensions: [
    StarterKit,
    ExportDocx.configure({ token: CONVERSION_TOKEN, exportType: 'buffer', styleOverrides: {} }),
  ],
})

const file = await new Promise<Uint8Array>((resolve, reject) => {
  editor.commands.exportDocx({
    onCompleteExport: (result) => resolve(result as Uint8Array),
    onError: reject,
  })
}).finally(() => editor.destroy())
```

Here `json` stands for your Tiptap document. `styleOverrides` and the other options of the 0.x call move to `ExportDocx.configure()`, and `customNodes` becomes `customNodeDsl` in [step 4](#4-move-custom-nodes-to-customnodedsl).

The editor needs an extension for each node type in your documents, such as tables and images, next to `StarterKit`. For documents from an import, also add `PreservedContent` from `@tiptap-pro/extension-preserved-content`, or the editor loads them as an empty document.

An editor that isn't mounted shows nothing, so export has no CSS to read. The file then has the Conversion service's default styles, changed by `styleOverrides` and `cssStyles`, as [Export styles and fonts](/conversion/v3/docx/export-styles) shows.

### 3. Read buffers as `Uint8Array` and drop stream output

`exportType: 'buffer'` gives a `Uint8Array` in 1.0, not a Node.js `Buffer`. Code that only passes the file on, such as to `writeFile`, keeps working. A check such as `Buffer.isBuffer(file)` becomes `file instanceof Uint8Array`.

`exportType: 'stream'` is gone and fails the export. Use `'buffer'` or `'blob'` instead. After this step, `onCompleteExport` receives the type your code expects.

### 4. Move custom nodes to `customNodeDsl`

1.0 can't run the JavaScript renderers of `customNodes` on the Conversion service, so it removed them. Describe each node type of your own with a custom node rule in `customNodeDsl` instead, built with the helpers from `@tiptap-pro/extension-export-docx/dsl`:

```ts
// 0.x
import { Docx, ExportDocx } from '@tiptap-pro/extension-export-docx'

ExportDocx.configure({
  customNodes: [
    {
      type: 'notice',
      render: (node) => new Docx.Paragraph(String(node.attrs?.message ?? '')),
    },
  ],
})

// 1.0
import { ExportDocx } from '@tiptap-pro/extension-export-docx'
import { docxNode, paragraph, ref, textOp } from '@tiptap-pro/extension-export-docx/dsl'

ExportDocx.configure({
  token: CONVERSION_TOKEN,
  customNodeDsl: {
    dslVersion: '1.0',
    nodes: [
      docxNode('notice')
        .block()
        .emit(paragraph().children(textOp(ref('node.attrs.message', { default: '' }))))
        .toJSON(),
    ],
  },
})
```

The `notice` node then exports as a paragraph with its message:

- `docxNode('notice')` starts the rule for the node type, and `.block()` says it is a block node.
- `emit()` says what export writes: a paragraph with one text run, `textOp()`, whose text `ref()` reads from the node's `message` attribute.
- `.toJSON()` turns the rule into the plain object that `customNodeDsl` takes.

[Custom nodes in Word files](/conversion/v3/docx/custom-nodes) explains the rules, and [Custom node DSL](/conversion/v3/docx/custom-nodes/dsl) lists the helpers. If your 0.x configuration sets `customNodeDslLimits`, remove it, because the Conversion service applies its own limits.

### 5. Turn function overrides into plain objects

The override options take plain objects only in 1.0, because a function can't be sent to the Conversion service. When one holds a function, the command leaves it out and reports an `unsupported` warning.

The override options are `paragraphOverrides`, `textRunOverrides`, `tableOverrides`, `tableRowOverrides`, `tableCellOverrides`, `imageOverrides` and each field of `headerFooterOverrides`:

```ts
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

// 0.x
ExportDocx.configure({
  paragraphOverrides: (node, context) => (context.table ? {} : { spacing: { after: 120 } }),
})

// 1.0
ExportDocx.configure({
  token: CONVERSION_TOKEN,
  paragraphOverrides: { spacing: { after: 120 } },
})
```

The plain object applies to every paragraph, including those in tables. No 1.0 override option formats only the paragraphs in tables, so the 0.x exception for tables has no counterpart.

A `customNodeDsl` rule as in step 4 can't help here either: it formats a node type of your own, not a built-in one such as `paragraph`.

### 6. Remove headers, footers and placeholders

1.0 writes headers and footers only from Page Layout, the Tiptap Pro extension that shows the editor as pages and replaces `@tiptap-pro/extension-pages`.

So the options that built them in code are gone: `headers`, `footers`, `placeholders`, `Docx.Header`, `Docx.Footer`, `convertHeader` and `convertFooter`. Remove `@tiptap-pro/extension-export-docx-header-footer` and its `ExportDocxHeaderFooter` extension too, because 1.0 ignores them. The command then takes no header or footer content:

```ts
// 0.x
import { Docx } from '@tiptap-pro/extension-export-docx'

editor.commands.exportDocx({
  headers: { default: new Docx.Header({ children: [new Docx.Paragraph('Example report')] }) },
  footers: { default: new Docx.Footer({ children: [new Docx.Paragraph('Confidential')] }) },
})

// 1.0
editor.commands.exportDocx()
```

To keep headers and footers in the file, add [Page Layout](/features/page-layout/getting-started/overview) to the editor. The file then has the headers and footers the user sees, and an editor without Page Layout has none to export. Keep `headerFooterOverrides` to format them.

[Header and footer](/features/page-layout/header-and-footer) shows how to add them, and [Page numbers](/features/page-layout/page-numbers) how a footer shows the page number that `placeholders` filled in.

1.0 reads nothing from `@tiptap-pro/extension-pages`, so its page size doesn't reach the file. Without Page Layout, pass the page size and margins in the `pageSize` and `pageMargins` options, as [Page size and margins](/conversion/v3/docx/export#page-size-and-margins) shows.

Footnotes and endnotes of the [Footnotes](/features/footnotes) extension are nodes in the document, and they export without Page Layout too. A document with no such nodes can still pass its notes in the `footnotes` and `endnotes` options, as [Footnotes and endnotes](/conversion/v3/docx/elements/footnotes) shows.

An editor that still uses `@tiptap-pro/extension-pages`, the legacy Pages extension, keeps its notes in the extension's storage, not in the document. Pass them in these options to export them:

```ts
editor.commands.exportDocx({
  footnotes: editor.storage.pages.footnotesJSON,
  endnotes: editor.storage.pages.endnotesJSON,
})
```

### 7. Replace removed exports

1.0 no longer exports the `docx` library or its own converters, because the Conversion service builds the file. Replace each import your code still has:

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `Docx`                                                                                                                                                                                                              | None. Use plain objects in overrides, and `customNodeDsl` for output of your own.                                                 |
| `CharacterSet`                                                                                                                                                                                                      | The character set string, such as `'00'` for ANSI.                                                                                |
| `LevelFormat`                                                                                                                                                                                                       | The format string, such as `'decimal'` or `'lowerRoman'`.                                                                         |
| `IRunOptions`, `PositiveUniversalMeasure`                                                                                                                                                                           | The types `TextRunOverrides` and `PageMeasure` of this package.                                                                   |

The Conversion service renders the nodes.                                                                                   |
| `processCssStyles`, `createExportStyles`, `exportStylesFromCss`, `ExportStyles`, `ExportStylesOptions`                                                                                                              | The `cssStyles` option, or `documentStyles: true`, the default. See [Export styles and fonts](/conversion/v3/docx/export-styles). |
| `compileCustomNodeDsl`, `DEFAULT_LIMITS`, `DslCompileError`, `DslRuntimeError`, `DslErrorCode`, `DslErrorPayload`                                                                                                   | None. The Conversion service checks `customNodeDsl`.                                                                              |
| `CustomNode`, `CustomNodeResult`, `OverrideContext`, `*OverridesConfig`, `ResolvedHeaderFooterOverrides`, `DocxPlaceholders`, `DocxPlaceholderField`, `DocxPlaceholderRegistry`, `ConvertConfig`, `ImageDimensions` | None. 0.34.8 renamed the option and the functions that read the editor's styles, and 1.0 doesn't have the new names. The rows marked 0.34.8 give the name 1.0 uses instead.

A constant becomes its string value, so `LevelFormat.LOWER_ROMAN` becomes `'lowerRoman'`. After this step, your code imports nothing that 1.0 removed, so it builds again.

### 8. Replace the unit helpers

0.x exported helpers that convert pixels and points to Word's units. `@tiptap-pro/extension-export-docx` 1.0 no longer exports them. Each one is a single multiplication, so write it in your code:

| 0.x helper                 | 1.0 code       |
| -------------------------- | -------------- |
| `pixelsToPoints(px)`       | `px * 0.75`    |
| `pixelsToHalfPoints(px)`   | `px * 1.5`     |
| `pointsToTwips(pt)`        | `pt * 20`      |
| `pointsToHalfPoints(pt)`   | `pt * 2`       |
| `lineHeightToDocx(height)` | `height * 240` |

### 9. Check images and fonts

1.0 builds the file on the Conversion service, so the service needs every image and font of the document. Check that each image is public or on the page's own origin.

The command uploads an image from the browser when it is one of these:

- an image on the page's own origin,
- a `blob:` URL,
- a `data:` URL over 64 KB.

The service downloads every other image from its URL. So an image on another origin that needs a login is left out with a warning. To keep it, serve it from the page's own origin, such as through a route of your app, or make it public.

An editor in Node.js has no page, so there the command uploads only `blob:` and large `data:` URLs.

The `fonts` option, which embeds font files you pass, keeps its shape and takes WOFF2 files in 1.0 as well as TTF and OTF. `embedFonts: true`, which 0.x didn't have, uploads the page's `@font-face` files, so you don't need to pass them. [Embed fonts](/conversion/v3/docx/export-styles#embed-fonts) shows both.

One export uploads at most 64 files, fonts first and then images. A file over the limit is left out with a warning. [Limitations](/conversion/v3/reference/limitations#size-limits-of-an-export) lists the other limits.

After this step, the file has the images and fonts the user sees.

### 10. Handle export warnings

Export reports what it leaves out to `onWarning`, and that includes the 0.x options from the steps before. Add a handler, so a leftover 0.x option shows up instead of being dropped without notice:

```ts
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

ExportDocx.configure({
  token: CONVERSION_TOKEN,
  onWarning(warning) {
    if (warning.code === 'unsupported') console.warn(warning.attribute, warning.message)
  },
  onCompleteExport: (result) => save(result),
})
```

A removed option, such as `headers` or `customNodes`, isn't sent and arrives as an `unsupported` warning with its name in `attribute`. In TypeScript, a removed option written into `configure()` is also a type error, because the 1.0 types don't have it. [Warnings and errors](/conversion/v3/reference/warnings-and-errors) lists every warning code.

`ExportDocx` 1.0 logs no console warning when the editor lacks the extension from `@tiptap-pro/extension-convert-kit`. The PDF, DOC, ODT and EPUB export extensions still log one in development.

## Import

In Import DOCX 1.0, the `importDocx` command writes into Page Layout when the editor has it, and keeps content the editor has no extension for. Several 0.x options are gone, and warnings and errors have their own callbacks. Each step shows the 0.x code and its 1.0 replacement.

### 1. Check that you pass a `token`

`token` is required in 1.0. The import fails before it sends a request when `token` is missing, so make sure every `ImportDocx.configure()` call sets one. The token allows the `Convert:Import:Docx` action, as [Get a Conversion token](/conversion/v3/getting-started/install#3-get-a-conversion-token) shows:

```ts
import { ImportDocx } from '@tiptap-pro/extension-import-docx'

ImportDocx.configure({
  token: CONVERSION_TOKEN,
})
```

Add `appId`, and `region` or `endpoint`, as for export in [Add a Conversion token](#1-add-a-conversion-token). An `endpoint` that ends in `/v2` or `/v2/convert` still works, because the import calls `/v3` or `/v3/convert` on the same server. So one base serves both the import and the export extension, as [Connection options](/conversion/v3/getting-started/install#connection-options) explains.

### 2. Replace `imageUploadCallbackUrl`

`imageUploadCallbackUrl` is gone. Pass `imageUploadConfig` with the upload URL instead:

```ts
// 0.x
ImportDocx.configure({
  imageUploadCallbackUrl: 'https://example.com/upload',
})

// 1.0
ImportDocx.configure({
  token: CONVERSION_TOKEN,
  imageUploadConfig: { url: 'https://example.com/upload' },
})
```

`imageUploadConfig` also takes `headers`, `method` and `queryParams`, as [Images](/conversion/v3/docx/import#images) shows.

### 3. Replace `verbose` with `onWarning`

`verbose` is gone. `onWarning` receives everything the import left out or changed, and a warning never stops the import:

```ts
// 0.x
ImportDocx.configure({ verbose: 1 })

// 1.0
ImportDocx.configure({
  token: CONVERSION_TOKEN,
  onWarning: (warning) => console.warn(warning.code, warning.message),
})
```

A warning has a `code`, which is one of these:

- `preserved`: the editor has no extension for a node or mark, so the import kept it as preserved content. It comes back when you add the extension, as [Content the editor cannot show](/conversion/v3/docx/preserved-content) explains.
- `restructured` or `mark-excluded`: the import changed the shape of some content to fit the editor, and kept its text.
- A code from the Conversion service, such as `bookmarks-dropped` or `image-skipped`, for something it left out or changed while it read the file.

The service logs stay in `context.logs` and don't become warnings. Without `onWarning`, warnings go to the console. [Warnings and errors](/conversion/v3/reference/warnings-and-errors) lists every code.

### 4. Remove placeholders

The `placeholders` option is gone from the command, and the `placeholders` setting of the legacy Pages extension no longer feeds the import. Word page fields such as `PAGE` and `NUMPAGES` arrive as `pageNumber` nodes for Page Layout, and an editor without Page Layout keeps them as preserved content:

```ts
// 0.x
editor
  .chain()
  .importDocx({ file, placeholders: { total: 'pages' } })
  .run()

// 1.0
editor.chain().importDocx({ file }).run()
```

### 5. Read headers, footers and page setup from `content`

The import returns one Page Layout document. Sections, page setup, headers, footers, page numbers, breaks and notes are all inside `context.content`. The separate header, footer, `footnotes` and `endnotes` fields are gone from the `onImport` context, as are `pageLayout` and `numberingFormats`:

```ts
// 0.x
const { content, header, footer, pageLayout } = context

// 1.0
const { content } = context
```

With Page Layout, `setEditorContent` writes all of it in one step, as [The onImport context](/conversion/v3/docx/import#the-onimport-context) shows. 1.0 doesn't support the legacy Pages extension, `@tiptap-pro/extension-pages`. To keep using it, stay on 0.x from the `maintenance` tag.

### 6. Write into Page Layout

When the editor has Page Layout, `setEditorContent` replaces its Source Document, the document Page Layout lays out into pages, with the sections, headers, footers and notes. One undo takes the import back:

```ts
editor.commands.importDocx({
  file,
  onImport: (context) => {
    if (context.error) return
    context.setEditorContent()
  },
})
```

A Page Layout editor that has not mounted, such as a headless one in Node.js, has no pages. So the import writes into the editor's own document, which is then the Source Document.

Without Page Layout, the body goes into the editor with `setContent`. The parts only Page Layout shows, such as sections, headers and footers, are kept as preserved content until you add Page Layout, as [Without Page Layout](/conversion/v3/docx/preserved-content#without-page-layout) explains. See [Page Layout](/features/page-layout/getting-started/overview) and [Footnotes](/features/footnotes).

### 7. Handle errors with `onError`

Errors go to `onError`. Set it on the command or on `ImportDocx.configure()`, and the command's callback wins:

```ts
ImportDocx.configure({
  token: CONVERSION_TOKEN,
  onError: (error) => console.error(error),
})
```

Without `onError`, the error reaches `onImport` as `{ content: null, error }`, if the import hadn't handed over the document yet. Without either, the import logs the error with `console.error`.

A refused request or a network failure gives an `ImportDocxRequestError`. It has a `code` and, when the server responded, a `status`. [Warnings and errors](/conversion/v3/reference/warnings-and-errors) lists every error.

### 8. Expect a newer import to win

When you start a second import before the first response arrives, the first one writes nothing. It reports an `ImportDocxSupersededError`. Calling `setEditorContent` from an older import throws the same error:

```ts
import { ImportDocx, ImportDocxSupersededError } from '@tiptap-pro/extension-import-docx'

ImportDocx.configure({
  token: CONVERSION_TOKEN,
  onError(error) {
    if (error instanceof ImportDocxSupersededError) return
    console.error(error)
  },
})
```

## Check that it worked

Run an export with the `onWarning` handler of [Handle export warnings](#10-handle-export-warnings), and an import with `onWarning` and `onError`. The migration is done when `onCompleteExport` receives the file, the imported file shows in the editor, `onError` receives nothing, and the console shows no `unsupported` warning.
