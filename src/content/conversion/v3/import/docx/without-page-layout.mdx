In an editor without [Page Layout](/pages/v2/getting-started/overview), `setEditorContent` writes the body with `setContent`. Footnotes, endnotes, headers, footers and the page size stay in the `onImport` context.

## Import into the editor

Call `setEditorContent` from `onImport`. Without `onImport`, the import does the same as soon as the document arrives.

```ts
editor.commands.importDocx({
  file,
  onImport: ({ error, setEditorContent }) => {
    if (error) return
    setEditorContent()
  },
})
```

The import never records the write as tracked changes, even when the tracked changes extension is on the editor.

If the editor refuses the document, the import fails with an error. It reaches `onError`.

## Notes, headers and page setup

The import writes only the body. Everything else comes back in the `onImport` context for you to place.

```ts
editor.commands.importDocx({
  file,
  onImport: ({ error, setEditorContent, footnotes, endnotes, header, footer, pageLayout }) => {
    if (error) return
    setEditorContent()
    // Place the notes, header, footer and page setup where your app keeps them.
  },
})
```

- The references to notes stay in the text as `footnoteReference` and `endnoteReference` nodes. Each has a `noteId`. The editor needs nodes with those names to keep them.
- `footnotes` and `endnotes` hold the note bodies as Tiptap JSON, keyed by note id.
- `header`, `footer` and the other header and footer fields hold the headers and footers, or `null`.
- `pageLayout` holds the page size and margins in twips, or `null`.

See [footnotes and endnotes](/conversion/v3/content-reference/structures-and-media/footnotes-endnotes) for the references, [headers and footers](/conversion/v3/content-reference/page-layout/headers-footers) for the header fields and [page structure](/conversion/v3/content-reference/page-layout/page-structure) for the page size.

## Content the editor can't hold

The import rewrites the content to fit the editor schema before it writes. A node with content that the schema doesn't know becomes a paragraph and keeps its children. A node without content, and any mark the schema doesn't know, is dropped. `onWarning` receives one `unsupported` warning for each type.

Add the extension for a type to keep it. A section with several columns imports as a `columns` node that holds one `column` node, and the Columns extension can't hold that shape. See [page structure](/conversion/v3/content-reference/page-layout/page-structure#section-columns).

<Callout title="Page breaks need a node" variant="info">
  Without a `pageBreak` node, page breaks are left out and `onWarning` receives an `unsupported`
  warning. See [page breaks](/conversion/v3/content-reference/page-layout/page-breaks).
</Callout>

## Numbering formats

When the file has numbered lists, `setEditorContent` registers their formats with the editor. It does this when the editor has an extension with a `registerNumberingFormats` command. The formats also arrive as `numberingFormats` in the context. See [lists](/conversion/v3/content-reference/text-and-formatting/lists).
