A Word table imports as a `table` node with rows and cells, and exports back as a Word table. Merged cells, column widths, borders, cell backgrounds and row heights convert in both directions. Header rows import, but export from the editor writes them as ordinary rows.

## What you need

`TableKit` from `@tiptap/extension-table` registers `Table`, `TableRow`, `TableCell` and `TableHeader`, which `StarterKit` doesn't include:

```ts
import StarterKit from '@tiptap/starter-kit'
import { TableKit } from '@tiptap/extension-table'

const extensions = [StarterKit, TableKit]
```

Without them, import keeps each table as [preserved content](/conversion/v3/content-reference/overview#what-the-editor-keeps), whose cell text stays editable, and reports a `preserved` warning. The table comes back once you add `TableKit`.

The stock cells define `colspan`, `rowspan` and `colwidth`. Import also sets the attributes in this table, which no Tiptap extension defines:

| Node                          | Attributes import adds                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| `table`                       | `width`, `indent`, `border*` for each side and for the inside grid, `cellMargin*` per side |
| `tableRow`                    | `height` and `heightRule`                                                                  |
| `tableCell` and `tableHeader` | `background`, `verticalAlign`, `border*` for each side, `cellMargin*` per side             |

The editor keeps them in each node's `preservedAttrs` attribute, which holds attributes the editor's extensions don't define. You don't need to touch it, because export writes them back. They become real attributes when you add an extension that defines them. An imported table's `preservedAttrs` shows their exact names and values.

## Import

Import returns `tableCell` nodes, and `tableHeader` nodes for header rows:

- `colspan` and `rowspan` come from merged cells, also from cells merged across rows.
- `colwidth` is an array of pixel widths, one for each column the cell covers.
- `background` is the cell shading as a hex color, and `verticalAlign` is `top`, `middle` or `bottom`.
- `width` is the table's fixed width in pixels. A table with a percentage width imports without one, so it stays fluid.

A row is a header row only when Word's "Repeat as header row at the top of each page" is on for it. A first row that is only bold or shaded imports as ordinary cells.

To make such a row a header row, change its cells' `type` in `onImport`, before `setEditorContent()` writes the document. This example does it for the first table, with `file` as a `.docx` file the user picked:

```ts
editor.commands.importDocx({
  file,
  onImport: (context) => {
    if (context.error) return
    const table = context.content.content?.find((node) => node.type === 'table')
    table?.content?.[0]?.content?.forEach((cell) => {
      cell.type = 'tableHeader'
    })
    context.setEditorContent()
  },
})
```

A page break in a cell stays in the cell's paragraph, as [Page breaks](/conversion/v3/content-reference/page-layout/page-breaks) describes.

When the Conversion service, which converts the file, can't read a table, the paragraphs of its cells arrive without the table. An unreadable table without text is left out with a warning.

## Export

A table with a `width` exports at that width. Without one, it takes the width the editor shows, or the page width when nothing was measured. Column widths come from `colwidth`, or are shared evenly.

Export writes merged cells, borders, cell margins, backgrounds, vertical alignment and row heights from the attributes. `heightRule: 'exact'` writes an exact height, any other value a minimum.

A table without border or margin attributes gets the borders and cell padding the user sees, and header cells keep their own look. Export measures them from the CSS of the editor shown on the page.

A headless editor has nothing to measure, so such a table exports without borders and with Word's default cell margins.

A row whose CSS has `break-inside: avoid`, such as `.tiptap tr { break-inside: avoid; }`, stays on one page in Word.

`tableOverrides`, `tableRowOverrides` and `tableCellOverrides` set defaults for every table, as plain objects in twips, a twentieth of a point. The example runs on an editor set up as in [Export DOCX](/conversion/v3/export/docx/editor-extension), and [Export styles and fonts](/conversion/v3/export/docx/styles#set-default-formatting) lists the fields:

```ts
editor.commands.exportDocx({
  tableCellOverrides: { margins: { top: 80, bottom: 80 } },
})
```

The Export DOCX extension writes `tableHeader` cells as ordinary cells. For header rows that Word repeats on each page, send the document to the [Export DOCX REST API](/conversion/v3/rest-api/export-docx) with `repeatTableHeaderRows: true`.

## Limits

- A header row exported from the editor doesn't repeat on each page in Word.
- [Page Layout](/features/page-layout/getting-started/overview), the extension that shows the document on pages, has two table settings of its own. A table's `repeatHeaderRow` repeats its leading header rows on each page, and a row's `breakAcrossPages: false` keeps the row on one page. Import doesn't set them from Word, and export doesn't read them, without a warning. This is a known limit that is being fixed.
