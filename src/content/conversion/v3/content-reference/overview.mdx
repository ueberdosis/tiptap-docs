Each feature links to its page, which names the extension it needs and the details. To add import and export to an editor, see [Import DOCX](/conversion/v3/import/docx/editor-extension) and [Export DOCX](/conversion/v3/export/docx/editor-extension).

The editor's schema, the node and mark types it allows, comes from its extensions. An import also keeps content the editor has no extension for.

Where a note says an attribute is kept in `preservedAttrs`, the editor stores it without showing it, and export writes it back, as [What the editor keeps](#what-the-editor-keeps) explains.

## Text and formatting

Character formatting arrives as marks on the text, and paragraph formatting as attributes of the `paragraph` and `heading` nodes.

### Character formatting

| ----------------------------------------------------------------------------------------------------------------------- | ------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Bold, italic, strikethrough](/conversion/v3/content-reference/text-and-formatting/bold-italic-underline-strike#import) | Yes    | Yes    | Double strikethrough doesn't import.                                                                                                                                                                    |
| [Underline](/conversion/v3/content-reference/text-and-formatting/bold-italic-underline-strike#import)                   | Yes    | Yes    | Underline styles such as double or dotted import as `underlineType`, which `Underline` doesn't define, so the editor keeps it in `preservedAttrs`.                                                      |
| [Subscript, superscript](/conversion/v3/content-reference/text-and-formatting/subscript-superscript#what-you-need)      | Yes    | Yes    | Needs `Subscript` and `Superscript`.                                                                                                                                                                    |
| [Text color](/conversion/v3/content-reference/text-and-formatting/text-color-highlight#import)                          | Yes    | Yes    | A theme color without a hex value doesn't import.                                                                                                                                                       |
| [Highlight](/conversion/v3/content-reference/text-and-formatting/text-color-highlight#import)                           | Yes    | Yes    | Import also reads Word's character shading, a background color behind text, as a highlight. | [Font family, font size](/conversion/v3/content-reference/text-and-formatting/font-family-size#import)                  | Yes    | Yes    | Import rounds sizes to whole pixels. | [Letter spacing](/conversion/v3/content-reference/text-and-formatting/font-family-size#export)                          | Partly | Partly | Import keeps `letterSpacing` of `textStyle` in `preservedAttrs`. | [Tabs](/conversion/v3/content-reference/text-and-formatting/tabs#import)                                                | Partly | Yes    | A tab imports as four spaces, and tab stops don't import. | [Right-to-left text](/conversion/v3/content-reference/text-and-formatting/text-alignment#right-to-left-text)            | No     | Partly | Import ignores the text direction. ## Page layout

[Page Layout](/features/page-layout/getting-started/overview), the extension that shows the document on pages, holds sections, page setup, headers and footers. Import brings them into it, and export writes them from it. Without Page Layout, import keeps them as preserved content.

| ------------------------------------------------------------------------------------------------- | ------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [Page breaks](/conversion/v3/content-reference/page-layout/page-breaks)                           | Yes    | Yes    | Column breaks convert too. Without Page Layout, the node of `@tiptap-pro/extension-pagebreak` holds a page break.                                            |
| [Page size, orientation and margins](/conversion/v3/content-reference/page-layout/page-structure) | Yes    | Yes    | For each section. Import leaves out the binding gutter, with a `gutter-dropped` warning.                                                                     |
| [Sections](/conversion/v3/content-reference/page-layout/page-structure)                           | Yes    | Yes    | A section that starts on an even or odd page, or in the next column, starts on the next page.                                                                |
| [Section columns](/conversion/v3/content-reference/page-layout/page-structure)                    | Yes    | Yes    | Word's Layout > Columns, kept as settings of each section's `sectionBreak` node.                                                                             |
| [Headers and footers](/conversion/v3/content-reference/page-layout/headers-footers)               | Yes    | Yes    | Each section's own, with first page and even page versions.                                                                                                  |
| [Page number fields](/conversion/v3/content-reference/page-layout/headers-footers)                | Yes    | Yes    | Word's fields for the page number, the number of pages and the pages of the section import as Page Layout's `pageNumber` nodes, which export as live fields. |
| [Other fields, such as dates](/conversion/v3/content-reference/page-layout/headers-footers)       | Partly | No     | Import keeps the text Word last showed, which no longer updates. Export writes that text, not a field.                                                       |

## What the editor keeps

The editor shows what its extensions define. Content the editor has no extension for is kept as preserved content, so an import never fails because of the editor's schema and keeps all of its text.

Preserved content comes from `@tiptap-pro/extension-preserved-content`. The Import DOCX extension (`ImportDocx`) depends on it and adds it to the editor on its own, so you don't install or register it:

- **A node type the editor lacks**, such as a table without `TableKit`, is kept with its type and attributes. Its text stays editable.
- **A mark type the editor lacks**, such as a comment without the Comments extension, is kept on its text.
- **Attributes a node or mark type doesn't define**, such as table borders with the stock table extensions, are kept in its `preservedAttrs` attribute, without a warning. The editor doesn't show them.

For each preserved node or mark type, the `onWarning` callback of `ImportDocx` receives a `preserved` warning with its `nodeType` or `markType`.

Without Page Layout, notes and page breaks become real nodes when the editor has an extension for them, such as the Footnotes extension, and preserved content otherwise. Sections, headers and footers stay preserved content until you add Page Layout.

Export writes preserved content and `preservedAttrs` back to the `.docx` file in their original form, except `letterSpacing`, as [Font family and size](/conversion/v3/content-reference/text-and-formatting/font-family-size#export) says.

The package ships no stylesheet, so preserved content reads like body text, and a preserved page break or note reference doesn't show at all. This CSS frames each preserved block and labels it with its original type, and shows each empty preserved inline node as its type in brackets:

```css
.tiptap [data-preserved-block] {
  border-left: 2px solid #ccc;
  padding-left: 0.5rem;
}

.tiptap [data-preserved-block]::before {
  content: attr(data-preserved-type);
  display: block;
  font-size: 0.75rem;
  color: #888;
}

.tiptap [data-preserved-inline]:empty::before {
  content: '[' attr(data-preserved-type) ']';
  font-size: 0.75rem;
  color: #888;
}
```

### Turn preserved content back

Preserved content turns back into the real node, and `preservedAttrs` into real attributes, when you add the extension that defines them and load the saved document again. An editor created with `new Editor` does it on its own for a JSON document you pass as `content`.

With Page Layout, `createPageLayoutEditor` does it on its own too, and the restore isn't in the undo history.

To restore the document an editor already holds, run the `restorePreservedContent()` command. One undo takes it back. It returns `false` when there is nothing to restore:

```ts
editor.commands.restorePreservedContent()
```

A shared document, which Tiptap Collaboration syncs between users, is never restored when the editor opens, with or without Page Layout. If every client restored it, each would insert the same node, and the document would hold it twice.

So run the command for a shared document from one client only, at a time your app chooses. For example, run it from an action that one user starts after you add the extension. Once that restore has synced, the other clients find nothing to restore, and the command returns `false` there.

`holdsPreservedContent(editor.getJSON())` from `@tiptap-pro/extension-preserved-content` tells you whether to offer that action at all.

To restore a document without an editor, such as on a server, call the function `restorePreservedContent({ content, schema })`. It returns the restored JSON. `holdsPreservedContent(content)` tells you whether a document holds any preserved content. Both come from `@tiptap-pro/extension-preserved-content`.

### Content that changes shape

Import changes the shape of some content to fit the editor and keeps its text. `onWarning` names each case:

- **`restructured`** is the warning for a node that didn't fit where it was, such as a numbered heading that becomes its list item's paragraph.
- **`mark-excluded`** is the warning for a mark the editor doesn't allow next to another one, such as `bold` on `code`.

A third code, `unsupported`, means a type was left out with nothing kept. Import gives it only when the editor's schema has no preserved content.

### Change the import before it reaches the editor

To read or change the document before the editor shows it, pass `onImport` to the `importDocx()` command. `onImport` receives a `context`, and `context.content` holds the whole Word file as one JSON document, with the headers, footers and notes inside.

Once you pass `onImport`, the editor changes only when you call `context.setEditorContent()`. It writes `context.content`, or the document you pass it.

In this example, `file` is a `.docx` file the user picked. `context.error` is set when the import failed:

```ts
editor.commands.importDocx({
  file,
  onImport: (context) => {
    if (context.error) return
    console.log(context.warnings)
    context.setEditorContent()
  },
})
```

[Import DOCX API](/conversion/v3/import/docx/api#importcontext) lists the other fields, such as `commentThreads` and `warnings`.

Warnings from the Conversion service, the server that converts the file, reach `onWarning` before `onImport` runs. The editor's own warnings, such as `preserved`, arrive when `setEditorContent()` writes. [Warnings and errors](/conversion/v3/import/docx/warnings-and-errors) lists every code.

## Limits

These Word features have no page of their own, and convert only partly or not at all. Where import leaves something out without a warning, it is a known limit that is being fixed.

| Feature                                                                                                 | What happens                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Table of contents                                                                                       | Import keeps the entries as plain paragraphs, with a `toc-flattened` warning. Export drops a `tableOfContents` node with an `unsupported` warning. |
| Text boxes                                                                                              | Import leaves them out with their text, without a warning.                                                                                         |
| Shapes, SmartArt, WordArt                                                                               | Import leaves them out, without a warning.                                                                                                         |
| Symbols inserted with Word's Symbol command                                                             | Import keeps each symbol as its character in the symbol's font, so it shows correctly only where that font is installed.                           |
| Text in custom XML tags, which mark parts of a file for other software, and in text direction overrides | Import keeps the text, but a text direction override loses its direction.                                                                          |
| Hidden text                                                                                             | Import leaves it out, without a warning.                                                                                                           |
| Content controls and form fields                                                                        | Import keeps the text and drops the control.                                                                                                       |
| Document properties, such as author and title                                                           | Import doesn't read them, and export doesn't write them.                                                                                           |
