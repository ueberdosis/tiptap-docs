This page shows how to import a Word file into a Page Layout editor and export it again. What each section keeps is in [Sections and page setup](/conversion/v3/docx/page-layout/sections), and what happens to headers, footers and page numbers is in [Headers and footers](/conversion/v3/docx/page-layout/headers-and-footers).

## Import a Word file

With Page Layout, the import writes the file into the document, with its sections, page setup, headers, footers and notes. Without `onImport`, the import writes the document when it arrives. With `onImport`, it writes when you call `setEditorContent()`, as [Review an import before it applies](/conversion/v3/docx/import/review) shows:

```ts
editor.commands.importDocx({
  file,
  onImport: (context) => {
    if (context.error) return
    context.setEditorContent()
  },
})
```

The write is one step, so one undo takes the import back. The caret lands at the start of the body. The Tracked Changes extension doesn't record the write as a suggestion, even while it records the user's edits.

You save the imported document as any Page Layout document: store what `editor.getJSON()` returns. It holds the sections, headers and notes, but no pages, because Page Layout draws the pages from it each time. Don't save `editor.state.doc`, which holds the pages the user sees.

A Page Layout editor that has not mounted, such as a headless one in a Node.js script, draws no pages. The import still writes the sections, headers and notes, and `editor.getJSON()` returns them.

An import never fails because of your schema. Content that the editor has no extension for is kept, as [Content the editor cannot show](/conversion/v3/docx/preserved-content) explains.

### Tell the import apart from an edit

Each write of the import carries the `DOCX_IMPORT_META` transaction meta, set to `true`, so your extensions can tell an import apart from the user's edits. With Page Layout, read it in `onUpdate`, not in `onTransaction`, because only the `update` event carries the import's own transaction:

```ts
import { Extension } from '@tiptap/core'
import { DOCX_IMPORT_META } from '@tiptap-pro/extension-import-docx'

const LogImports = Extension.create({
  name: 'logImports',
  onUpdate({ transaction }) {
    if (transaction.getMeta(DOCX_IMPORT_META)) console.log('DOCX imported')
  },
})
```

### When the import fails

`setEditorContent()` throws when the editor was destroyed before the write, such as when its component unmounts during the import. It also throws when a newer import has started.

You don't need to catch these errors yourself. An error thrown inside `onImport`, including by `setEditorContent()`, reaches `onError`, on the command or in `ImportDocx.configure()`. [Import errors](/conversion/v3/reference/errors#import-errors) lists every error of an import.

## Export a Page Layout document

Export reads the page setup from the document, so the file gets each section's paper, headers and footers without any export option. Export starts a Word section at each `sectionBreak`, the node that starts a section and holds its page setup. [Sections and page setup](/conversion/v3/docx/page-layout/sections) and [Headers and footers](/conversion/v3/docx/page-layout/headers-and-footers) say what Word gets.

### Export on other paper

Each section exports on the paper its `sectionBreak` holds. An imported document starts with a `sectionBreak`, so no export option changes its paper, only a change to its sections does.

Page Layout's `setPageSections()` command replaces every section in one step, which one undo takes back. This example puts every section on US Letter, keeps its orientation and margins, and undoes the change once the file arrives, so the user's document keeps its paper. `PAGE_FORMATS` holds Page Layout's paper sizes, and `save` stands for your app's code that stores the file:

```ts
import { PAGE_FORMATS } from '@tiptap-pro/extension-page-layout'

const engine = editor.storage.pageLayout.engine

editor.commands.setPageSections(
  engine.getSections().map((section) => ({
    ...section,
    setup: { ...section.setup, format: PAGE_FORMATS.Letter },
  })),
)

editor.commands.exportDocx({
  onCompleteExport: (file) => {
    editor.commands.undo()
    save(file)
  },
  onError: () => editor.commands.undo(),
})
```

Undo takes back the last step, so the user should not edit while the export runs. To keep Letter in the document, leave out the undo. In a pageless editor, `setPageSections()` returns `false`. [Sections](/features/page-layout/sections) and [Page format](/features/page-layout/page-format) describe the commands.

### A document that stores no paper

A document written in the editor may store no paper of its own, so its content before the first `sectionBreak` has none. Export gives that content the paper the editor shows, which the `setup` of `PageLayout.configure()` or the `setPageSetup()` command sets.

The `pageSetup` option replaces that paper for one export. It changes nothing in a document that starts with a `sectionBreak`, such as an imported one. Build it with Page Layout's `pageSetup()` function. The `id` of its `format` can be any string, because the paper size in the file comes from the format's `width` and `height` in CSS pixels. This example sets US Letter with one-inch margins:

```ts
import { pageSetup } from '@tiptap-pro/extension-page-layout'

editor.commands.exportDocx({ pageSetup: pageSetup('Letter') })
```

A pageless editor shows the document as one continuous column, without pages. An editor is pageless when `PageLayout` has no `setup`, or after `setPageSetup(null)`, as [Page format](/features/page-layout/page-format) describes.

A pageless editor shows no paper, so the content before the first `sectionBreak` exports with the `pageSize` and `pageMargins` options, unless you pass `pageSetup`. Their default is A4 with margins of 2.54cm at the top and bottom and 3.17cm at the sides, as [Page size and margins](/conversion/v3/docx/export#page-size-and-margins) shows.

## How the document holds the pages

Page Layout keeps the page setup of a Word file in the document, as nodes, so it is saved with the document and export finds it there:

| Node                       | What it holds                                                               |
| -------------------------- | --------------------------------------------------------------------------- |
| `sectionBreak`             | The start of a section, with the section's page setup                       |
| `pageFurniture`            | One header or footer of a section, inside the section's `sectionBreak`      |
| `pageNumber`               | A page number field that Page Layout updates, in a header, a footer or text |
| `pageBreak`, `columnBreak` | A break the user inserted, inside its paragraph                             |

[Sections](/features/page-layout/sections), [Section columns](/features/page-layout/section-columns), [Header and footer](/features/page-layout/header-and-footer), [Page numbers](/features/page-layout/page-numbers) and [Breaks](/features/page-layout/breaks) show how Page Layout uses these nodes.

Footnotes and endnotes come from the Footnotes extension, which works with or without Page Layout. [Footnotes and endnotes](/conversion/v3/docx/elements/footnotes) says how they convert.

## Without Page Layout

An editor without Page Layout has no pages, so import keeps the page setup as [preserved content](/conversion/v3/docx/preserved-content), with a `preserved` warning for each type. Preserved content holds what the editor has no extension for, so export can write it back and Page Layout can show it later.

Each `sectionBreak` keeps its setup, headers and footers, and sits in the text where its Word section starts, the first one at the start of the document. Page numbers and note references stay in the text.

When you add Page Layout and load the saved document, it opens with its pages, headers and footers.

### Page breaks without Page Layout

`@tiptap-pro/extension-pagebreak`, which you install and add to the editor yourself, has a block `pageBreak` node, which import and export both use. A page break inside a paragraph then splits it, with the `pageBreak` between the halves.

An editor with no `pageBreak` or `columnBreak` node keeps each break in the text as preserved content, with a `preserved` warning. The preserved break is visible only with CSS of your own, such as the CSS in [Show preserved content](/conversion/v3/docx/preserved-content#show-preserved-content).

### Export without Page Layout

Without Page Layout, export writes one section from the `pageSize` and `pageMargins` options: A4 with 2.54cm top and bottom and 3.17cm side margins by default. [Page size and margins](/conversion/v3/docx/export#page-size-and-margins) shows the options. An editor without Page Layout has no headers or footers to export.

## Limits

These page settings don't convert, or change on the way:

- Word has one page color per document and no section text or accent colors, so export drops them, as [Page color](/conversion/v3/docx/page-layout/sections#page-color) says.
- Import starts an even or odd page section on the next page, with a warning, and a next-column section without one.
- Import leaves out the binding gutter, with `gutter-dropped`.
- Import reads a custom Word page number format as the default, without a warning.
- Export doesn't write a section's note settings.
- Fields other than page numbers import as plain text.
- Word keeps one header and footer distance per section, and one odd and even switch per file.
- Soft page breaks don't import, because they are Word's layout, not content.
- No export option changes the paper of a document that starts with a `sectionBreak`, such as an imported one.
