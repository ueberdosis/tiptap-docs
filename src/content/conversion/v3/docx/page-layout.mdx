With [Page Layout](/features/page-layout/getting-started/overview), the extension that shows the document on pages, a Word file keeps its pages when it moves between Word and the editor. Its sections, page setup, headers, footers, page numbers and page breaks import into the document, and export writes them back to the `.docx` file.

A section is a part of the document with its own page setup, as in Word: paper size, orientation, margins, section columns, page numbering, headers and footers. Section columns are Word's Layout > Columns, which flow a section's text through several columns.

## How the document holds the pages

Page Layout keeps the page setup of a Word file in the document, as nodes. So it is saved with the document, and export finds it there:

| Node                       | What it holds                                                          |
| -------------------------- | ---------------------------------------------------------------------- |
| `sectionBreak`             | The start of a section, with the section's page setup                  |
| `pageFurniture`            | One header or footer of a section, inside the section's `sectionBreak` |
| `pageNumber`               | A page number that keeps counting, in a header, a footer or the body   |
| `pageBreak`, `columnBreak` | A break the user inserted, inside its paragraph                        |

[Sections](/features/page-layout/sections), [Page format](/features/page-layout/page-format), [Section columns](/features/page-layout/section-columns), [Header and footer](/features/page-layout/header-and-footer), [Page numbers](/features/page-layout/page-numbers) and [Breaks](/features/page-layout/breaks) show how Page Layout uses these nodes.

Footnotes and endnotes are notes of the Footnotes extension, with or without Page Layout. [Footnotes and endnotes](/conversion/v3/docx/elements/footnotes) says how they convert.

## Import a Word file

With Page Layout, the import writes the file into the Source Document, the document Page Layout lays out on pages. Its sections, page setup, headers, footers and notes go in with it.

Without `onImport`, the import writes the document when it arrives. With `onImport`, it writes when you call `setEditorContent()`, as [Import DOCX](/conversion/v3/docx/import) shows:

```ts
editor.commands.importDocx({
  file,
  onImport: (context) => {
    if (context.error) return
    context.setEditorContent()
  },
})
```

The write is one step, so one undo takes the import back. The caret lands at the start of the body. The Tracked Changes extension doesn't record the write as a suggestion, even while it records the user's edits.

A Page Layout editor that has not mounted, such as a headless one in a Node.js script, has no pages. Its own document is then the Source Document, and the import writes the sections, headers and notes into it as it does in a mounted editor.

Before it writes, the import fits the document to the schema of the Source Document, so the schema can't make an import fail. Content that the editor has no extension for is kept, as [Content the editor cannot show](/conversion/v3/docx/preserved-content) explains.

### Tell the import apart from an edit

Each write of the import carries the `DOCX_IMPORT_META` transaction meta, set to `true`, so your extensions can tell an import apart from the user's edits.

With Page Layout, read it in `onUpdate`. The editor's `transaction` event carries the transactions of the pages, and only `update` carries the import's own transaction:

```ts
import { Extension } from '@tiptap/core'
import { DOCX_IMPORT_META } from '@tiptap-pro/extension-import-docx'

const LogImports = Extension.create({
  name: 'logImports',
  onUpdate({ transaction }) {
    if (transaction.getMeta(DOCX_IMPORT_META)) console.log('DOCX imported')
  },
})
```

### When the import fails

`setEditorContent()` throws when Page Layout's engine was destroyed before the write. It also throws when a newer import has started. An error thrown inside `onImport`, including by `setEditorContent()`, reaches `onError`. [Warnings and errors](/conversion/v3/reference/warnings-and-errors) lists every error of an import.

## Export a Page Layout document

Export reads the page setup from the document, so the file gets each section's page, headers and footers without any export option. Export starts a Word section at each `sectionBreak`. [Sections and page setup](#sections-and-page-setup) and [Headers and footers](#headers-and-footers) say what Word gets for each of them.

The `pageSize` and `pageMargins` options have no effect with Page Layout, because they set the page of an editor without it, as [Page size and margins](/conversion/v3/docx/export#page-size-and-margins) shows.

### Export the first section on other paper

The `pageSetup` option replaces the editor's page setup for one export. It takes the page setup in CSS pixels, as [Page format](/features/page-layout/page-format) describes, and its `format` needs the `id`, the `width` and the `height`. This example sets US Letter with one-inch margins:

```ts
editor.commands.exportDocx({
  pageSetup: {
    format: { id: 'Letter', width: 816, height: 1056 },
    orientation: 'portrait',
    margins: { top: 96, right: 96, bottom: 96, left: 96 },
  },
})
```

The editor's page setup, and so `pageSetup`, applies only to the content before the first `sectionBreak`. An imported document starts with a `sectionBreak`. A document written in the editor may not, and its content before the first `sectionBreak` is its first section.

Each later section keeps the page of the `sectionBreak` that starts it. To put the whole document on Letter, change every section in the editor with Page Layout's `setSectionSetup()` command, as [Sections](/features/page-layout/sections) shows.

A pageless document, which Page Layout shows as one continuous column, exports on A4 pages with one-inch margins and no warning, unless you pass `pageSetup`. This is a known limit that is being fixed.

## Sections and page setup

Each Word section becomes a Page Layout section with its own page setup, and export writes each section back as a Word section.

### Import sections

Import puts a `sectionBreak` node in front of each section, the first at the very start of the document. Each one holds its section's setup in these attributes, with lengths in pixels:

| Setting              | Attributes                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------- |
| Paper size           | `formatId`, `pageWidth`, `pageHeight`                                                        |
| Orientation          | `orientation`                                                                                |
| Margins              | `marginTop`, `marginRight`, `marginBottom`, `marginLeft`                                     |
| Section break kind   | `kind`: `nextPage` or `continuous`                                                           |
| Section columns      | `columnCount`, `columnGaps`, `columnWidths`, `columnRule` for the line between columns       |
| Page numbering       | `pageNumbering`, an object with `format`, `start` and `chapter`                              |
| Different first page | `differentFirstPage`                                                                         |
| Note settings        | `notePlacement`, `footnoteNumbering`, `endnoteNumbering`: where notes go, format and restart |
| Page color           | `themePage`, a hex color such as `#fff8e8`, on the first section only                        |
| Header and footer    | See [Headers and footers](#headers-and-footers)                                              |

`columnGaps` holds the space after each column but the last, in pixels. `columnWidths` holds one share of the text width for each column, such as `[0.6, 0.4]`, so the widths follow the paper size.

A section's columns are settings on its `sectionBreak`. Its blocks aren't wrapped in column nodes, and Page Layout flows them through the columns, as [Section columns](/features/page-layout/section-columns) explains.

`pageNumbering.format` is the number format, such as `decimal` or `lowerRoman`. `start` is the first page number, or `null` to continue from the section before.

`pageNumbering.chapter` is Word's "Include chapter number": `null`, or an object with the heading `level` that starts a chapter and the `separator` between the chapter and page numbers, such as `hyphen` for `2-5`.

A body without a section setup imports as one US Letter section with 1-inch margins. An "at least" top or bottom margin imports as a fixed margin of the same size.

Some settings change to ones Page Layout has, each with a warning:

- A section that starts on an even or odd page starts on the next page, with `section-start-even-odd`.
- The binding gutter of the margins is left out, with `gutter-dropped`.
- A section break inside a table is ignored, with `section-in-table-cell`, because Word doesn't end a section there.

Two more settings change without a warning, which is a known limit that is being fixed:

- A section that starts in the next column starts on the next page.
- A custom Word number format, such as `001`, imports as the default for its kind: decimal for pages and footnotes, lowercase Roman for endnotes.

### Export sections

Export writes the settings of the [Import sections](#import-sections) table back, with two exceptions. The note settings don't export, and the page color follows the rules in [Page color](#page-color).

The paper size comes from the format's width and height, and the chapter number keeps its `separator`. A `nextPage` section starts a new page. A `continuous` one stays on the sheet and takes the paper of the section before it, because paper can't change halfway down a sheet.

Page numbers use the section's number format, such as `decimal` or `lowerRoman`. A format without an exact Word match is written as the closest one, with an `unsupported` warning.

### Page color

Word has one page color for the whole document. Import puts it on the first section as `themePage` when Word stores a hex color. A page color of `auto`, or a theme color without a hex value, gives none.

Export writes the `themePage` of the first section, such as one from an import. To set the color yourself, pass `pageColor` to the command of an editor set up as in [Export DOCX](/conversion/v3/docx/export). `pageColor` wins over `themePage`:

```ts
editor.commands.exportDocx({ pageColor: '#fff8e8' })
```

Export drops a different page color on a later section, with an `unsupported` warning. It also drops the text and accent colors Page Layout can give a section, `themeText` and `themeAccent`, with one `unsupported` warning for each kind. Word prints the page color only with its print background setting on.

## Headers and footers

Word's headers and footers convert in both directions, one set for each section, and page number fields stay live fields.

### Import headers and footers

Import puts each section's headers and footers into its `sectionBreak`, as `pageFurniture` nodes with a `zone` of `header` or `footer` and one of these `slot` values:

| `slot`    | Shows on                                                       |
| --------- | -------------------------------------------------------------- |
| `default` | Every page, or the odd pages when odd and even pages differ    |
| `first`   | The first page of the section, when `differentFirstPage` is on |
| `even`    | The even pages, when `differentOddEven` is on                  |

The `sectionBreak` also carries `differentFirstPage`, `differentOddEven`, and the distance of the header and footer from the page edge as `headerOffset` and `footerOffset`, in pixels. Import gives each `sectionBreak` an `id`: `sec-1` for the first section, `sec-2` for the second, and so on.

A Word section set to "Link to Previous" gets no header or footer of its own, and shows the one of the section before it. When several sections use the same header or footer in the file, each of them gets its own copy.

Word's page number fields, `PAGE`, `NUMPAGES` and `SECTIONPAGES`, become `pageNumber` nodes in headers, footers and the body, so they keep counting. Other fields, such as dates, import as the text Word last showed and no longer update.

### Export headers and footers

Export reads the headers and footers from the `pageFurniture` nodes of each section's `sectionBreak`. Headers and footers hold rich content, such as tables and images, and convert like the body. Their content comes from the page setup, so no export option sets it.

- A section can have a `default`, `first` and `even` version of its header and of its footer.
- A section without its own version uses the previous section's.
- A section can use another section's version instead. Its `headerDefaultLink`, `headerFirstLink`, `headerEvenLink` or matching `footer…Link` attribute then holds the `id` of that section's `sectionBreak`, such as `sec-1`.
- `differentFirstPage` exports for each section on its own.
- Word has one odd and even switch for the whole file. Export turns it on when any section has `differentOddEven`. A section without it then gets its `default` version on the even pages too.

The header and footer distance comes from each section, 1.25cm by default. A `pageFurniture` node can set a distance of its own in `offset`. When the versions a section shows have different distances, export uses the section's distance, with an `unsupported` warning, because Word keeps one per section.

A `pageNumber` node exports as a live Word field, which its `kind` picks. [Page numbers](/features/page-layout/page-numbers#a-page-number-in-a-header-or-footer) shows how to add one:

| `kind`         | Word field                         |
| -------------- | ---------------------------------- |
| `page`         | The page number                    |
| `pages`        | The number of pages                |
| `sectionPages` | The number of pages in the section |

### Format headers and footers

`headerFooterOverrides` formats headers and footers differently from the body, with the same override fields, such as `paragraphOverrides`. A field you leave out uses the body's value. [Export styles and fonts](/conversion/v3/docx/export-styles#header-and-footer-formatting) lists the fields. The example runs on an editor set up as in [Export DOCX](/conversion/v3/docx/export):

```ts
editor.commands.exportDocx({
  headerFooterOverrides: { paragraphOverrides: { spacing: { after: 0 } } },
})
```

## Page breaks and column breaks

A page break the user inserted in Word imports as a `pageBreak` node and exports back as a Word page break. A column break converts the same way, as a `columnBreak` node. Page Layout has both as inline nodes, with the `insertPageBreak` command, as [Breaks](/features/page-layout/breaks) shows.

Import keeps a page break inside its paragraph, where Word has it:

```json
{
  "type": "paragraph",
  "content": [{ "type": "text", "text": "End of part one" }, { "type": "pageBreak" }]
}
```

A paragraph set to start on a new page, directly or by its style, gets a `pageBreak` at its start. A page break in a table cell stays in the cell's paragraph.

Import doesn't read the soft page breaks Word saves from its last layout, because they are Word's layout, not content.

On export, a `pageBreak` inside a paragraph writes the break at that place. A `pageBreak` between blocks exports as a paragraph with a Word page break. A `columnBreak` exports as a Word column break.

## Without Page Layout

An editor without Page Layout has no pages, so import keeps the page setup as [preserved content](/conversion/v3/docx/preserved-content), with a `preserved` warning for each type.

Each `sectionBreak` keeps its setup, headers and footers, and sits in the text where its Word section starts, the first one at the start of the document. Page numbers and note references stay in the text.

When you add Page Layout and load the saved document, it opens with its pages, headers and footers.

### Page breaks without Page Layout

`@tiptap-pro/extension-pagebreak` has a block `pageBreak` node, which import and export both use. A page break inside a paragraph then splits it, with the `pageBreak` between the halves.

An editor with no `pageBreak` or `columnBreak` node keeps each break in the text as preserved content, with a `preserved` warning.

The preserved break is visible only with CSS of your own, such as the CSS in [Content the editor cannot show](/conversion/v3/docx/preserved-content). `editor.getText()` returns a space for it, so the words around it stay apart.

### Export without Page Layout

Without Page Layout, export writes one section from the `pageSize` and `pageMargins` options: A4 with 2.54cm top and bottom and 3.17cm side margins by default. [Page size and margins](/conversion/v3/docx/export#page-size-and-margins) shows the options. An editor without Page Layout has no headers or footers to export.

## Limits

These page settings don't convert, or change on the way:

- Word has one page color per document and no section text or accent colors, so export drops them, as [Page color](#page-color) says.
- Import starts an even or odd page section on the next page, with a warning, and a next-column section without one.
- Import leaves out the binding gutter, with `gutter-dropped`.
- Import reads a custom Word page number format as the default, without a warning.
- Export doesn't write a section's note settings.
- Fields other than page numbers import as plain text.
- Word keeps one header and footer distance per section, and one odd and even switch per file.
- Soft page breaks don't import, because they are Word's layout, not content.
- A pageless document exports on A4 pages with one-inch margins, unless you pass `pageSetup`.
