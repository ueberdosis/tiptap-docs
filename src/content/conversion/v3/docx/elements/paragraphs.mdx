A Word paragraph imports as a `paragraph` node, and export writes it back as a Word paragraph. Its alignment, spacing, indents and line spacing travel as attributes on the node, and tabs, quotes, line breaks, horizontal rules and code convert with it.

Headings and the Word styles that decide a paragraph's node type are on [Headings and Word styles](/conversion/v3/docx/elements/headings-and-styles).

## What you need

`StarterKit` from `@tiptap/starter-kit` has the nodes, but alignment and line spacing need two more extensions:

| Element                                          | Extension                                                                                      | Node, mark or attribute                                                                 |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Paragraphs                                       | `Paragraph` from `StarterKit`                                                                  | `paragraph`                                                                             |
| Blockquotes, horizontal rules, hard breaks, code | `Blockquote`, `HorizontalRule`, `HardBreak`, `CodeBlock` and the `code` mark from `StarterKit` | `blockquote`, `horizontalRule`, `hardBreak`, `codeBlock`, the `code` mark               |
| Text alignment                                   | `TextAlign` from `@tiptap/extension-text-align`, with `types`                                  | `textAlign`                                                                             |
| Line spacing                                     | `LineHeight` from `@tiptap/extension-text-style`, with `types`                                 | `lineHeight`                                                                            |
| Spacing, indents, Word's keep settings           | No Tiptap extension. The editor keeps them in `preservedAttrs`.                                | `spacingBefore`, `indent` and the others in [Import](#spacing-indents-and-line-spacing) |
| Tabs                                             | None, because a tab imports as plain text                                                      | Text                                                                                    |

`TextAlign` defines `textAlign` on the node types you list in its `types` option, which is empty by default. `LineHeight` defines `lineHeight` on the types in its `types` option, which is `['textStyle']` by default. So list `paragraph` and `heading` in both.

`TextStyleKit` adds `LineHeight` with the other text style extensions of [Text formatting](/conversion/v3/docx/elements/text-formatting), and takes its options under `lineHeight`:

```ts
import StarterKit from '@tiptap/starter-kit'
import TextAlign from '@tiptap/extension-text-align'
import { TextStyleKit } from '@tiptap/extension-text-style'

const extensions = [
  StarterKit,
  TextStyleKit.configure({ lineHeight: { types: ['textStyle', 'paragraph', 'heading'] } }),
  TextAlign.configure({ types: ['heading', 'paragraph'] }),
]
```

Without one of the nodes or the `textStyle` mark, import keeps that content as preserved content, with a `preserved` warning, until you add the extension. [Content the editor cannot show](/conversion/v3/docx/preserved-content) explains it.

When no extension in the editor defines an attribute, import keeps it in the node's `preservedAttrs` attribute, which the ImportDocx extension adds itself. The editor doesn't show such an attribute, and export still writes it to the `.docx` file:

- **Without `TextAlign`**, the editor shows every paragraph with its default alignment. The alignment comes back when you add `TextAlign`.
- **Spacing and indents** have no Tiptap extension, so the editor shows the spacing of its own CSS, without indents, until you add the extension in [Show spacing and indents](#show-spacing-and-indents).
- **Word's keep settings**, "Keep with next" and "Keep lines together", have no Tiptap extension either. They change nothing on screen.

## Import

Import sets each paragraph's formatting as attributes on the node and as marks on its text. Which node type a paragraph becomes depends on its Word style, as [Node types from Word styles](/conversion/v3/docx/elements/headings-and-styles#node-types-from-word-styles) shows.

### Spacing, indents and line spacing

Import sets these attributes on a `paragraph` or `heading` node when Word has a value for them:

| Attribute                       | Word setting                                                                                           | Value                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `spacingBefore`, `spacingAfter` | Space before and after                                                                                 | Pixels                                               |
| `lineHeight`                    | Line spacing                                                                                           | A multiple such as `1.5`, or a length such as `18pt` |
| `indent`, `indentRight`         | Left and right indent                                                                                  | Pixels                                               |
| `firstLineIndent`               | First line indent. A hanging indent is negative.                                                       | Pixels                                               |
| `contextualSpacing`             | Don't add space between paragraphs of the same style                                                   | `true`                                               |
| `keepNext`, `keepLines`         | Keep with next, keep lines together                                                                    | `true`                                               |
| `fontSize`                      | Font size of the paragraph mark, the ¶ at its end, which sets the height of an empty paragraph in Word | A pixel string such as `16px`                        |

Import converts the values like this:

- Word stores spacing and indents in twips, a twentieth of a point. Import converts them to whole pixels.
- A line spacing in multiples becomes a number such as `1.5`. Import leaves out a value within 0.01 of single spacing.
- A line spacing of "at least" or "exactly" becomes a length in points, such as `18pt`.
- `contextualSpacing`, `keepNext` and `keepLines` are `true` when Word turns them on.

This is a justified paragraph with space after it and a line spacing of 1.15, in an editor with the extensions from [What you need](#what-you-need). `spacingAfter` sits in `preservedAttrs`, because no extension in that editor defines it. `preservedAttrs` holds the kept attributes under its own `attrs` key:

```json
{
  "type": "paragraph",
  "attrs": {
    "textAlign": "justify",
    "lineHeight": 1.15,
    "preservedAttrs": { "attrs": { "spacingAfter": 13 } }
  },
  "content": [{ "type": "text", "text": "This is a paragraph." }]
}
```

### Show spacing and indents

To show a kept attribute, define it in an extension of your own. The node then holds it as a real attribute, and export reads it the same way. This extension shows the spacing and indents of each paragraph and heading, and `parseHTML` keeps the space before when the user pastes HTML. Add it to the editor's `extensions`:

```ts
import { Extension } from '@tiptap/core'

// Draws one attribute as one CSS property, in pixels.
function pixelStyle(name: string, property: string) {
  return {
    default: null,
    renderHTML: (attributes: Record<string, unknown>) =>
      attributes[name] == null ? {} : { style: `${property}: ${attributes[name]}px` },
  }
}

const ParagraphSpacing = Extension.create({
  name: 'paragraphSpacing',
  addGlobalAttributes() {
    return [
      {
        types: ['paragraph', 'heading'],
        attributes: {
          spacingBefore: {
            ...pixelStyle('spacingBefore', 'margin-top'),
            parseHTML: (element) => parseFloat(element.style.marginTop) || null,
          },
          spacingAfter: pixelStyle('spacingAfter', 'margin-bottom'),
          indent: pixelStyle('indent', 'margin-left'),
          indentRight: pixelStyle('indentRight', 'margin-right'),
          firstLineIndent: pixelStyle('firstLineIndent', 'text-indent'),
        },
      },
    ]
  },
})
```

Tiptap joins the `style` values of several attributes on one element. A negative `firstLineIndent`, a hanging indent, draws as a negative `text-indent`.

### Text alignment

Import reads the alignment of each Word paragraph and sets `textAlign` on the `paragraph` or `heading` node:

| Word alignment | `textAlign` |
| -------------- | ----------- |
| Left           | `left`      |
| Center         | `center`    |
| Right          | `right`     |
| Both           | `justify`   |

Any other Word value, such as `start` or `end`, passes through as it is. `TextAlign` draws only the values in its `alignments` option, by default the four in the table, so such a paragraph shows with the default alignment, and export ignores the value. When a paragraph sets no alignment, the alignment of its named style applies.

### Blockquotes, rules and breaks

A paragraph in Word's Quote style, whatever the capitalization of the style name, imports as a `blockquote` with one `paragraph`. Its inline formatting stays. Each Quote paragraph becomes a `blockquote` of its own, so three in a row import as three blockquotes.

Import turns these Word shapes into a `horizontalRule` node:

- The rule from Word's horizontal line command.
- A simple line shape, or a rectangle shape without text.

A shape that holds text isn't a rule. A rule drawn inside a paragraph imports after the paragraph's text.

A line break inside a paragraph imports as a `hardBreak`, also when the file stores it as a carriage return. A page or column break isn't a hard break, as [Page breaks and column breaks](/conversion/v3/docx/page-layout/sections#page-breaks-and-column-breaks) describes.

No Word style imports as a `codeBlock`, so a code block comes back from Word as a paragraph. Text in Word's Code character style imports with the `code` mark.

### Tabs

Each tab in a Word run becomes four spaces in the text, at the start of a paragraph and in the middle of one. A positional tab (Word's `w:ptab`) imports as four spaces too.

The editor shows those spaces because Tiptap's default editor styles set `white-space: break-spaces`, which keeps runs of spaces. If your CSS sets `white-space: normal` on paragraphs, the spaces collapse, and an indent made with a tab looks like it vanished.

## Export

Export writes each node as a Word paragraph in a fixed Word style, with the attributes of the node. [Word styles from your editor's CSS](/conversion/v3/docx/elements/headings-and-styles#word-styles-from-your-editors-css) lists the styles and where their look comes from.

### Paragraph and heading attributes

Export reads the attributes from [Spacing, indents and line spacing](#spacing-indents-and-line-spacing) on each `paragraph` and `heading` node:

- A number is pixels. A string with a unit also works: `cm`, `mm`, `in`, `pt`, `pc` or `px`, such as `0.5in`.
- A negative `firstLineIndent` becomes a hanging indent.
- A `lineHeight` multiple such as `1.5` or `150%` becomes an "at least" line height of that many times the font size. Export ignores a multiple above `5`.
- A `lineHeight` length such as `24px`, `18pt` or `1cm` becomes an exact line height. For an `em` or `rem` value, export writes no line height, so the paragraph takes the one of its Word style.
- `keepNext` and `keepLines` become Word's "Keep with next" and "Keep lines together".

An empty paragraph exports as an empty Word paragraph, so a blank line keeps its space.

Export writes the `textAlign` values `left`, `center`, `right` and `justify` as the matching Word alignment. It ignores any other value, such as `start`, so the paragraph takes the alignment of its Word style.

### Right-to-left text

Export takes the text direction from your editor's CSS. When the editor renders its paragraphs right to left, for example with `direction: rtl` on the editor, export marks every paragraph in the file as right to left. Export doesn't detect a single paragraph with a direction of its own.

### Blockquotes, rules and code

Export writes each paragraph in a `blockquote` with the Quote style. A list or table in a blockquote is left out, with an `unsupported` warning for each.

A `horizontalRule` exports as a gray line across the text width. Only its spacing comes from your editor's CSS. A `hardBreak` exports as a line break.

A `codeBlock` exports as one paragraph in a Code Block style, Courier New on gray, with a line break for each newline. When the editor is mounted, the style takes your code block CSS, as [Export styles and fonts](/conversion/v3/docx/export-styles#match-your-editors-formatting) describes. Word has no language setting, so `language` is left out.

The `code` mark exports with Word's Code character style.

### Tab characters

Export writes a tab character in the text as a Word tab.

The `defaultTabStop` option sets the distance between Word's default tab stops, in twips, so `720` is half an inch. In this example, `editor` is an editor with `ExportDocx`, as [Export DOCX](/conversion/v3/docx/export) sets it up:

```ts
editor.commands.exportDocx({ defaultTabStop: 720 })
```

Without `defaultTabStop`, export uses the `tab-size` your editor's CSS renders.

## Limits

These limits concern paragraphs and their formatting:

- Import ignores paragraph borders and paragraph shading. Export writes paragraph borders only from the editor's CSS.
- A line spacing of "at least" imports as a length, so it exports as an exact line height. A line spacing in multiples, such as 1.5, exports as an "at least" line height, so it doesn't come back from a round trip as a multiple.
- The exported file doesn't match the editor pixel for pixel, because Word and the browser measure fonts and lines differently.
- Import drops hidden text without a warning. This is a known limit that is being fixed.
- Import ignores the right-to-left setting of Word paragraphs and runs. It keeps the text inside Word's bidirectional embedding elements (`w:dir` and `w:bdo`), which right-to-left documents use, but not the text direction they set.

Tabs have these limits:

- A Word tab doesn't come back from a round trip as a tab, because import turns it into four spaces and export writes those as spaces.
- Import doesn't read tab stops, so left, center, right, decimal and bar stops are lost. Export writes no tab stop positions from the document. The `paragraphOverrides` option can set `tabStops` for every paragraph, as [Export styles and fonts](/conversion/v3/docx/export-styles) shows.
- A positional tab loses its alignment, because it imports as four spaces.

Blockquotes and code blocks have these limits:

- A list or table inside a blockquote doesn't export.
- A `blockquote` with several paragraphs comes back from Word as one `blockquote` for each paragraph.
- A code block comes back from Word as a paragraph, without its `language`.
