Headings and the Word styles that decide a paragraph's node type are on [Headings and Word styles](/conversion/v3/docx/elements/headings-and-styles).

## What you need

`StarterKit` from `@tiptap/starter-kit` has the nodes, but alignment and line spacing need two more extensions:

| Element                                          | Extension                                                                                      | Node, mark or attribute                                                                 |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Paragraphs                                       | `Paragraph` from `StarterKit`                                                                  | `paragraph`                                                                             |
| Blockquotes, horizontal rules, hard breaks, code | `Blockquote`, `HorizontalRule`, `HardBreak`, `CodeBlock` and the `code` mark from `StarterKit` | `blockquote`, `horizontalRule`, `hardBreak`, `codeBlock`, the `code` mark               |
| Text alignment                                   | `TextAlign` from `@tiptap/extension-text-align`, with `types`                                  | `textAlign`                                                                             |
| Line spacing                                     | `LineHeight` from `@tiptap/extension-text-style`, with `types`                                 | `lineHeight`                                                                            |
| Spacing, indents, Word's keep settings           | None, kept in `preservedAttrs`                                                                 | `spacingBefore`, `indent` and the others in [Import](#spacing-indents-and-line-spacing) |
| Tabs                                             | None, a tab imports as text                                                                    | Text                                                                                    |

Both extensions add their attribute only to the node types in their `types` option. For `TextAlign` it is empty by default, for `LineHeight` it is `['textStyle']`. So list `paragraph` and `heading` in both.

`TextStyleKit`, from [Text formatting](/conversion/v3/docx/elements/text-formatting), includes `LineHeight` and takes its options under `lineHeight`:

```ts
import StarterKit from '@tiptap/starter-kit'
import TextAlign from '@tiptap/extension-text-align'
import { TextStyleKit } from '@tiptap/extension-text-style'

const extensions = [
  StarterKit,
  TextStyleKit.configure({ lineHeight: { types: ['textStyle', 'paragraph', 'heading'] } }),
  TextAlign.configure({ types: ['heading', 'paragraph'] }),
]
```

Without one of these nodes or the `textStyle` mark, import keeps that content as [preserved content](/conversion/v3/docx/preserved-content), with a `preserved` warning, until you add the extension.

When no extension defines an attribute, import keeps it in the node's `preservedAttrs`, which the ImportDocx extension adds itself. The editor doesn't show it, but export writes it back to the `.docx` file:

- **Without `TextAlign`**, every paragraph shows its default alignment until you add `TextAlign`.
- **Spacing and indents** have no Tiptap extension, so the editor shows the spacing of its own CSS and no indents. [Show spacing and indents](#show-spacing-and-indents) adds one.
- **Word's keep settings**, "Keep with next" and "Keep lines together", have no Tiptap extension either and change nothing on screen.

## Import

Import sets a paragraph's formatting as node attributes and as marks on its text. Its Word style decides the [node type](/conversion/v3/docx/elements/headings-and-styles#node-types-from-word-styles).

### Spacing, indents and line spacing

Import sets these attributes on a `paragraph` or `heading` when Word has a value:

| Attribute                       | Word setting                                                                 | Value                                                |
| ------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| `spacingBefore`, `spacingAfter` | Space before and after                                                       | Pixels                                               |
| `lineHeight`                    | Line spacing                                                                 | A multiple such as `1.5`, or a length such as `18pt` |
| `indent`, `indentRight`         | Left and right indent                                                        | Pixels                                               |
| `firstLineIndent`               | First line indent. A hanging indent is negative.                             | Pixels                                               |
| `contextualSpacing`             | Don't add space between paragraphs of the same style                         | `true`                                               |
| `keepNext`, `keepLines`         | Keep with next, keep lines together                                          | `true`                                               |
| `fontSize`                      | Size of the paragraph mark ¶, which sets an empty paragraph's height in Word | A pixel string such as `16px`                        |

Import converts the values like this:

- Spacing and indents become whole pixels. Word stores them in twips, a twentieth of a point.
- A line spacing in multiples becomes a number such as `1.5`. Import leaves out a value within 0.01 of single spacing.
- A line spacing of "at least" or "exactly" becomes a length in points, such as `18pt`.

This justified paragraph has space after it and a line spacing of 1.15, imported into an editor with the extensions from [What you need](#what-you-need). No extension there defines `spacingAfter`, so it sits under the `attrs` key of `preservedAttrs`:

```json
{
  "type": "paragraph",
  "attrs": {
    "textAlign": "justify",
    "lineHeight": 1.15,
    "preservedAttrs": { "attrs": { "spacingAfter": 13 } }
  },
  "content": [{ "type": "text", "text": "This is a paragraph." }]
}
```

### Show spacing and indents

To show a kept attribute, define it in an extension of your own. The node then holds it as a real attribute, and export reads it from there.

This extension draws the spacing and indents of each paragraph and heading. Its `parseHTML` keeps the space before when the user pastes HTML. Add it to the editor's `extensions`:

```ts
import { Extension } from '@tiptap/core'

// Draws one attribute as one CSS property, in pixels.
function pixelStyle(name: string, property: string) {
  return {
    default: null,
    renderHTML: (attributes: Record<string, unknown>) =>
      attributes[name] == null ? {} : { style: `${property}: ${attributes[name]}px` },
  }
}

const ParagraphSpacing = Extension.create({
  name: 'paragraphSpacing',
  addGlobalAttributes() {
    return [
      {
        types: ['paragraph', 'heading'],
        attributes: {
          spacingBefore: {
            ...pixelStyle('spacingBefore', 'margin-top'),
            parseHTML: (element) => parseFloat(element.style.marginTop) || null,
          },
          spacingAfter: pixelStyle('spacingAfter', 'margin-bottom'),
          indent: pixelStyle('indent', 'margin-left'),
          indentRight: pixelStyle('indentRight', 'margin-right'),
          firstLineIndent: pixelStyle('firstLineIndent', 'text-indent'),
        },
      },
    ]
  },
})
```

Tiptap joins the `style` values of several attributes on one element. A negative `firstLineIndent`, a hanging indent, draws as a negative `text-indent`.

### Text alignment

Import reads the alignment of each Word paragraph and sets `textAlign` on the `paragraph` or `heading` node:

| Word alignment | `textAlign` |
| -------------- | ----------- |
| Left           | `left`      |
| Center         | `center`    |
| Right          | `right`     |
| Both           | `justify`   |

When a paragraph sets no alignment, the alignment of its named style applies.

Any other Word value, such as `start` or `end`, passes through unchanged. `TextAlign` draws only the values in its `alignments` option, by default the four in the table. So such a paragraph shows the default alignment, and export ignores the value.

### Blockquotes, rules and breaks

A paragraph in Word's Quote style, in any capitalization, imports as a `blockquote` with one `paragraph` and keeps its inline formatting. Each Quote paragraph becomes its own `blockquote`, so three in a row import as three.

Import turns Word's horizontal line, a simple line shape and a rectangle without text into a `horizontalRule` node. A shape that holds text isn't a rule. A rule drawn inside a paragraph imports after the paragraph's text.

A line break inside a paragraph imports as a `hardBreak`, also when the file stores it as a carriage return. A page or column break isn't a hard break, see [Page breaks and column breaks](/conversion/v3/docx/elements/sections#page-breaks-and-column-breaks).

No Word style imports as a `codeBlock`, so a code block comes back from Word as a paragraph. Text in Word's Code character style imports with the `code` mark.

### Tabs

Each tab imports as four spaces, wherever it sits in the paragraph. So does a positional tab (Word's `w:ptab`).

Tiptap's default editor styles keep runs of spaces with `white-space: break-spaces`. If your CSS sets `white-space: normal` on paragraphs, the spaces collapse and an indent made with a tab seems to vanish.

## Export

Export writes each node as a Word paragraph in a fixed Word style, with the node's attributes. [Word styles from your editor's CSS](/conversion/v3/docx/elements/headings-and-styles#word-styles-from-your-editors-css) lists the styles and where their look comes from.

### Paragraph and heading attributes

Export reads the [spacing, indent and line spacing attributes](#spacing-indents-and-line-spacing) of each `paragraph` and `heading`:

- A number is pixels. A string with a unit also works: `cm`, `mm`, `in`, `pt`, `pc` or `px`, such as `0.5in`.
- A negative `firstLineIndent` becomes a hanging indent.
- A `lineHeight` multiple such as `1.5` or `150%` becomes an "at least" line height of that many times the font size. Export ignores a multiple above `5`.
- A `lineHeight` length such as `24px`, `18pt` or `1cm` becomes an exact line height. For an `em` or `rem` value, export writes none, so the line height of the Word style applies.
- `keepNext` and `keepLines` become Word's "Keep with next" and "Keep lines together".

An empty paragraph exports as an empty Word paragraph, so a blank line keeps its space.

Export writes the `textAlign` values `left`, `center`, `right` and `justify` as the matching Word alignment. It ignores any other value, such as `start`, so the alignment of the Word style applies.

### Right-to-left text

Export takes the text direction from your editor's CSS. When the editor renders right to left, for example with `direction: rtl` on the editor, export marks every paragraph as right to left. It doesn't detect a single paragraph with its own direction.

### Blockquotes, rules and code

Export writes each paragraph in a `blockquote` with the Quote style. A list or table in a blockquote is left out, with an `unsupported` warning for each.

A `horizontalRule` exports as a gray line across the text width. Only its spacing comes from your editor's CSS. A `hardBreak` exports as a line break.

A `codeBlock` exports as one paragraph in a Code Block style, Courier New on gray, with a line break for each newline. When the editor is mounted, the style takes your [code block CSS](/conversion/v3/docx/export/styles-and-fonts#match-your-editors-formatting). Word has no language setting, so `language` is left out.

The `code` mark exports with Word's Code character style.

### Tab characters

Export writes a tab character in the text as a Word tab.

The `defaultTabStop` option sets the distance between Word's default tab stops in twips, so `720` is half an inch. The example needs an editor with `ExportDocx`, as [Export DOCX](/conversion/v3/docx/export) sets it up:

```ts
editor.commands.exportDocx({ defaultTabStop: 720 })
```

Without `defaultTabStop`, export uses the `tab-size` your editor's CSS renders.

## Limits

Paragraphs and their formatting have these limits:

- Import ignores paragraph borders and shading. Export writes paragraph borders only from the editor's CSS.
- A line spacing of "at least" imports as a length, so it exports as an exact line height.
- A line spacing in multiples, such as 1.5, exports as an "at least" line height, so it doesn't come back from a round trip as a multiple.
- The exported file doesn't match the editor pixel for pixel, because Word and the browser measure fonts and lines differently.
- Import drops hidden text without a warning, a known limit that is being fixed.
- Import ignores the right-to-left setting of Word paragraphs and runs. It keeps the text inside Word's bidirectional embedding elements, `w:dir` and `w:bdo`, but not the direction they set.

Tabs have these limits:

- A Word tab doesn't come back from a round trip as a tab, because import turns it into four spaces and export writes those as spaces.
- Import doesn't read tab stops, so left, center, right, decimal and bar stops are lost. Export writes no tab stops from the document. The `paragraphOverrides` option of [Export styles and fonts](/conversion/v3/docx/export/styles-and-fonts) can set `tabStops` for every paragraph.
- A positional tab loses its alignment, because it imports as four spaces.

Blockquotes and code blocks have these limits:

- A list or table inside a blockquote doesn't export.
- A `blockquote` of several paragraphs comes back as one for each paragraph.
- A code block comes back as a paragraph, without its `language`.
