Comments convert in both directions as threads of the Comments extension, with their replies and resolved state.

On import, you can also accept or reject every tracked change instead of keeping it as a suggestion.

## What you need

Each kind of review content needs its extension in the editor:

| Word content    | Extension                                                                                                                                    | In the document                                                                                                                      |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Tracked changes | Tracked Changes, `@tiptap-pro/extension-tracked-changes`, as [Track changes in your editor](/tracked-changes/getting-started/overview) shows | A `suggestion` mark on changed text, and node attributes on changed content without text, such as an image                           |
| Comments        | Comments, `@tiptap-pro/extension-comments`, as [Integrate Comments into your app](/comments/getting-started/overview) shows                  | An `inlineThread` mark on commented text, or a `blockThread` node around several blocks, both with the thread id in `data-thread-id` |

In the JSON, the thread id attribute of both is named `data-thread-id`, as in the HTML, not `threadId`.

Without the Tracked Changes extension, import accepts every change by default, as [Import tracked changes](#import-tracked-changes) explains.

Without the Comments extension, import keeps `inlineThread` and `blockThread` as [preserved content](/conversion/v3/docx/preserved-content), with a `preserved` warning. The marks come back once you add the extension, and the threads still arrive in `onImport`.

## Import tracked changes

The `trackedChanges` option decides what import does with each change. Set it in `ImportDocx.configure()` or on one `importDocx()` call, which wins. In this example, `CONVERSION_TOKEN` stands for your Conversion token, `editor` for your editor and `file` for a `.docx` file the user picked:

```ts
import { ImportDocx } from '@tiptap-pro/extension-import-docx'

ImportDocx.configure({
  token: CONVERSION_TOKEN,
  trackedChanges: 'auto',
})

editor.commands.importDocx({ file, trackedChanges: 'preserve' })
```

The option takes these modes:

| Mode         | What happens                                                                         |
| ------------ | ------------------------------------------------------------------------------------ |
| `'preserve'` | Insertions and deletions become suggestions, with their author and date              |
| `'accept'`   | Insertions become ordinary text, and deletions are removed                           |
| `'reject'`   | Deletions come back as ordinary text, and insertions are removed                     |
| `'auto'`     | The default. `'preserve'` when the editor has the `suggestion` mark, else `'accept'` |

An editor without the `suggestion` mark would show deleted text as ordinary text. In such an editor:

- **`'auto'`** accepts the changes.
- **`'preserve'`** keeps the suggestions as preserved content, with a `preserved` warning, until you add the extension.

If you renamed the mark with `prosemirrorMarks`, as [Custom nodes on import](/conversion/v3/docx/custom-nodes/import) shows, `'auto'` looks for the new name.

When the Tracked Changes extension is recording the user's edits, it doesn't record the import as one large suggestion, and one undo takes the import back.

### Where suggestions are kept

Import keeps suggestions in the body, table cells included. It accepts every change in headers, footers, comments, footnotes and endnotes, so an insertion in a header arrives as ordinary text, and a deletion there is gone.

### What a suggestion looks like

Text with a change carries a `suggestion` mark:

```json
{
  "type": "text",
  "text": "brave ",
  "marks": [
    {
      "type": "suggestion",
      "attrs": {
        "id": "docx-suggestion-1",
        "type": "add",
        "userId": "ada lovelace",
        "createdAt": "2026-07-27T10:00:00Z",
        "updatedAt": "2026-07-27T10:00:00Z",
        "userMetadata": { "name": "Ada Lovelace" }
      }
    }
  ]
}
```

`type` is `add` for an insertion and `delete` for a deletion. A replacement in Word imports as a deletion followed by an insertion. Neighboring changes of the same type by the same reviewer merge into one suggestion.

Word knows a reviewer by display name only. `userMetadata.name` holds it, and `userId` is the name lowercased, trimmed and with single spaces. So two reviewers with one display name share a `userId`. A change without a name gets `anonymous` as `userId` and `null` as `userMetadata`.

An inserted or deleted image, or other content without text, carries the change as node attributes instead of a mark: `suggestionId`, `suggestionType`, `suggestionUserId`, `suggestionCreatedAt`, `suggestionUpdatedAt` and `suggestionUserMetadata`.

## Import comments

Import turns Word comments into comment threads with their replies and resolved state, and marks the commented text. `onImport` receives the threads in `commentThreads`, which is empty when the file has no comments.

Import doesn't build a comments UI, and the Comments extension keeps its threads on the Document Server, the Tiptap server that stores collaborative documents:

- **With live threads**, import creates the threads there, so the editor shows them as threads, as [Live threads](#live-threads) describes.
- **Without live threads**, the text keeps its marks with the ids from the file, and `commentThreads` is the only copy of the threads. Store it with the document if you need the comments later, for example to write them into an export, as [Export comments](#export-comments) shows.

In this example, `editor` is an editor set up as in [Import DOCX](/conversion/v3/docx/import), and `file` is a `.docx` file the user picked:

```ts
editor.commands.importDocx({
  file,
  onImport: (context) => {
    if (context.error) return
    context.setEditorContent()
    saveThreads(context.commentThreads)
  },
})
```

`context.error` is set when the import failed. `saveThreads` stands for your app's own storage.

### Thread fields

Each thread has an `id`, which matches `data-thread-id` in the content, a `resolved` flag and its `messages`. The root comment comes first, then the replies by date. A message has these fields:

| Field  | Holds                                                                            |
| ------ | -------------------------------------------------------------------------------- |
| `body` | The comment as Tiptap JSON                                                       |
| `data` | The `author` and, when the file has them, the `initials` and the dates           |
| `wId`  | The comment's id in the Word file                                                |
| `id`   | The comment's id on the Document Server, only with [live threads](#live-threads) |

[Review an import before it applies](/conversion/v3/docx/import/review#comment-threads) lists every field of `ImportedCommentThread`.

### Live threads

Import creates the threads on the Document Server when all of these are true:

- The editor has a collaboration provider with a document name, passed as the `provider` option of the Comments, CollaborationCaret or CollaborationCursor extension.
- Your Conversion token, the `token` of `ImportDocx.configure()`, also allows `Documents:Write` for that document.
- The file has comments.

The token lists the action in its `permissions`, with the document name as `resource`. For a document named `report-2026`, the permissions from [Get a Conversion token](/conversion/v3/getting-started/install#3-get-a-conversion-token) become:

```js
permissions: [
  { action: 'Convert:Import:Docx', resource: '*' },
  { action: 'Documents:Write', resource: 'report-2026' },
]
```

A `resource` of `'*'` allows every document, so one token covers all of them. Scope it to the documents a user may change, as [Authenticate and authorize in Collaboration](/collaboration/getting-started/authenticate) explains.

Import then returns the Document Server's thread ids, and the content uses them. Otherwise the ids come from the file, and the import still succeeds. When the token was the reason, `context.logs.warn`, the service's warning messages in the `onImport` context, says so.

### Import the same file again

With live threads, each comment an import creates records its Word id. When you import a file again into the same collaborative document, import compares it with earlier Word imports:

- A comment that is already there isn't created twice.
- A changed comment updates its thread.
- A new comment becomes a new thread.
- A comment gone from the file is removed, if a Word import created it.

Import doesn't remove a comment the user wrote in the editor. Keep one collaborative document for each `.docx` file, so an import is compared only with that file's comments.

## Export tracked changes

Export writes text with a `suggestion` mark as a Word revision. `replaceInsertion` and `replaceDeletion` are the two halves of a replacement made in the editor:

| Mark `type`                 | Word revision |
| --------------------------- | ------------- |
| `add`, `replaceInsertion`   | Insertion     |
| `delete`, `replaceDeletion` | Deletion      |

The revision's name is `userMetadata.name`, then `userId`, then `anonymous`. Its date is `createdAt`, and a missing or invalid date becomes `1970-01-01T00:00:00Z`.

A change to a whole block, such as an image, is read from its `suggestionType`, `suggestionUserId`, `suggestionUserMetadata` and `suggestionCreatedAt` attributes. A table cell or row that carries these attributes itself exports as an inserted or deleted cell or row.

Some suggestions don't become revisions:

- **A `markChange` suggestion**, a formatting change, is skipped.
- **An unknown `type`** is ignored.
- **A pending node type change**, such as a paragraph suggested as a heading, fails the export before any request. Such a node has a `suggestionNodeTypeChange` attribute, so accept or reject that suggestion first, as [A pending node type change fails the export](/conversion/v3/reference/errors#a-pending-node-type-change-fails-the-export) shows.

### Export a clean copy

Export has no option that accepts or rejects the changes. To export a clean copy, run `acceptAllSuggestions()` or `rejectAllSuggestions()` before the export.

These commands change the editor's document, not only the export. If the user should keep reviewing, undo them once `onCompleteExport`, the callback that receives the file, has it. In this example, `save` stands for your app's code that stores the file:

```ts
editor.commands.acceptAllSuggestions()
editor.commands.exportDocx({
  onCompleteExport: (file) => {
    editor.commands.undo()
    save(file)
  },
})
```

## Export comments

Each comment thread becomes a Word comment on the same text, with its replies in order, its resolved state, and the name, initials and date of each message. A comment body converts like the document, so its formatting stays, but a table in it is left out.

Export reads the threads from:

- **The Comments extension's provider**, resolved threads included and archived ones left out.
- **The `comments` option**, for threads of your own. Pass `comments: { threads }` on the command or in `ExportDocx.configure()` of an editor set up as in [Export DOCX](/conversion/v3/docx/export). Each thread is a [`SourceThread`](/conversion/v3/docx/export-options/types#sourcethread).

The `comments` option wins over the provider, so export then reads no threads from it. An empty list, `{ threads: [] }`, exports no comments. Without a provider, and without the `comments` option, export writes no comments, and the text stays.

### Stored threads

This example turns the `commentThreads` stored after an import, here `storedThreads`, back into threads for the export.

A message has an `id` only with live threads, so the example builds one when it is missing. An imported thread has no resolve date, so a resolved thread gets the time of the export:

```ts
const threads = storedThreads.map((thread) => ({
  id: thread.id,
  resolvedAt: thread.resolved ? new Date().toISOString() : null,
  comments: thread.messages.map((message, index) => ({
    id: message.id ?? `${thread.id}-${index}`,
    content: message.body,
    data: { ...message.data, originalWId: message.wId },
  })),
}))

editor.commands.exportDocx({ comments: { threads } })
```

`originalWId` gives the exported comment the Word id it was imported with. So when you import that file into the same collaborative document again, import finds the thread it already created.

## Limits

Review content converts with these limits:

- Formatting changes don't convert in either direction.
- A paragraph split or joined while Word tracked changes imports in its final form, without a suggestion.
- Import doesn't read Word's tracked moves, and gives no warning, so the moved text may be missing. Check a moved passage before you rely on it. This is a known limit that is being fixed.
- Changes in headers, footers, comments, footnotes and endnotes import as accepted.
- A pending node type change blocks the export.
- A comment is tied to the text it marks, so deleting that text removes the mark.
- Live threads need a collaboration provider and write access to the document.
- A table in a comment body doesn't export.
