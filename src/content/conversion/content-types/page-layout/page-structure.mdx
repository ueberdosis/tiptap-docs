Page structure covers the elements that control how content flows across pages: page breaks, sections, page size, margins, and page numbers. Page breaks round-trip through the pipeline. Other page structure properties are partially supported.

## What you need

- **Extensions:** `@tiptap-pro/extension-pagebreak` (not in StarterKit) and [`Pages`](/pages/getting-started/overview) for paginated layout
- **Export options:** `pageSize` and `pageMargins` on the export extension or REST API
- **Integration paths:** Import and export work identically via both the [editor extension](/conversion/import/docx/editor-extension) and [REST API](/conversion/import/docx/rest-api). Both export paths accept `pageSize` and `pageMargins`.

## Support overview

| Feature | Import | Editor | Export |
| --- | --- | --- | --- |
| Page breaks | Supported | Supported (PageBreak) | Supported |
| Page size | Supported with Pages (the import editor extension applies it) | Supported ([Pages](/pages/getting-started/overview)) | Supported (configurable) |
| Page margins | Supported with Pages (the import editor extension applies it) | Supported (Pages) | Supported (configurable) |
| Sections | Partial (column configuration is extracted and applied) | Not supported | Single section only |
| Page numbers | Supported (PAGE/NUMPAGES → `{page}`/`{numpages}` tokens, see [below](#page-numbers)) | Supported (via header/footer) | Supported. The editor extension and the REST API emit `{page}`/`{total}` tokens in headers/footers as live `PAGE`/`NUMPAGES` fields. The REST API also accepts `{numpages}`. |
| Columns | Supported on import (columns/column nodes created) | Not supported | Not supported |

## Page breaks

Page breaks fully round-trip through the pipeline. See the dedicated [Page breaks](/conversion/content-types/page-layout/page-breaks) page for details.

## Page size and margins

The parser reads the page size and margins from the DOCX section properties. With the [Pages extension](/pages/getting-started/overview) registered, the import editor extension applies them to the editor with `setPageFormat`. Without Pages, the editor has no page, so they are not used.

The [Pages extension](/pages/getting-started/overview) provides paginated layout with configurable page size and margins. For configuration details, see the [Page format guide](/pages/core-concepts/page-format).

The export extension accepts `pageSize` and `pageMargins` options:

```ts
ExportDocx.configure({
  pageSize: {
    width: '21.0cm',
    height: '29.7cm',
  },
  pageMargins: {
    top: '2.54cm',
    bottom: '2.54cm',
    left: '3.17cm',
    right: '3.17cm',
  },
})
```

Values accept CSS-style units: `cm`, `in`, `pt`, `pc`, `mm`, `px`. A number, or a string without a unit such as `'12240'`, is read as twips. Defaults produce an A4 page with standard Word margins.

<Callout variant="info" title="The export reads the Pages page format">
  With the Pages extension installed, the export extension takes the page size and body margins
  from the Pages `pageFormat`, and the header and footer distances from Pages. A `pageMargins`
  value replaces the Pages margins for the sides it sets. A `pageSize` value replaces the Pages
  page size, and a width or height it leaves out falls back to 21cm or 29.7cm.
</Callout>

## Sections

Word documents can have multiple sections, each with its own page layout properties (size, orientation, margins, columns, headers/footers). Section support in the conversion pipeline is partial:

- **Import:** Section boundaries are used to detect multi-column layouts. Multi-column sections are wrapped in `columns`/`column` Tiptap nodes. Other section-level properties (size, orientation, margins) are parsed but not applied.
- **Editor:** Tiptap does not have a section concept, but column nodes are rendered natively.
- **Export:** Produces a single section. Mixed portrait/landscape or multi-section documents cannot be created.

## Page numbers

Page numbers in Word are field codes (`PAGE`, `NUMPAGES`) inside headers and footers. The import translates these into canonical text tokens (`{page}` for `PAGE` and `{numpages}` for `NUMPAGES`) when the Pages extension is installed (or you opt in explicitly: `placeholders: true` (or `{ page?, total? }`) on the [editor command](/conversion/import/docx/editor-extension#page-number-fields), or the `placeholders={}` form field on the [REST API](/conversion/import/docx/rest-api#page-number-fields)). On export, the [editor extension](/conversion/export/docx/editor-extension) emits `{page}` / `{total}` tokens in header/footer content as live `PAGE` / `NUMPAGES` fields so Word recalculates them on print or repagination. The REST API export does the same translation; pass `placeholders: false` to keep the tokens as literal text.

The Pages extension recognizes `{page}` and `{total}` by default; it does **not** recognize `{numpages}`. To make Word's `NUMPAGES` field render live in the editor preview after an import, configure `Pages.configure({ placeholders: { total: 'numpages' } })`. See [DOCX import → page-number fields](/conversion/import/docx/editor-extension#page-number-fields).

## What round-trips

| Feature | Round-trips? | Notes |
| --- | --- | --- |
| Page breaks | Yes | Requires `@tiptap-pro/extension-pagebreak` |
| Page size | Yes, with Pages | The import editor extension applies the DOCX page size to Pages, and the export editor extension writes the Pages page size |
| Page margins | Yes, with Pages | The import editor extension applies the DOCX margins to Pages, and the export editor extension writes the Pages margins |
| Sections | Partial | Column configuration survives; other section properties do not |
| Page numbers | Yes          | Word `PAGE` / `NUMPAGES` ↔ `{page}` / `{numpages}` (Pages canonical name for total is `{total}`; configure `placeholders: { total: 'numpages' }` to bridge). The REST API recognizes `{numpages}` on export without that setting. |
| Columns | Partial | Import creates column nodes; export does not yet write them back |
