When exporting to `DOCX`, you can define custom styles that will be applied to the exported document. This is useful when you want to have a consistent look and feel across your documents.

<ExportStylesGuide />

## Which style wins

With the `exportDocx` command, the export combines the styles in this order, from lowest to highest priority:

1. The default styles of the export and of the `docx` library.
2. The [computed styles](/conversion/export/docx/computed-styles) that the export reads from the editor. `computedStyles: false` turns them off.
3. The Word styles that [`cssStyles`](/conversion/export/docx/css-to-docx) creates from CSS rules.
4. `styleOverrides`, including its `default` entries. `styleOverrides.default.heading1` wins over an `h1` rule in `cssStyles`.
5. The element overrides, such as `paragraphOverrides` and `textRunOverrides`.
6. Formatting that the document stores, such as a `textStyle` color mark or the `textAlign` of a paragraph. `tableOverrides` and `imageOverrides` are the exception: they win over the borders and cell margins that a table node stores, and over the size that an image node stores.

A higher level replaces a lower level only for the properties it sets. `styleOverrides` merges property by property, also inside nested objects. A `paragraphStyles` item `{ id: 'Normal', name: 'Normal', paragraph: { indent: { left: 900 } } }` changes the left indent of body paragraphs and keeps the right and first line indents that the export read from the editor. [Which value wins](/conversion/export/docx/computed-styles#which-value-wins) on the computed styles page explains how deep each option merges.

A `styleOverrides` option on the `exportDocx` command replaces the whole `styleOverrides` object of `ExportDocx.configure()`.

### Document defaults

`styleOverrides.default.document` sets the defaults of the whole document. When the export reads the editor's styles, these values also replace what it read for body paragraphs, the `Normal` style. Other styles, such as headings, keep the values that the export read for them. They take your document defaults only for the properties that the export did not read for them.

```ts
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

ExportDocx.configure({
  styleOverrides: {
    // Body paragraphs use Verdana. Headings keep the font that the export read for them.
    default: { document: { run: { font: 'Verdana' } } },
  },
})
```

To change every text run, use `textRunOverrides` instead.

### False values and parsed JSON

- For `pageBreakBefore: false` or `wordWrap: false` in a paragraph style, the export writes a reset into the style, so the style turns off a setting it inherits. The `docx` library alone leaves these false values out.
- The export ignores `__proto__` keys in `styleOverrides`, so you can pass styles that you parsed from JSON.

## Native DOCX options

The exported `Docx` namespace and raw element overrides use native `docx` 9.12 options.

### RTL alignment

Set `bidirectional: true` and `alignment` together in the raw paragraph options. Use `LEFT` for text on the physical left; native docx handles the left/right mapping:

```ts
import { Docx, ExportDocx } from '@tiptap-pro/extension-export-docx'

ExportDocx.configure({
  paragraphOverrides: {
    bidirectional: true,
    alignment: Docx.AlignmentType.LEFT,
  },
})
```

This applies to both static overrides and callbacks. A paragraph node's explicit `textAlign` takes precedence over the override.

### Table widths and default styles

With `Docx.WidthType.PERCENTAGE`, numeric `size: 50` means 50 percent. Use a percentage string such as `size: '33.33%'` to preserve finer precision; native numeric percentages round to increments of 0.02 percent.

Native documents include `Normal` and `TableNormal` styles and infer omitted grid and cell widths. The exporter also supplies its paragraph and list styles, which you can customize through `styleOverrides`.

## Per-node overrides with a function

Every element override — `paragraphOverrides`, `textRunOverrides`, `tableOverrides`, `tableRowOverrides`, `tableCellOverrides`, and `imageOverrides` — accepts a function in addition to a static object. The function receives the node currently being converted and returns the overrides for that node, so you can vary overrides per node based on its attributes. The object form keeps working unchanged, so this is a drop-in addition.

```ts
ExportDocx.configure({
  onCompleteExport: (result) => {
    /* ... */
  },
  // `node` is the image node currently being converted, including its `attrs`.
  imageOverrides: (node) => ({
    // Carry the editor's alt text into Word's accessibility metadata.
    altText: { name: node.attrs?.alt, description: node.attrs?.alt },
    // Derive the rendered size from the dimensions set on the node.
    transformation: {
      width: Number(node.attrs?.width),
      height: Number(node.attrs?.height),
    },
  }),
  // The function receives the matching node for every override type.
  paragraphOverrides: (node) => ({
    keepNext: node.attrs?.keepWithNext === true,
  }),
})
```

The value returned by the function is applied exactly like the static object — with the same precedence as the object form of that override. Returning an empty object leaves every default in place for that node.

<Callout title="Function form in other exports">
  A function can't travel in a JSON request, so the REST API can't take the function form. The
  [REST API](/conversion/export/docx/rest-api) page lists the element overrides it accepts. PDF,
  ODT, DOC and EPUB exports create the file through
  `ExportDocx` when it is registered, so they use its element overrides in both forms.
</Callout>
