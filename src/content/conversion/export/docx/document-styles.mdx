Since v0.33.0, the DOCX export follows the CSS your editor renders with. Export in the browser and the file gets the fonts, sizes, colors, spacing, list indents and table borders your users see in the editor. There's no `styleOverrides` config to keep in sync with your stylesheet.

This is the `documentStyles` option, and it's on by default.

## Turn it off

Set `documentStyles: false` on the extension to turn it off for every export, or pass it to the command to turn it off once:

```js
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

// Every export
ExportDocx.configure({
  onCompleteExport: (result) => saveAs(result, 'document.docx'),
  documentStyles: false,
})

// One export
editor.chain().exportDocx({ documentStyles: false }).run()
```

The command wins over the extension config, so `exportDocx({ documentStyles: true })` still uses your CSS when the extension turns it off. Without it, you get the package's [default styles](/conversion/export/docx/styles#tiptaps-export-default-styles).

## When it applies

Only the `exportDocx` command uses your CSS, and only in the browser with an editor that's on the page and visible:

| Where you export                                                                      | What happens                                                                                        |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `editor.commands.exportDocx()` in the browser                                         | Uses the editor's CSS                                                                               |
| On a server, in a headless editor, or with an editor that's destroyed or off the page | Uses the default styles, without a warning                                                          |
| With an editor hidden by `display: none`, on itself or on a parent                    | Warns with [`document-styles-failed`](#warnings) and uses the default styles                        |
| With the standalone `exportDocx()` function                                           | Uses the default styles. See [Use the standalone function](#use-the-standalone-exportdocx-function) |

So the same document exports with different styles on a server and in the browser. If you need both to match, set `documentStyles: false` in the browser.

## What carries over

The export uses your styles as the browser renders them. Rules scoped to your editor, like `.tiptap p` or `.my-app .tiptap h1`, apply, and CSS variables, `calc()`, inherited values and stylesheets from other origins all work.

| In the editor                                         | In the exported file                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Body text                                             | The `Normal` style: font, size, color, line height, spacing, alignment, indent, borders and background |
| `h1` to `h6`                                          | The `Heading 1` to `Heading 6` styles                                                                  |
| `blockquote`                                          | The `Quote` style, with the quote's margin, padding, border and background                             |
| `hr`                                                  | The space above and below the rule                                                                     |
| Bullet, ordered and task lists, up to nine levels     | Indents, marker text, marker font and the ordered counter style. See [Lists](#lists)                   |
| `a`                                                   | The `Hyperlink` style                                                                                  |
| `code`                                                | The `Code` style                                                                                       |
| `strong`, `em`, `u`, `s`, `mark`, `sub`, `sup`        | Their color, font, background and other text styles                                                    |
| `table`, `th`, `td`                                   | Table width, alignment and borders, cell padding, cell background, vertical alignment and cell text    |
| The background behind the editor                      | The page color. See [Page color](#page-color)                                                          |
| `direction: rtl` on the editor                        | Right-to-left paragraphs and text throughout the document                                              |
| The nearest `lang` attribute, often the one on `html` | The proofing language of the text                                                                      |
| `tab-size`                                            | The default tab stop                                                                                   |

These CSS properties carry over: `font-family`, `font-size`, `font-weight`, `font-style`, `color`, `background-color`, `text-decoration`, `letter-spacing`, `text-transform: uppercase`, small caps, `font-stretch`, `vertical-align`, `text-align`, `text-indent`, `line-height`, `margin`, `padding`, `border`, `break-before`, `break-after` and `break-inside`. A `font-weight` of 600 or more exports as bold.

### Fonts

Word gets the first named family in each `font-family` stack, even when the browser falls back to a later one because the first didn't load. Generic families map to common Word fonts: `serif` to Times New Roman, `sans-serif` and `system-ui` to Arial, and `monospace` to Courier New. If a reader doesn't have the font installed, Word swaps in another one, unless you [embed it](/conversion/export/docx/fonts).

### Line height

Line spacing exports as a minimum line height. A line with a taller image or inline element still grows, the same way it does in the editor.

## How your options combine with your CSS

Everything you configure sits on top of your CSS. From lowest to highest precedence, the export's styles come from:

1. The package's default styles
2. The editor's CSS
3. [`cssStyles`](/conversion/export/docx/css-to-docx)
4. [`styleOverrides`](/conversion/export/docx/styles)

`styleOverrides` merges property by property, so a style you only partly override keeps the rest of your CSS. A `Normal` style that sets only `font`, for example, keeps the font size from your CSS.

That merge reaches into nested objects too. Line spacing from your CSS uses `lineRule: 'atLeast'`, so if you set `spacing.line` on a style, set `lineRule` as well. Otherwise `line: 276` means a minimum line height of 13.8pt, not 1.15 lines:

```js
ExportDocx.configure({
  onCompleteExport: (result) => saveAs(result, 'document.docx'),
  styleOverrides: {
    paragraphStyles: [
      {
        id: 'Normal',
        name: 'Normal',
        // 1.15 lines. 'auto' makes `line` a multiple of the line height.
        paragraph: { spacing: { line: 276, lineRule: 'auto' } },
      },
    ],
  },
})
```

Your element overrides, `listLevels`, `pageColor` and `defaultTabStop` win over your CSS too:

- In `paragraphOverrides`, `textRunOverrides`, `tableOverrides`, `tableRowOverrides` and `tableCellOverrides`, each top-level key you set replaces the whole value for that key. So `spacing: { after: 200 }` replaces the whole `spacing` object.
- `listLevels` applies per list kind and nesting depth. See [List positions with `listLevels`](/conversion/export/docx/ordered-list-numbering#list-positions-with-listlevels).
- `pageColor` and `defaultTabStop` replace what your CSS gives.

Content that sets its own formatting keeps it. A table with its own width, borders or cell margins, like one that came from a DOCX import, exports with those instead of what your CSS says.

<Callout title="Styles on marks and table cells" variant="hint">
  The styles your CSS gives to marks such as `strong` or `mark`, and to text in table cells, apply
  to that text directly. A `styleOverrides` change to `Normal` doesn't change them, so it won't
  recolor bold text your CSS colors. Use `textRunOverrides` for that.
</Callout>

```js
ExportDocx.configure({
  onCompleteExport: (result) => saveAs(result, 'document.docx'),
  // Bold text gets this color instead of the one from your CSS.
  // Other runs return nothing and keep their styles.
  textRunOverrides: (node) =>
    node.marks?.some((mark) => mark.type === 'bold') ? { color: '1F2937' } : {},
})
```

## Lists

List items keep the indent they have in the editor, unless a [numbering format](/conversion/export/docx/ordered-list-numbering) or [`listLevels`](/conversion/export/docx/ordered-list-numbering#list-positions-with-listlevels) sets the indent for that depth.

Markers follow your CSS too. `disc`, `circle` and `square` become `•`, `◦` and `▪`, a quoted string in `list-style-type` or `::marker` content stays as written, and `none` hides the marker. An ordered list keeps its `list-style-type` counter for `decimal`, `decimal-leading-zero`, `lower-alpha`, `upper-alpha`, `lower-roman` and `upper-roman`. The marker's font, size, color and weight follow `::marker`.

A list that names a numbering format keeps that format's counter and marker text. Its marker font comes from the format, or from your CSS if the format doesn't set one. Task lists only take their indent from your CSS.

## Page color

Every page gets the background your editor shows. In a light theme that's usually white. In a dark color scheme the exported page is dark and the text light, the way your users saw it.

To export without a page color, pass `pageColor: 'transparent'`. A color of your own also works, and it wins over the one from your CSS:

```js
ExportDocx.configure({
  onCompleteExport: (result) => saveAs(result, 'document.docx'),
  pageColor: 'transparent',
})
```

Word shows the page color on screen but leaves it out when printing, unless the reader changes that setting. See [Page background color](/conversion/export/docx/page-layout#page-background-color).

## Limitations

- Margins on the table wrapper, `div.tableWrapper`, don't export. Word tables have no margin.
- The gap between a list marker and its text stays at Word's quarter inch, or less when the list indents less, whatever your CSS says. Lists that use a numbering format are the exception.
- All list items share one text style in Word, taken from your top-level bullet list items.
- Page size, margins and columns don't come from your CSS. Set [`pageSize` and `pageMargins`](/conversion/export/docx/page-layout), or use the [Pages extension](/pages/getting-started/overview), which the export takes the page setup from.
- A horizontal rule keeps a fixed color and thickness. Only the space around it follows your CSS.
- Margins around a block image, and the gap between two headings in a row, don't export.
- Code block styling doesn't export.
- Styles on a single node don't export. That covers a class or attribute on one paragraph, a node view, and your custom node types. Use [custom nodes](/conversion/export/docx/custom-nodes), the [custom nodes DSL](/conversion/export/docx/custom-nodes-dsl) or the [element overrides](/conversion/export/docx/styles#element-overrides) for those.
- Text direction applies to the whole document. A direction set on a single paragraph doesn't export.
- The export uses the styles that apply when it runs, at the editor's current width and color scheme.

## Use the standalone `exportDocx()` function

The standalone `exportDocx()` function doesn't use your CSS on its own. To get the same styles with it in the browser, pass it the result of `createExportStyles`:

```js
import { createExportStyles, exportDocx } from '@tiptap-pro/extension-export-docx'

const content = editor.getJSON()
const styles = await createExportStyles({ editor, document: content })
const file = await exportDocx({ document: content, exportType: 'blob', ...styles })
```

`createExportStyles` returns `styleOverrides`, the element overrides, `listLevels`, `pageColor` and `defaultTabStop`. If you pass any of those yourself, merge them with the returned values, or use the `exportDocx` command, which merges them for you.

Pass `genericFonts` to pick the Word font for a generic family, for example `genericFonts: { 'sans-serif': 'Calibri' }`. `createExportStyles` throws outside a browser, and when the editor is destroyed, off the page or hidden.

## Warnings

If the export can't use your CSS, it calls `onWarning` with the code `document-styles-failed` and finishes with the default styles. Without `onWarning`, the message goes to `console.warn`.

```js
ExportDocx.configure({
  onCompleteExport: (result) => saveAs(result, 'document.docx'),
  onWarning: (warning) => {
    if (warning.code === 'document-styles-failed') {
      console.warn(warning.message)
    }
  },
})
```

## PDF, ODT, DOC and EPUB

When `ExportDocx` is installed, PDF, ODT, DOC and EPUB exports follow your editor's CSS too. They don't have a `documentStyles` option of their own, so turn it off on `ExportDocx`:

```js
import { ExportDocx } from '@tiptap-pro/extension-export-docx'
import { ExportPdf } from '@tiptap-pro/extension-export-pdf'

const editor = new Editor({
  extensions: [
    // Other extensions ...
    ExportDocx.configure({ documentStyles: false }),
    ExportPdf.configure({ token: 'YOUR_TOKEN' }),
  ],
})
```

## Upgrading from v0.32 or earlier

Before v0.33.0, every export started from the package's default styles. After you upgrade, a browser export takes its fonts, colors, spacing, list indents, table borders and page color from your editor's CSS instead. Your `cssStyles` and `styleOverrides` still win. To keep the old output, set `documentStyles: false`.
