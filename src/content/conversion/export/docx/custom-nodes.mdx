One of the biggest advantages of the `@tiptap-pro/extension-export-docx` extension is the ability to define how custom nodes in your Tiptap schema should be rendered in DOCX.

This allows you to preserve application-specific content in the exported Word file.

<Callout variant="hint" title="Looking for the REST-compatible variant?">
  Functions can't be serialized over HTTP, so the function API on this page only works inside the
  editor extension. For a JSON-based equivalent that travels over REST and runs in both surfaces,
  see the [Custom-nodes DSL](/conversion/export/docx/custom-nodes-dsl).
</Callout>

## Export custom nodes to .docx

<CodeDemo isPro path="/Extensions/ExportDocxCustomNode" />

Pass an array of custom node definitions as `customNodes`, either to `ExportDocx.configure` or to the `exportDocx` command. Each definition specifies the node type and a render function.

<CustomNodeConversionGuide />

### Define the custom node render function

And we will define how the `Hintbox` custom node should be rendered in the exported document:

```ts
// Import the ExportDocx extension
import {
  convertTextNode,
  Docx,
  ExportDocx,
  lineHeightToDocx,
  pixelsToHalfPoints,
  pointsToTwips,
} from '@tiptap-pro/extension-export-docx'

const editor = new Editor({
  extensions: [
    // Other extensions ...
    ExportDocx.configure({
      onCompleteExport: (result) => {
        setIsLoading(false)
        const blob = new Blob([result], {
          type: 'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
        })
        const url = URL.createObjectURL(blob)
        const a = document.createElement('a')
        a.href = url
        a.download = 'export.docx'
        a.click()
        URL.revokeObjectURL(url)
      },
      exportType: 'blob',
      customNodes: [
        {
          type: 'hintbox',
          render: (node) => {
            // Here we define how our custom Hintbox node should be rendered in the DOCX.
            // Per the documentation, we should return a Docx node
            // that's either a Paragraph, an array of Paragraphs, a Table, a TextRun, an ExternalHyperlink, or null.
            return new Docx.Paragraph({
              children: node.content.map((content) => convertTextNode(content)),
              style: 'Hintbox', // Here we apply our custom style to the Paragraph node.
            })
          },
        },
      ], // Custom nodes
      styleOverrides: {
        paragraphStyles: [
          // Here we define our custom styles for our custom Hintbox node.
          {
            id: 'Hintbox',
            name: 'Hintbox',
            basedOn: 'Normal',
            next: 'Normal',
            quickFormat: false,
            run: {
              font: 'Aptos Light',
              size: pixelsToHalfPoints(16),
            },
            paragraph: {
              spacing: {
                before: pointsToTwips(12),
                after: pointsToTwips(12),
                line: lineHeightToDocx(1),
              },
              border: {
                // DOCX colors are in Hexadecimal without the leading #
                top: { style: Docx.BorderStyle.SINGLE, size: 1, color: 'b8d8ff', space: 5 },
                bottom: { style: Docx.BorderStyle.SINGLE, size: 1, color: 'b8d8ff', space: 5 },
                right: { style: Docx.BorderStyle.SINGLE, size: 1, color: 'b8d8ff', space: 5 },
                left: { style: Docx.BorderStyle.SINGLE, size: 1, color: 'b8d8ff', space: 5 },
              },
              shading: {
                type: Docx.ShadingType.SOLID,
                color: 'e6f3ff',
              },
            },
          },
        ],
      }, // Style overrides
    }),
    // Other extensions ...
  ],
  // Other editor settings ...
})
```

Then, at a later point in your application, you can export the editor content to a `DOCX` file:

```ts
editor.chain().exportDocx().run()
```

You can construct any supported `DOCX` elements in the `render` function using the `Docx` library classes (`Paragraph`, `TextRun`, `Table`, etc.) that are provided via the `Docx` import from the `@tiptap-pro/extension-export-docx` package.

The `render` function can also use the converters the package exports, such as `convertTable`. For a table node without cells, `convertTable` returns a table with one empty cell, because Word cannot open a table without cells. The export leaves that table out when `render` returns it. When `render` puts it inside a table cell of its own, the export keeps it with its empty cell.

See [Native DOCX options](/conversion/export/docx/styles#native-docx-options) for RTL alignment, percentage widths, and default styles.

## Custom nodes inside lists and quotes

The export calls `render` for a custom node wherever the node sits, also when it is a block inside a list item, a task item or a quote. A node there without a definition exports its text as a paragraph.

In these containers, a block node can return a run, such as a `TextRun`, instead of a paragraph. The export writes the run into a paragraph with the style and indent of the container, for example the `Quote` style in a quote, and with the alignment, indent and spacing attributes of the node. Paragraphs and tables that `render` returns stay as they are. The same applies to nodes that a [`customNodeDsl`](/conversion/export/docx/custom-nodes-dsl) rule renders.

A function-form `paragraphOverrides` runs once for the paragraph the export writes, and gets the custom node itself. Its context holds the paragraph style the container selects in `paragraphStyle`, such as `Quote` in a quote or `ListParagraph` in a task item.

When the custom node, or a block around it, is a [tracked change](/conversion/export/docx/tracked-changes), the export marks the run that `render` returns as that insertion or deletion. If `render` returns no run in this case, the export leaves its output out and writes the node's own text as a tracked paragraph, so Word can still accept or reject the change.

## Fit images to the page or table cell

An image that a custom node renders without `width` and `height` exports at its pixel size, so a large photo runs past the right margin in Word. The custom node can keep it inside the page.

`render` gets a second argument, `context`. Its `maxImageWidth` is the width of the page's text column in pixels, or the content width of the table cell the node is in. The content width is the cell width minus its left and right cell margins. Margins from `tableOverrides` count, margins from `tableCellOverrides` do not. Outside a table, list and quote indents are not subtracted. A table inside a list item or quote is narrower by that indent, and its cells pass on the narrower width. Inline custom nodes get the same value, also in a quote. `context` is `undefined` for a custom node inside a [`customNodeDsl`](/conversion/export/docx/custom-nodes-dsl) rule.

Pass it as `maxWidth` to `convertImage` or `convertImageRun`:

```ts
import { convertImage, ExportDocx } from '@tiptap-pro/extension-export-docx'

ExportDocx.configure({
  customNodes: [
    {
      type: 'photo',
      render: (node, context) => {
        const { src, width, height } = node.attrs ?? {}

        return convertImage({
          node: { type: 'image', attrs: { src, width, height } },
          maxWidth: context?.maxImageWidth,
        })
      },
    },
  ],
})
```

`maxWidth` only changes an image that has neither `width` nor `height`. A wider image shrinks to `maxWidth` and keeps its aspect ratio. An image with its own size, and `imageOverrides.transformation`, still win.

When the node lays out content around the image, use `convertImageRunWithSize`. It returns the image run together with the size it gets in the document (`{ imageRun, width, height }`, in pixels), or `null` for an image the export skipped. This example puts a caption under the image in a table as wide as the image:

```ts
import {
  convertImageRunWithSize,
  Docx,
  ExportDocx,
  pixelsToPoints,
  pointsToTwips,
} from '@tiptap-pro/extension-export-docx'

ExportDocx.configure({
  customNodes: [
    {
      type: 'figure',
      render: async (node, context) => {
        const { src, width, height } = node.attrs ?? {}
        const image = await convertImageRunWithSize({
          node: { type: 'image', attrs: { src, width, height } },
          maxWidth: context?.maxImageWidth,
        })
        if (!image) return null

        // Word measures table widths in twips.
        const tableWidth = Math.round(pointsToTwips(pixelsToPoints(image.width)))

        return new Docx.Table({
          // A fixed layout without cell margins keeps the table exactly as wide as the image.
          layout: Docx.TableLayoutType.FIXED,
          width: { size: tableWidth, type: Docx.WidthType.DXA },
          columnWidths: [tableWidth],
          margins: { top: 0, bottom: 0, left: 0, right: 0 },
          rows: [
            new Docx.TableRow({
              children: [
                new Docx.TableCell({
                  children: [
                    new Docx.Paragraph({ children: [image.imageRun] }),
                    new Docx.Paragraph({ text: node.attrs?.caption }),
                  ],
                }),
              ],
            }),
          ],
        })
      },
    },
  ],
})
```

Built-in `image` nodes fit the page without a custom node. An image without `width` and `height` that is wider than the room in its text column or table cell shrinks to fit. That room leaves out the side indents of the paragraph or list item that holds the image. With [computed styles](/conversion/export/docx/computed-styles), an image that the editor shows wider than that room shrinks too. A size you set with `imageOverrides` stays as it is.
