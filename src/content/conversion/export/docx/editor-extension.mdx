Use Tiptap’s `@tiptap-pro/extension-export-docx` to export the editor’s content as a `.docx` file. This extension works in any JavaScript environment, including server-side applications, due to the isomorphic nature of the `exportDocx` function.

You can also export via the [REST API](/conversion/export/docx/rest-api). Both paths use the same conversion library. The main differences:

|                       | Editor extension                                                                                                                                                                                                                                                                                     | REST API                                                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Runs in               | Your app (client or server-side)                                                                                                                                                                                                                                                                     | Tiptap cloud                                                                                  |
| Custom node rendering | Supported via [`customNodes`](/conversion/export/docx/custom-nodes) and [`customNodeDsl`](/conversion/export/docx/custom-nodes-dsl)                                                                                                                                                                 | Supported via [`customNodeDsl`](/conversion/export/docx/custom-nodes-dsl)\*                   |
| Element overrides     | [`paragraphOverrides`, `textRunOverrides`, `tableOverrides`, `tableRowOverrides`, `tableCellOverrides`, `imageOverrides`](/conversion/export/docx/styles#element-overrides), plus [`headerFooterOverrides`](/conversion/export/docx/styles#headerfooteroverrides) for header/footer-scoped overrides | Same fields as static objects, except `tableRowOverrides`\*                                   |
| Style overrides       | Supported                                                                                                                                                                                                                                                                                            | Supported                                                                                     |
| Headers and footers   | docx.js objects, Tiptap JSON converted with [`convertHeader` and `convertFooter`](/conversion/export/docx/headers-footers), or auto-extracted from Pages                                                                                                                                               | Plain text, stringified JSON, or a JSON object                                                |
| Footnotes             | Auto-extracted from [Pages footnotes](/pages/core-concepts/footnotes), or provided via the `footnotes` option                                                                                                                                                                                        | Provided via the [`footnotes` field](/conversion/export/docx/rest-api#footnotes-and-endnotes) |
| Endnotes              | Auto-extracted from [Pages endnotes](/pages/core-concepts/endnotes), or provided via the `endnotes` option                                                                                                                                                                                           | Provided via the [`endnotes` field](/conversion/export/docx/rest-api#footnotes-and-endnotes)  |

\* The REST API does not accept `customNodes` render functions or `tableRowOverrides`. Requests carrying them have those fields stripped during validation and the export proceeds with defaults. Use the editor extension if you need either.

Choose the REST API to export from your server without an editor. Use the editor extension when you need `customNodes` render functions, function-based overrides, `tableRowOverrides`, or full control over the output.

By default, the extension maps Tiptap nodes to DOCX elements. If your content includes custom nodes, configure their [export behavior](/conversion/export/docx/custom-nodes) to ensure they’re properly converted.

## Install the DOCX Export extension

The Conversion extensions are published in Tiptap’s private npm registry. Integrate the extensions by following the [private registry guide](/guides/pro-extensions).

Once done you can install and import the **Export DOCX** extension package

```bash
npm i @tiptap-pro/extension-export-docx
```

Using the export extension does not require any Tiptap Conversion credentials, since the conversion is handled right away in the extension. Only [automatic font embedding](/conversion/export/docx/fonts#automatic-embedding) needs a token, to convert WOFF2 fonts.

```js
import { ExportDocx } from '@tiptap-pro/extension-export-docx'
```

## Configuring the extension

The `ExportDocx` extension can be configured with an `ExportDocxOptions` (`object`) as an argument to the `configure` method with the following properties:

```ts
// Import the ExportDocx extension
import { Editor } from '@tiptap/core'
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

const editor = new Editor({
  extensions: [
    // Other extensions ...
    ExportDocx.configure({
      onCompleteExport: result => {}, // required
      onError: undefined, // optional. Default: undefined
      exportType: 'blob', // optional. Default: 'blob'
      computedStyles: true, // optional. Default: true
      customNodes: [], // optional. Default: []
      customNodeDsl: undefined, // optional. Default: undefined
      customNodeDslLimits: undefined, // optional. Default: undefined
      styleOverrides: {}, // optional. Default: {}
      cssStyles: undefined, // optional. Default: undefined
      paragraphOverrides: undefined, // optional. Default: undefined
      textRunOverrides: undefined, // optional. Default: undefined
      tableOverrides: undefined, // optional. Default: undefined
      tableRowOverrides: undefined, // optional. Default: undefined
      repeatTableHeaderRows: false, // optional. Default: false
      tableCellOverrides: undefined, // optional. Default: undefined
      imageOverrides: undefined, // optional. Default: undefined
      headerFooterOverrides: undefined, // optional. Default: undefined
      headers: undefined, // optional. Default: the Pages headers, if Pages is installed
      footers: undefined, // optional. Default: the Pages footers, if Pages is installed
      footnotes: undefined, // optional. Default: the Pages footnotes, if Pages is installed
      endnotes: undefined, // optional. Default: the Pages endnotes, if Pages is installed
      comments: undefined, // optional. Default: the threads of the comments provider
      pageSize: undefined, // optional. Default: the Pages page size, or A4
      pageMargins: undefined, // optional. Default: the Pages margins, or 2.54cm top and bottom, 3.17cm at the sides
      pageColor: undefined, // optional. Default: undefined
      defaultTabStop: undefined, // optional. Default: undefined
      numberingFormats: undefined, // optional. Default: undefined
      listLevels: undefined, // optional. Default: undefined
      fonts: undefined, // optional. Default: undefined
      embedFonts: false, // optional. Default: false
      appId: undefined, // optional. Default: undefined
      token: undefined, // optional. Default: undefined
      endpoint: undefined, // optional. Default: undefined
      region: 'eu', // optional. 'eu' or 'us'. Default: 'eu'
      onWarning: undefined, // optional. Default: undefined
      onImageError: 'skip', // optional. Default: 'skip'
    }),
    // Other extensions ...
  ],
  // Other editor settings ...
})
```

## Export a DOCX file

With the extension installed, you can convert your editor’s content to `.docx`.

Before diving into an example, let's take a look into the signature of the `exportDocx` method available in your editor's commands:

```ts
/**
 * Export the current document as a .docx file
 *
 * Notes: 'buffer' and 'stream' export types are only available in the server environment
 * as they use the Node Buffer and Stream APIs respectively
 *
 * @param options - Export options. An option left out uses the value from ExportDocx.configure
 * @example editor.commands.exportDocx({ onCompleteExport: result => {}, exportType: 'buffer' })
 */
exportDocx: (options?: ExportDocxCommandOptions) => ReturnType
```

The command returns `true` at once and runs the export in the background. It passes the file to `onCompleteExport`, or the error to `onError` when the export fails. It does not return the file.

The `exportDocx` command takes an optional `ExportDocxCommandOptions` object. It accepts every option of `ExportDocx.configure` from the [table above](#configuring-the-extension), and each one is optional. A value you pass replaces the configured value for this export only. `onCompleteExport` is required here only when you did not configure it.

Some options combine with other sources:

- `headers` and `footers` replace the configured value as a whole. `headers` stops the command from using the Pages headers, and `footers` the Pages footers. [See Where headers and footers come from](/conversion/export/docx/headers-footers#where-headers-and-footers-come-from)
- `numberingFormats` replaces the configured formats. The formats of the `OrderedListNumbering` extension are added either way, and a format you pass wins over one of them with the same `id`.
- `pageMargins` replaces the configured margins as a whole. With Pages, each margin you leave out keeps the Pages value.
- `computedStyles` and `documentStyles` from the command win over both values on the extension.

```js
// Import the ExportDocx extension
import { Editor } from '@tiptap/core'
import { ExportDocx } from '@tiptap-pro/extension-export-docx'

// Setup you editor
const editor = new Editor({
  extensions: [
    // Other extensions ...
    ExportDocx.configure({
      onCompleteExport: result => {}, // required
      exportType: 'blob', // optional. Default: 'blob'
      // Any other option from the table above
    }),
    // Other extensions ...
  ],
  // Other editor settings ...
})

// Declare some functions that will call the exportDocx method from your editor

function handleExportDocx() {
  // Call your editor's exportDocx method
  editor
    .chain()
    // Method call without any overrides
    // It will take the configuration set in the configure method
    .exportDocx()
    .run()
}

function handleExportDocxBase64() {
  // Call your editor's exportDocx method
  editor
    .chain()
    // Method call with some overrides
    .exportDocx({
      // Override the onCompleteExport callback to handle the override exported type
      onCompleteExport: result => {
        // Handle the exported file as a Base64 string
      },
      // Receive the error if the export fails
      onError: error => {
        console.error(error)
      },
      // Override the export type
      exportType: 'base64',
    })
    .run()
}

// Call those functions at any point in your application
handleExportDocx()
handleExportDocxBase64()
```

### How it works

The above example runs entirely in the browser, generating a DOCX Blob via the ExportDocx extension since it's the default value for the `exportType` as we haven't override it. We then programmatically download the file. You can adjust this logic, for instance, to send the blob to a server instead of downloading.

| Parameter        | Description                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| onCompleteExport | When the conversion completes, we will get the `result` of the conversion as the main and only argument to the callback function which, in this case, it would be a `Blob` since we've declared that we wanted this type in the `exportType` within the `options` parameter. You can then handle it however you prefer, e.g. prompting a file download, like we showcased in the example above. |
| exportType       | We're using the default `blob` so the conversion returns a `Blob`.                                                                                                                                                                                                                                                                                                                              |
| customNodes      | We won't provide any custom node mapping since we are not providing any custom nodes.                                                                                                                                                                                                                                                                                                           |
| styleOverrides   | We won't provide any style overrides. The export uses the styles it reads from the editor with [computed styles](/conversion/export/docx/computed-styles), on top of its own Word defaults.                                                                                                                                                                                                       |

### What the command exports

- The command exports the document as it is when the command runs. In a chain, this includes the edits that earlier commands in the same chain made. The command reads the editor's styles after the chain is applied.
- When you call the command, it also takes the Pages headers, footers and notes, the comment threads and the registered numbering formats. Edits to the document after the call do not reach the file.
- The export still finishes when you call `editor.destroy()` before it is done. If it is still reading the editor's styles, it reads them at once, before the editor view goes away.
- `editor.can().exportDocx()` returns `true` without exporting and without reading styles.

## Server-side export

For applications requiring complex document generation or to reduce client-side bundle size, you can export `.docx` files in your the server.

In order to do so, you'd need to import the `exportDocx` function from the `@tiptap-pro/extension-export-docx` package, pass it your Tiptap JSON content, and return the resulting conversion to the client.

Let's first take a look into the `exportDocx` function signature:

```ts
/**
 * Export the current document as a .docx file
 *
 * Notes: 'buffer' and 'stream' export types are only available in the server environment
 * as they use the Node Buffer and Stream APIs respectively
 *
 * @param options.document - The JSON representation of the document
 * @param options.exportType - The type of export to perform
 * @param options.customNodes - Custom node definitions
 * @param options.styleOverrides - Style overrides for the exported document
 * @example exportDocx({ document: editor.getJSON(), exportType: 'blob', customNodes: [], styleOverrides: {} })
 */
declare function exportDocx(options: {
  document: JSONContent
  exportType: 'buffer' | 'string' | 'base64' | 'blob' | 'stream'
  customNodes: CustomNode[]
  styleOverrides: IStylesOptions
  // Every other option of ExportDocx.configure, except onCompleteExport,
  // onError, computedStyles and documentStyles
}): Promise<Buffer | string | Blob | Stream>
```

The `exportDocx` function returns the file in the type that `exportType` names. Always pass `exportType`, because the function has no default for it and fails without it. TypeScript also expects `customNodes` and `styleOverrides`.

The function has no editor, so it does not read computed styles, Pages headers, footers and notes, comment threads or registered numbering formats. Pass them as options. To export the styles of an editor in the browser, see the [computed styles API](/conversion/export/docx/computed-styles-api).

Here you have a simple example using `Express` and `@tiptap-pro/extension-export-docx` on the server-side:

```ts
import { exportDocx } from '@tiptap-pro/extension-export-docx'
import express from 'express'

const app = express()

app.post('/export-docx', async (req, res) => {
  try {
    // Get Tiptap JSON content from the request or from your database
    const { content } = req.body

    // Convert Tiptap JSON to DOCX
    const docxBuffer = await exportDocx({
      document: content,
      exportType: 'buffer',
      customNodes: [],
      styleOverrides: {},
    })

    // Send as a downloadable file
    res.setHeader(
      'Content-Type',
      'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
    )
    res.setHeader('Content-Disposition', 'attachment; filename="document.docx"')
    res.send(docxBuffer)
  } catch (error) {
    res.status(500).json({ error: error.message })
  }
})
```

## Extension storage

`editor.storage['export-docx']` holds three values for other export extensions:

| Key             | Value                                                    |
| --------------- | -------------------------------------------------------- |
| `Docx`          | The copy of the `docx` library that this extension uses  |
| `convertHeader` | The [`convertHeader`](/conversion/export/docx/headers-footers) function of this extension |
| `convertFooter` | The [`convertFooter`](/conversion/export/docx/headers-footers) function of this extension |

The export throws an error for a `Header` or `Footer` built with another copy of `docx`, because such an instance would write an empty header or footer. The [PDF export](/conversion/export/pdf/editor-extension) builds its headers and footers with these values when `ExportDocx` is registered, so they pass that check.

## Images that cannot be exported

The export fetches every image by its `src`. Some cannot be used: the URL returns a 404,
the host does not answer, or the format is one DOCX cannot embed. Word writes EMF for
pasted charts and equations, so documents that came from Word often carry one.

By default the export leaves that image out and carries on, so one broken picture does not
cost you the whole file. If the image was the only thing in its paragraph, the paragraph
goes too, leaving no blank line behind.

Pass `onWarning` to find out which images were skipped:

```js
ExportDocx.configure({
  onCompleteExport: result => saveAs(result, 'export.docx'),
  onWarning: warning => {
    console.log(warning.code, warning.src)
  },
})
```

Each warning carries:

| Field         | Description                                                                       |
| ------------- | --------------------------------------------------------------------------------- |
| `code`        | `image-missing-src`, `image-request-failed`, `image-fetch-failed`, or `image-unsupported-type` for an image. See [Warning codes](#warning-codes) for the other codes |
| `message`     | Readable summary, safe to log                                                     |
| `src`         | The image URL, when the node had one                                              |
| `status`      | HTTP status, when the host answered with a failure                                 |
| `contentType` | The detected type, for an unsupported format                                       |

Without `onWarning`, skipped images are reported through `console.warn`. Exceptions thrown
inside `onWarning` are swallowed, so a mistake in your handler cannot break an export.

To fail the export instead, set `onImageError: 'throw'`. The thrown error is one of
`ImageMissingSrcError`, `ImageRequestError`, `ImageFetchError` or `UnsupportedImageTypeError`,
all exported from the package and all extending `ImageConversionError`:

```js
import { ImageConversionError } from '@tiptap-pro/extension-export-docx'

try {
  await exportDocx({
    document,
    exportType: 'buffer',
    customNodes: [],
    styleOverrides: {},
    onImageError: 'throw',
  })
} catch (error) {
  if (error instanceof ImageConversionError) {
    console.log(`Could not use ${error.src}: ${error.code}`)
  }
}
```

<Callout title="Relative image URLs are not resolved" variant="hint">
  Export runs against the `src` exactly as stored. A relative URL such as `/img/chart.png` has
  no origin to resolve against, so it is reported as `image-request-failed` and skipped. Store
  absolute URLs the exporter can reach.
</Callout>

## Warning codes

`onWarning` receives every problem the export works around instead of failing. Set it on the extension or on the command. The command value replaces the extension value. Check `warning.code` to tell the warnings apart:

| `code`                      | The export sends it when                                                                                                                                                                                   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `image-missing-src`         | An image node has no `src`. The export leaves the image out.                                                                                                                                               |
| `image-request-failed`      | The image request did not complete, for example because the host did not answer or the `src` is not an absolute URL. The export leaves the image out.                                                       |
| `image-fetch-failed`        | The image host answered with a failure. `status` holds the HTTP status. The export leaves the image out.                                                                                                    |
| `image-unsupported-type`    | The image format is one DOCX cannot embed. `contentType` holds the detected type when the response declared one. The export leaves the image out.                                                          |
| `document-styles-failed`    | The export could not read some or all of the editor's [computed styles](/conversion/export/docx/computed-styles), for example those of a Pages header, or the editor changed while the export waited for fonts. The export goes on with fewer of the editor's styles. |
| `document-styles-dark-page` | The editor page is dark and you did not set `pageColor`. The file gets a dark page color and light text, and Word leaves page color out of PDFs and print. Export from a light page, or set `computedStyles: false`. Setting `pageColor` stops the warning but keeps the light text. |

The two `document-styles-` warnings carry only `code` and `message`. The package exports the types `ExportDocxWarning` and `OnExportDocxWarning` for your handler.

Without `onWarning`, the export logs each warning with `console.warn` as `[export-docx] <message>`. Problems with [automatic font embedding](/conversion/export/docx/fonts#automatic-embedding) never reach `onWarning`. They go to `console.warn`.

## Node attribute inference

The DOCX export automatically respects node-level attributes set by the editor, rather than always computing values from scratch. This means resized images, adjusted table columns, and other editor-level customizations are preserved in the exported document.

| Feature                                   | Description                                                                                                                                                                                               |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Image `width`/`height`**                | When an image has been resized in the editor, the user-set dimensions are used. Priority: `imageOverrides.transformation` > the size the editor shows, with computed styles > `node.attrs.width/height` > intrinsic dimensions. A size read from the editor that is wider than the room on the page shrinks to fit. A size from `imageOverrides` stays as you set it |
| **Image `alt` text**                      | Mapped to the docx `altText` property for accessibility metadata                                                                                                                                          |
| **Table cell `colwidth`**                 | Per-cell pixel array from editor-resized columns produces precise column widths in the export. On a fluid table the columns keep their proportions                                                        |
| **Table cell `rowspan`**                  | Cells spanning multiple rows are correctly exported                                                                                                                                                       |
| **Table `width`**                         | A table with an explicit `width` exports at that fixed width; a table with no width exports as a percentage of the text area (fluid) so it reflows to the page. In a list or quote, that percentage leaves room for the indent. [See Tables and the text area](/conversion/export/docx/page-layout#tables-and-the-text-area) |
| **Table borders**                         | The table's own borders (outer edges plus the inside horizontal and vertical grid) are exported; a borderless table stays borderless                                                                     |
| **Table cell `background`**               | Exported as cell shading                                                                                                                                                                                 |
| **Table cell borders**                    | Per-side cell borders (`width` / `style` / `color`) are exported; a cell border that differs from the table's is kept as an override                                                                     |
| **Table cell `verticalAlign`**            | `top` / `middle` / `bottom` exported as the cell vertical alignment                                                                                                                                      |
| **Table row `height` / `heightRule`**     | Row height is exported; `exact` clips to the height, `atLeast` treats it as a minimum                                                                                                                     |
| **Table cell margins**                    | `cellMarginTop` / `cellMarginRight` / `cellMarginBottom` / `cellMarginLeft` on the table node are exported as the table's cell margins. A table without them uses Word's default                          |
| **Paragraph `textAlign: 'justify'`**      | Correctly mapped to `AlignmentType.JUSTIFIED` (previously fell through to left alignment)                                                                                                                 |
| **Text run `backgroundColor`**            | `textStyle` mark `backgroundColor` exported as solid character shading                                                                                                                                    |
| **Paragraph/heading `lineHeight`**        | Proportional line height (a unitless multiple such as `1.5` or a percentage such as `150%`) is written as an "at least" line height of that multiple of the paragraph's font size. A fixed `px`/`pt` line height is written as an exact line height                                                 |
| **Paragraph/heading spacing**             | `spacingBefore` and `spacingAfter` are written as space before/after the paragraph                                                                                                                        |
| **Paragraph/heading indentation**         | `indent`, `indentRight`, and `firstLineIndent` are written as left, right, and first-line indentation; a negative `firstLineIndent` becomes a hanging indent                                              |
| **Paragraph/heading `contextualSpacing`** | Suppresses spacing between adjacent paragraphs of the same style in the export                                                                                                                            |
| **Paragraph/heading `keepNext` / `keepLines`** | Written as Word's keep-with-next and keep-lines-together pagination hints                                                                                                                            |

## What to expect

- **No authentication required.** The export runs entirely in the browser (or your Node.js server using the same package). No token, no API call. The one exception is `embedFonts`, which can download fonts from Google Fonts and sends WOFF2 fonts to the Convert Service.
- **Browser and server-side environments are both supported** via the same package. The server-side example above shows the Node.js path; the browser path is the default.
- **Result delivery through a callback.** The command returns at once. The `onCompleteExport` callback receives the exported file when the export finishes, as a `Blob`, `Buffer`, `Stream`, or `string` depending on `exportType`.

## What not to expect

- **Round-trip identity.** Importing a DOCX, editing it, and exporting it back is not byte-identical. A handful of attributes, such as tab stops, are extracted on import but not written on export today. See the [feature support matrix](/conversion/getting-started/feature-support-matrix) for the full list.
- **Pixel-perfect Word match.** We aim for visually faithful round-trips on the supported feature set; absolute parity with Word's rendering engine is out of scope.
- **Page layout from the editor.** DOCX export preserves headers, footers, and page-format settings you configure on the export options. It does not infer page boundaries from on-screen pagination, so pair it with the [Pages extension](/pages/getting-started/overview) when you need pagination-aware exports.
