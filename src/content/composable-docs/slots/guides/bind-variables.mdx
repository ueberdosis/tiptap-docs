Bind a slot to a [Variable](/composable-docs/variables/getting-started/overview) when its value should be reused elsewhere in the editor. Editing either bound slot updates the variable, its dependents, and every other slot bound to the same name.

## Configure the bindings

Install both `@tiptap-pro/extension-slot` and `@tiptap-pro/extension-variable`. Map slot IDs to variable names in the `Variable` extension:

```ts
import { Editor } from '@tiptap/core'
import StarterKit from '@tiptap/starter-kit'
import { Slot } from '@tiptap-pro/extension-slot'
import { Variable } from '@tiptap-pro/extension-variable'

const editor = new Editor({
  extensions: [
    StarterKit,
    Slot,
    Variable.configure({
      variables: {
        customer: 'Ada',
        greeting: ({ get }) => `Hello, ${get('customer')}!`,
      },
      slots: { customerField: 'customer', signatureField: 'customer' },
    }),
  ],
  content: {
    type: 'doc',
    content: [
      {
        type: 'paragraph',
        content: [
          {
            type: 'inlineSlot',
            attrs: { id: 'customerField' },
            content: [{ type: 'text', text: 'Ada' }],
          },
          { type: 'text', text: ' / ' },
          {
            type: 'inlineSlot',
            attrs: { id: 'signatureField' },
            content: [{ type: 'text', text: 'Ada' }],
          },
          { type: 'text', text: ' — ' },
          { type: 'variable', attrs: { name: 'greeting' } },
        ],
      },
    ],
  },
})
```

Each slot displays its value directly inside the slot. It does not contain an extra Variable node. The greeting reference is a separate, non-editable inline value.

## Update from either side

Typing inside a bound slot or filling it with `fillSlot` updates its variable:

```ts
editor.commands.fillSlot({
  id: 'customerField',
  content: [{ type: 'text', text: 'Grace' }],
})
```

You can also update the variable. Both slots are then refilled:

```ts
editor.commands.setVariable({ name: 'customer', value: 'Lin' })
```

## Initial values and text content

On editor creation, the first bound slot in document order supplies the variable's initial plain text value, including an empty string. Other slots bound to that variable are synchronized when the editor is created. If no bound slot exists, the configured value or resolver is used.

Slot edits produce strings. Setting a number or boolean displays its string representation in each slot; `null` displays as empty text. Block slot text uses newlines between blocks. Refilling a block slot writes a paragraph, and refilling an inline slot writes text. Bind text fields rather than rich documents when you want this behavior: formatting, embedded nodes, and nested structure are not copied to the other slots.

Every bound slot must have a unique ID. A bound slot cannot contain another bound slot. Missing slot IDs are allowed so a template can insert them later; a newly inserted slot supplies its text to the variable. If one transaction changes several slots bound to the same variable, the last changed slot in document order supplies the value.

Resolver-backed variables can also be bound. Editing a bound slot overrides the cached resolver value until that resolver is refreshed or one of its dependencies changes.

## Saving, undo, and protection

Filled slot text is part of the document. It is saved and exported, and undoing a slot edit updates the variable and its dependents. Bindings and resolvers stay in extension configuration, so provide them again when loading the document.

Synchronization respects Content Protection. If another bound slot cannot be updated, the source edit is rejected rather than leaving the slots with different values. Give the user permission to edit every slot in a binding group. Existing slot validation still applies to the filled content.

This integration runs only inside the client-side editor. It does not provide server-side filling or synchronize runtime variables between editor instances.
